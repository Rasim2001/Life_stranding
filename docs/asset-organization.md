# Организация ассетов: куда класть файл

**Статус:** действующий · **Принят:** 29.09.2026 · **Обновлён:** 29.09.2026 ·
**Основание:** фича `art-organization` (спек и тикеты 01–20, грилл пересмотра 29.09.2026)
**Проект:** SpiderRig · Unity 6.3 LTS (`6000.3.20f1`) · URP 17.3

Документ отвечает на вопрос **«в какой папке живёт файл»**. Как файл назвать — в
[`asset-naming.md`](asset-naming.md). Устройство сцены и чанк-префаба изнутри —
в [`scene-regulations.md`](scene-regulations.md).

Регламент обязателен для нового и для того, что трогаешь. Старое, которое не трогаешь, не
переносится ради красоты.

### Что было в прежнем регламенте и что решено

Прежний документ `asset-organization-and-naming.md` (статус «предложенный», 22.09.2026)
разделён на этот и `asset-naming.md`. Его разделы «Аудит текущего состояния» и «Безопасное
внедрение» не перенесены: миграция выполнена фичей `art-organization`, снимок устарел.

| Было | Решено на самом деле |
|---|---|
| `Art/<Тип>/<Домен>/<Набор>` — тип сначала | гибрид: уникальное у владельца-места, повторяемое в наборе или у объекта, система с кодом — модуль (§2) |
| `Materials/_Master`, `Materials/_Common`, `Textures/_Common` | упразднены; общее — только `Shared/<Type>/` (§3) |
| `Prefabs/Chunks/<Segment>/`, `Prefabs/Actors/`… | чанк — папка места в `Worlds`, актор — папка в `Actors` (§2) |
| присвоенный вендор уезжает «в `Art/` или `Scripts/`» | уезжает в `Modules/`, если у него есть код (§6.1) |
| `Settings/Weather/` для пресетов погоды | данные модуля живут в `Data/` модуля (§2.6) |
| `_TK_Tools`, `_PolygonPrototype` | `_Local`, `_BlockoutKit` (§6.3) |
| аудит считал `Modules` категорией D | `Modules` — продакшн наравне с `Art` (§7) |
| шрифты в `Art/Text` | `Art/UI/Fonts/<Family>/` (§2.7) |

## 1. Правило в один экран

```text
НОВЫЙ ФАЙЛ
   │
   ├─ сторонний пакет? ──────────► код → Plugins/<Vendor>; контент → ThirdParty/<Vendor>; внутри не трогаем
   ├─ сцена? ────────────────────► Scenes/ (scene-regulations.md)
   ├─ система с собственным C#? ─► Modules/<Name>/
   ├─ инструмент редактора? ─────► Editor/<Tool>/
   ├─ прочий код? ───────────────► Scripts/<Система>
   ├─ конфигурация движка? ──────► Settings/<Система>/
   ├─ грузится строкой? ─────────► Resources/ — только по §5
   └─ арт? ──────────────────────► Art/: чей он? (§2–3)
```

Шесть правил, которые нарушают чаще всего:

1. **Ссылки важнее красивого дерева.** Рабочий путь не меняется ради косметики.
2. **Один канонический дом.** Копия вместо переноса запрещена: у ассета один GUID.
3. **Новый ассет приватен владельцу**, пока не появился второй независимый потребитель (§3).
4. **Перенос — только в Unity.** Project window или `AssetDatabase.MoveAsset`; никогда
   проводник, `git mv`, `mv` (§8).
5. **`Resources` — API, а не склад** (§5).
6. **Внутри вендора порядок не наводим** (§6.1).

## 2. Карта

```text
Assets/
├─ Art/
│  ├─ Worlds/<World>/<Seg_NN>/<CHNK_NNN_Place>/   уникальное место (чанк)
│  ├─ Sets/<Domain>/                              кит, пропы и общий трим темы
│  ├─ Actors/<Name>/ · Actors/<Family>/<Name>/    повторяемый объект с поведением
│  ├─ Characters/<Name>/                          уникальное со скелетом
│  ├─ Cutscenes/<Name>/                           декорации катсцены
│  ├─ UI/<Feature>/ · UI/Fonts/<Family>/          интерфейс и шрифты
│  └─ Shared/<Type>/                              общее без лица
│
├─ Modules/<Name>/{Runtime,Editor,Shaders,Materials,Textures,Meshes,Prefabs,Data}
├─ Editor/<Tool>/          самостоятельные инструменты редактора
├─ Scripts/<Система>/      код без собственного контента
├─ Scenes/                 сцены (имена — asset-naming.md §6)
├─ Timeline/<Name>Cutscene/  .playable и .signal катсцен
├─ Settings/<Система>/     конфигурация движка и проекта
├─ Resources/              контракт строковой загрузки, §5
├─ Plugins/<Vendor>/ · ThirdParty/<Vendor>/   вендоры, §6.1
│
│  ── не в билде (§6.3) ──
└─ _Local/ · _BlockoutKit/ · _Experiments/ · _Archive~/
```

**Глубина — не больше пяти уровней от `Art`.** Каждый уровень отвечает на новый вопрос;
папка без собственного смысла не создаётся, пустые папки не заводятся.

**Растущие владельцы — чанк, набор, модуль, персонаж, катсцена — получают подпапки типа
с первого файла этого типа:** `Meshes`, `Materials`, `Textures`, `Animations`, `Audio`, `VFX`,
`Prefabs`, `Shaders`, `Data`. Имена подпапок — ровно эти, во множественном числе.

### 2.1 `Worlds` — место

Уникальное место мира — чанк: `Worlds/Tower/Seg_01/CHNK_004_Factory/`. В папке — всё
приватное этому месту: чанк-префаб в корне папки, его меши, материалы, текстуры, вложенные
пропы. Новый чанк — одна новая папка.

- **`CHNK_000_<Name>` — база сегмента**: подложка и общий рельеф под всеми чанками этажа.
  Номер `000` за ней зарезервирован; места маршрута нумеруются с `001`.
- Номер сегмента стоит в имени папки (`Seg_01`) той же ширины, что в имени сцены
  (`Seg_01_Base`). Номера чанков и имена мест уникальны в пределах мира.
- Папка сегмента и папка мира принимают **только своё личное** (эмбиент ветра сегмента,
  музыка столба). Общее между чанками туда не уходит: этаж — единица стриминга, а не тема.
- Сценовые данные чанка (ProBuilder-геометрия, overrides экземпляра) живут в `.unity`
  и папкой места не переносятся.

### 2.2 `Sets` — тема

Повторяемый кит уровня и его пропы: `Sets/LevelKit/`, `Sets/Factory/`. Набор заводится,
**только когда есть реальная тема**, которую делят несколько мест. Пустых `Sets/<Domain>`
«на вырост» не создаём.

### 2.3 `Actors` — объект с поведением

**Актором объект делает поведение** — собственный скрипт, работа по событиям, память, —
а не число мест, где он стоит. Мост, стоящий в одном чанке, — актор; статика без поведения —
проп или содержимое места.

Акторы **плоские по умолчанию**: префаб и зависимости в одной папке, группирует сортировка
по префиксам. Подпапки типа внутри актора включаются разово и осознанно решением владельца,
а не порогом по числу файлов: правило от числа файлов меняет адрес при росте.
Семейство похожих акторов — `Actors/<Family>/<Name>/` (`Actors/Products/`).

### 2.4 `Characters` — строго по скелету

Персонаж — то, у чего `SkinnedMeshRenderer` и риг. Размер комплекта ни при чём: сегодня это
только паук; цветок с большим комплектом — актор.

### 2.5 `Cutscenes` и `Timeline`

Декорации катсцены — `Art/Cutscenes/<Name>/{Meshes,Materials,Prefabs,Textures}`; папка
заводится только при наличии содержимого. `.playable` и `.signal` остаются в
`Assets/Timeline/<Name>Cutscene/`, в папку катсцены не переносятся. Общие сигналы
(`Blend*.signal`) — в корне `Timeline`. Написание — `Cutscene`, не `CutScene`.

### 2.6 `Modules` — система с кодом

**Модуль = собственный C# (runtime или editor) плюс контент для билда.** Контент без кода
модулем не является. Критерий проверяется взглядом на папку и не зависит от важности системы.
Сейчас: `ENV_Lit`, `Weather`, `TerrainScan`.

- Код, шейдеры, материалы и editor-инструменты системы — одна папка: правка шейдера и правка
  драйвера — одна работа.
- **Данные модуля — в его `Data/`**, не в `Settings/` (пресеты погоды — `Modules/Weather/Data`).
- Editor-код модуля — часть модуля. Самостоятельный инструмент, не принадлежащий системе, —
  `Assets/Editor/<Tool>/`. В `Assets/Plugins` инструменты не кладутся: код там компилируется
  в `firstpass`, которая не видит `Assembly-CSharp`.
- **Перед переносом любого шейдера** — поиск входящих `#include` по всему `Assets`, не только
  внутри модуля. `MoveAsset` строки `#include` не меняет, граф зависимостей их не видит.
  Модули могут подключать друг друга (`ENV_Lit` → `Weather/WeatherFog.hlsl`).

### 2.7 `UI` и шрифты

`Art/UI/<Feature>/` — интерфейс: текстуры, анимации (`Art/UI/Animations/`), видео.

**Шрифт — наш арт-ассет, не вендор**, даже если он сторонний: `Art/UI/Fonts/<Family>/`,
вместе с SDF-ассетами TextMeshPro и файлом лицензии. Лицензию (`OFL.txt` и подобное) не
удалять: у OFL это условие использования. OFL разрешает бесплатное коммерческое использование
и встраивание в билд; продавать шрифт отдельно нельзя, изменённая версия не может носить
исходное имя семейства.

### 2.8 `Settings`

Конфигурация движка и проекта: `Settings/<Система>/<Asset>`.

```text
Settings/Rendering/        URP Assets, Renderer Data, UniversalRenderPipelineGlobalSettings
Settings/Volume Profile/   профили Volume; VP_Default — профиль по умолчанию URP
Settings/LightSettings/    Lighting Settings Assets
Settings/World/            каталог мира и сегментов
Settings/Build Profiles/
```

| Настройка | Где лежит | Разделяется по сценам |
|---|---|---|
| тени, каскады, Light Probe System | URP Asset | нет — через Quality Level |
| Renderer Features | Renderer Data | нет |
| тонмаппер, Bloom, Color Adjustments | Volume Profile | да — ссылка в компоненте `Volume` |
| ambient, skybox, отражения | RenderSettings сцены | да |
| Lightmapping, Lighting Mode | Lighting Settings Asset | да — ссылка в сцене |

Не путать с корневым `ProjectSettings`: он управляется Unity. **Конфигурация проекта не
живёт внутри вендорского пакета** — она пропадёт при его обновлении.

## 3. Лестница общности

Куда идёт арт, который используют больше одного раза:

```text
владелец → семейство → тема (Sets) → мир → Shared
```

1. **Новый ассет приватен владельцу**, пока не появился второй потребитель.
2. **Второй потребитель — другой независимый владелец** (другое место, набор, актор, модуль).
   Несколько экземпляров внутри одного владельца — один потребитель: деталь завода, стоящая
   в заводе дважды, остаётся приватной заводу.
3. **Потребитель считается по прямым ссылкам на сам файл.** Префаб может быть приватным,
   а его меш — общим, если меш напрямую использует ещё одно место.
4. **Выбирается смысловая ступень, а не файловый предок.** Текстура, которую делят чанк
   и кит, уходит в `Sets/<Domain>`, хотя общий предок в дереве — корень `Art`.
5. **Ступень «мир» — только для того, что принадлежит миру целиком** (скайбокс, освещение,
   террейн мира). Модульный кит уровня — это тема, а не мир.
6. **`Shared/<Type>/`** — общее без лица: `Shared/Materials`, `Shared/Textures`. Ступень
   в имя файла не пишется: обобщение ассета не должно устаревать его имя.

**Исключение — временный арт.** Арт, который планируется заменить, при втором потребителе
**дублируется каждому владельцу**, а не поднимается в `Shared`: замена одного не должна
тащить за собой другого (случай скафандра паука и слона, тикет 11).

Обобщение ассета — один `MoveAsset` в новую ступень, без переименования.

## 4. Покрашенный vertex color сохраняется в mesh asset

Меш с вручную покрашенными каналами vertex color — авторский результат, даже если его создал
editor-инструмент. Порядок: покрасить → сохранить (Bake/Print) в отдельный mesh asset рядом
с мешами владельца → проверить vertex colors и UV2 → назначить сохранённый меш → удалить
временный компонент-хранилище. Компонент не остаётся в боевом префабе или сцене: он
сериализует лишние копии геометрии.

## 5. Контракт `Resources`

Unity включает всё из папок `Resources` в Player build и грузит по строковому пути без
расширения. Пути централизованы в `AssetsPath`.

> **Путь внутри `Resources` — часть программного контракта.** Перенос или переименование
> меняет ключ загрузки даже при сохранённом GUID. `.meta` защищает сериализованные ссылки,
> но не строку в коде.

**Новый ассет попадает в `Resources`, только если одновременно:**
1. его действительно грузят динамически, и сериализованная ссылка не подходит;
2. известен владелец загрузки и момент освобождения;
3. ключ хранится централизованно и проверяется, что разрешается в ассет.

«Так проще найти из кода» — не основание.

**Не класть:** исходники DCC, материалы и текстуры, которые и так приходят по ссылке из
префаба, контент «на будущее», тестовое, копию ассета с домом в `Art`. **Контент владельца
остаётся в `Art`**: зависимости ассета из `Resources` попадают в билд сами, а лишние файлы
в `Resources` раздувают индекс старта и становятся загружаемыми строкой без причины.

Структура `Resources/Prefabs/<System>/` и `Resources/StaticData/<System>/` заморожена до
предметной миграции. Вынос системы из `Resources` — отдельная задача: инвентаризация ключей →
выбор сериализованной ссылки или Addressables → одна система → проверка Player build → только
затем удаление ключа.

## 6. Вендоры и служебные папки

### 6.1 Вендорский остров

Код-плагин — `Plugins/<Vendor>`, контент в билде — `ThirdParty/<Vendor>`. Корень переносится
целиком через `MoveAsset`, имя вендора сохраняется. Внутри:

- не переименовывать и не раскладывать по нашим папкам;
- не исправлять опечатки поставщика;
- не добавлять свои файлы, если можно сделать адаптер снаружи;
- обновлять пакет отдельной задачей.

`_BlockoutKit` — тоже вендорская библиотека внутри: словарь имён к её содержимому
не применяется. Остров может жить **внутри модуля** — `Modules/TerrainScan/Packages/Custom
Attributes` не нормализуется.

Перед переносом корня — найти зашитые пути в коде вендора (`Assets/<Vendor>/…`, пути
сохранения, `#include`). `MoveAsset` их не меняет.

**Присвоение.** Вендорский ассет, который мы глубоко переработали и берём на поддержку,
перестаёт быть вендорским: с кодом — уезжает в `Modules/<Name>/`, без кода — в `Art/` по
лестнице общности; получает имена по словарю и больше не обновляется от поставщика.
TerrainScan присвоен 27.09.2026: источник открытый, доработан и поддерживается нами.

Вендор уходит целиком, когда появилась своя замена (Cozy Weather — после полной замены
встроенной погодой).

**Реестр правок внутри вендоров.** Вынужденная правка записывается сюда; при обновлении
пакета она слетит — после обновления пройти реестр и вернуть.

| Пакет | Файл | Что изменено | Зачем | Дата |
|---|---|---|---|---|
| RealBlend | `Assets/Plugins/RealBlend/Editor/VertexPainter_PaintTab.cs`, константы `PaletteRelativeDirectory`, `VertexColorPreviewShaderAssetPath` | `Assets/RealBlend/...` → `Assets/Plugins/RealBlend/...` | вендор зашил путь без `Plugins/`: превью vertex color не находило шейдер, палитры создавали корень `Assets/RealBlend` | 2026-09-22 |

### 6.2 Новые зависимости

Порядок предпочтения: Package Manager в корневом `Packages` → `Assets/Plugins/<Vendor>` →
отдельный корень, только если требует поставщик. Не импортировать пакет в `Art`, `Scripts`
или `Resources` без изолированного корня.

### 6.3 Корни с подчёркиванием

Для движка начальный `_` ничего не значит. Смысл задаёт правило проекта:
**корневая `Assets/_*` — не в билде**, без `_` — продакшн. Держит это аудит (§7).

| Корень | Значение |
|---|---|
| `_Local` | в `.gitignore`, только на диске владельца: непроверенные плагины, вынесенное чисткой. Файл под git не должен от него зависеть — на чистом клоне ссылка молча станет пустой |
| `_BlockoutKit` | кит блокаута. Маркерные материалы — `Materials/Markers/`, `Shaders/Markers/`, `Textures/Markers/`; `Kit/` — библиотека как есть. **Единственное исключение** из «не в билде»: в сценах допустим, пока уровень в работе, и считается долгом блокаута — к релизу уровня долг = 0 |
| `_Experiments/<Task>` | стенды и пробы; продакшн от него не зависит. Правила — `_Experiments/README.md` |
| `_Archive~` | выведенное из продакшна, под git; Unity не импортирует папки с `~`. `MoveAsset` в папку с `~` не пишет — переносить **до** тильды, и до тильды убрать все ссылки из билда внутрь |

Внутри веток `_Misc`, `_Temp`, `_Old`, `_Common`, `_Master` не создаются.

### 6.4 Ассеты, создаваемые движком

`UniversalRenderPipelineGlobalSettings`, `LightingData`, `Lightmap-*`, `ReflectionProbe-*` —
их имя часть контракта движка. Имя не нормализуем (при потере Unity создаст новый с
дефолтным именем, и переименованный останется мусором рядом); переносить можно — ссылки по
GUID; `LightingData` и карты рядом со сценой не трогаем — Unity перезаписывает при бейке.

**Ссылка на профиль Volume по умолчанию обязана вести на существующий ассет** (`VP_Default`).
Битую ссылку Unity молча чинит сам, создавая `DefaultVolumeProfile.asset` в корне `Assets`
при следующем импорте, — так было с 04.09 по 29.09.2026.

### 6.5 Старые корни

| Корень | Статус |
|---|---|
| `Assets/Materials`, `Assets/UI` | legacy; новые файлы запрещены |
| `Assets/Packages` | legacy / вендор; свой контент не добавлять |
| `Assets/MCP`, `Assets/Analyzers` | tooling; не смешивать с игровым |
| `TextMesh Pro` | создан Unity; не трогать |
| `SceneNotes`, `TutorialInfo` | назначение не определено; кандидаты на удаление после проверки ссылок |

«Legacy» не значит «срочно удалить» — значит «не увеличивать долг».

## 7. Аудит содержимого билда

`Assets/Editor/BuildContentAudit.cs`, меню `GD Tools/Build Content Audit`. Строит граф того,
что уходит в билд, и сверяет с ним папки; ничего не двигает и не удаляет. Отчёт —
`.scratch/build-audit/audit-report.md` и списки рядом.

**Входы билда:** включённые сцены из Build Settings; всё под `/Resources/` кроме `/Editor/`;
Always Included Shaders и Preloaded Assets; ассеты из настроек плеера (`GraphicsSettings`,
`QualitySettings`, `VFXManager`). Сцена — не зависимость: обход не проходит через `.unity`,
если это не вход.

**Продакшн-зона — `Art` и `Modules`.**

| | Что |
|---|---|
| A | в продакшн-зоне и в билде |
| B | в продакшн-зоне, используется только сценами вне билда |
| C | в продакшн-зоне, ни на что не ссылается |
| D | вне продакшн-зоны, но в билде |

**Правила**, каждое нарушение — ошибка:
1. файл под `Assets/_*` достижим из билда (кроме `_BlockoutKit` — выводится долгом блокаута);
2. файл под git зависит от `_Local`;
3. продакшн-зона зависит от `_Experiments`.

Отчёт также показывает фактический словарь имён по категории A (`asset-naming.md`).

**Когда запускать:** до и после массового переноса; перед релизной сборкой. В регламенте
**нет чисел, которые надо держать**: число файлов в A растёт вместе с игрой. Держать надо
«правила 1–3 — ноль нарушений».

**GUID-снимок категории A** — инструмент переноса: снимок «до» и «после» миграции показывает,
не выпало ли что-то из билда. Перенос GUID не меняет, поэтому разница — только реальные
потери. Вне миграций снимок не сравнивается.

**Слепые зоны.** Граф не видит `#include` (аудит разбирает их текстом, только пути внутри
`Assets`), строковые пути из кода, загрузку по строке вне `Resources`, ассеты для editor-
инструментов. Поэтому C — **кандидаты, а не приговор**: перед выносом из C — grep по `.cs`
на имя и путь и по `.shader`/`.hlsl` на `#include`.

## 8. Перенос, переименование, удаление

- **Только в Unity.** Project window, из кода — `AssetDatabase.MoveAsset`, папку назначения —
  `AssetDatabase.CreateFolder`. `MoveAsset` возвращает пустую строку при успехе; непустая —
  стоп. Проводник, `git mv`, `mv` запрещены: `.meta` отрывается, GUID меняется, ссылки рвутся.
- **Переименование — тем же `MoveAsset`**, что и перенос, одной операцией.
- **Перед переносом** — найти строковых потребителей: `Resources.Load`, `AssetsPath`, имена
  сцен, `AssetDatabase`-пути, `#include`. Для FBX со встроенными материалами — проверить
  импорт (`asset-naming.md` §5.3).
- **Одна предметная область — один коммит переноса**, отдельно от смысловых правок.
  Иначе потерю ссылки не отличить от нормального diff.
- **Case-only rename** (`interactive` → `Interactive`) на Windows — через временное промежуточное
  имя, отдельной операцией.
- **Удаление — только по указанию владельца:** сначала список, потом явное «да», потом
  `AssetDatabase.DeleteAsset` по одному. Вынос в `_Local` удалением не считается.
- Префабы, сцены и FBX на диске read-only (`lockable` в `.gitattributes`). `MoveAsset` это не
  мешает; `DeleteAsset` может вернуть `false` — снять атрибут у файла и `.meta`, повторить.

## 9. Чек-листы

### 9.1 Новый файл

- [ ] Понятно, чей он: место, набор, актор, персонаж, катсцена, модуль, UI.
- [ ] Лежит у владельца; в `Shared` — только при втором независимом потребителе.
- [ ] Подпапка типа — из списка §2, во множественном числе.
- [ ] Имя — по `asset-naming.md`.
- [ ] Не в `Resources` ради удобства.
- [ ] Не копия уже существующего ассета.

### 9.2 Перенос

- [ ] Перенос входит в задачу, а не попутная косметика.
- [ ] Найдены строковые потребители и входящие `#include`.
- [ ] Выполнен в Unity; `.meta` едет вместе.
- [ ] Консоль чиста, Missing нет, сцена владельца открывается.
- [ ] Diff — перенос, а не удаление плюс новый файл.
- [ ] Для массового переноса — аудит до и после, GUID-снимок без потерь.

## 11. Факт Unity или решение проекта

| Положение | Источник |
|---|---|
| `Editor`, `Resources`, `Plugins`, `~` имеют специальное значение | Unity ([Reserved folder names](https://docs.unity3d.com/6000.3/Documentation/Manual/SpecialFolders.html)) |
| `.meta` хранит GUID и должен двигаться с ассетом | Unity ([Asset metadata](https://docs.unity3d.com/6000.0/Documentation/Manual/AssetMetadata.html)) |
| путь `Resources.Load` — строковый ключ без расширения | Unity ([Resources system](https://docs.unity3d.com/6000.3/Documentation/Manual/LoadingResourcesatRuntime.html)) |
| код в `Plugins` компилируется в `firstpass` | Unity |
| гибридное дерево, лестница общности, модули | решение SpiderRig, фича `art-organization` |

Внутреннее устройство можно менять по опыту; механику `Resources`, `.meta` и специальных
папок голосованием не отменить.
