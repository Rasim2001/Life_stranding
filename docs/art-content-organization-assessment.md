# Организация арт-контента — оценка предложений и путь миграции

**Статус:** предлагаемое для рассмотрения, не является действующим регламентом  
**Дата:** 19.09.2026  
**Проект:** SpiderRig · Unity 6.3 LTS (`6000.3.20f1`) · URP 17.3  
**Оценены:** `art-content-organization-proposal.md` и
`art-content-organization-proposal-alt.md`  
**Действующий регламент:** `asset-organization-and-naming.md`

> Этот документ не разрешает массовое перемещение, переименование или удаление ассетов.
> Он отбирает наиболее полезные предложения из двух конкурирующих документов и задаёт
> проверяемую последовательность перехода. После принятия решения правила должны быть
> перенесены в действующие регламенты по `agents/doc-maintenance.md`.

## 1. Итог оценки

За основу следует взять приоритеты альтернативного предложения, а из основного —
пилоты, стресс-тест и проверки миграции.

Главная отдача находится не в названии корневых папок, а в четырёх свойствах:

1. обычная правка чанка не изменяет общую сцену;
2. у каждого ассета есть понятный владелец и один канонический GUID;
3. общие зависимости переиспользуются, а не копируются;
4. переносы и импорт проверяются по фактическим зависимостям и runtime-контрактам.

Целевая модель для пилота:

```text
Assets/Art/
├── Worlds/
│   └── <WorldId>/
│       └── Chunks/
│           └── <ChunkId>/
│               ├── CHN_<ChunkId>.prefab
│               ├── Meshes/       только если есть private-ассеты этого типа
│               ├── Materials/
│               ├── Textures/
│               └── VFX/
├── Library/
│   └── <Domain>/
│       └── <OwnerOrSet>/
├── UI/<Feature>/
├── VFX/<Feature>/
└── Rendering/
    ├── Shaders/
    └── GlobalMaterials/
```

`Library/<Domain>/<OwnerOrSet>` — гипотеза для пилота, а не доказанный окончательный
вариант. Один уровень `Library/Laboratory/{Meshes,Materials,Textures}` без владельцев
внутри снова размажет комплект объекта по типам.

## 2. Основания и граница доказательности

Проверено по проекту 19.09.2026:

- в `Assets/Art` — 2 056 файлов без `.meta`, около 1 093,83 MiB;
- `Seg_01_Base.unity` — 63 758 651 байт, около 60,8 MiB;
- в сохранённой сцене 67 секций `Mesh` и 500 записей `propertyPath`;
- в `Assets/Art/Prefabs/Chunks` — 19 prefab assets;
- семь MP4 из UI используются через `ProductsData.asset` и `VideoPlayer`;
- найдено 11 normal-подобных текстур, импортированных как Default;
- лабораторный компонент получает `_sealedProbe` и `_breachedProbe` через scene overrides;
- `ActorKeyAssigner` пропускает Prefab Stage;
- установленный код APV не поддерживает одновременную загрузку данных сцен из разных
  несовместимых baking sets;
- ProBuilder Export Asset по умолчанию не обязан заменять редактируемый оригинал:
  замена управляется отдельной настройкой.

Эти факты подтверждают наличие конкретных проблем и технических ограничений. Они не
доказывают заранее, что выбранное дерево ускорит ежедневную работу. Для этого нужны
пилот, пробный merge и замеры до и после.

Размер папки `Art` также не равен размеру build. Состав сборки определяется графом
зависимостей, `Resources` и build hooks, а не расположением файла в дереве.

## 3. Группа 1 — наибольшая ожидаемая эффективность

### 3.1 Тонкая сцена и содержательные chunk-prefabs

Сцена сегмента должна хранить композицию, сценовые системы и данные, которыми технически
владеет сцена. Завершённое содержимое участка должно находиться в `CHN_<ChunkId>` и его
ассетах.

В сцене допустимы:

- экземпляры чанков и их root transform;
- `Lighting/`: APV volumes, reflection probes, Volume и сегментный свет;
- `Contract/`: маркеры, `SegmentBounds`, `SegmentInjector`;
- действительно глобальные объекты сегмента;
- явно зарегистрированные данные конкретного экземпляра.

После блокаута в сцене не должны оставаться:

- embedded production meshes и редактируемые `ProBuilderMesh`, считающиеся финальными;
- loose FBX, материалы и prefabs, принадлежащие конкретному чанку;
- художественные изменения внутренностей чанка в виде случайных overrides;
- прямые зависимости чанк → другой чанк.

**Почему это первая группа:** текущая сцена уже является общим файлом размером 60,8 MiB.
Разделение по чанкам уменьшает область изменений и создаёт реальные файловые границы для
параллельной работы.

**Критерий:** обычная правка содержимого одного чанка не изменяет `.unity` и другие
chunk-prefabs.

### 3.2 Один чанк — один основной файл и одна единица работы

- `CHN_<ChunkId>` — основной prefab-файл чанка.
- Чанк редактируется в Prefab Mode, при необходимости в контексте сцены.
- На время правки у одного chunk-prefab один редактор.
- Общие actors, props и kit-elements остаются вложенными prefab-зависимостями.
- Role-subprefabs вводятся после подтверждённого конфликта дисциплин внутри одного чанка,
  а не заранее.
- Внутренняя иерархия следует `scene-regulations.md`.

Это даёт файловую изоляцию без преждевременного дробления каждого помещения на множество
формальных prefab-файлов.

### 3.3 Один канонический ассет и явное владение private/shared

- Ассет одного владельца хранится у владельца независимо от числа внутренних использований.
- Второй независимый потребитель запускает ownership review.
- Общий ассет переносится к конкретному общему владельцу; оба потребителя используют один GUID.
- Копирование ассета второму владельцу запрещено.
- Одинаковое имя или одинаковые байты не являются достаточным основанием для удаления копии:
  сравниваются import settings, назначение и потребители.

Правило масштабируется лучше дерева, в котором общие изменения распространяются через ручную
синхронизацию копий.

### 3.4 Политика импорта по роли ассета

Суффиксы карт используются как проверяемый сигнал:

| Карта | Суффикс |
|---|---|
| Base Color | `_BC` |
| Normal | `_N` |
| Metallic | `_M` |
| Roughness | `_R` |
| Smoothness | `_S` |
| Ambient Occlusion | `_AO` |
| Emission | `_E` |
| Height | `_H` |
| Opacity | `_O` |
| Packed mask | `_Mask` с документированным порядком каналов |

Суффикс помогает определить ожидаемые `Texture Type`, sRGB, compression и mipmaps, но не
заменяет контракт шейдера и проверку назначения. Vendor-ассеты и специальные карты требуют
явных исключений.

Для статических FBX отдельно проверяются import animation, material import, Read/Write и
настройки платформ. Автоматизация вводится после стабилизации правил на нескольких партиях.

### 3.5 Сохранение технической границы сцены

- persistent markers остаются scene-owned, пока выдача ID рассчитана на scene workflow;
- APV volumes, baking sets, reflection probes и generated lighting data принадлежат сцене
  или миру согласно действующим регламентам;
- чанк не должен хранить прямую сериализованную ссылку на scene object;
- такая ссылка заменяется только вместе с готовым coordinator или contract-key binding;
- перенос маркеров не должен перевыдавать существующие ключи.

Группировка `Contract/<ChunkId>/` полезна для навигации, но не устраняет конфликты: маркеры
по-прежнему сериализованы в одном файле сцены.

### 3.6 Безопасное перемещение с сохранением GUID

- Ассеты перемещаются через Unity Editor или `AssetDatabase` вместе с `.meta`.
- До переноса проверяются `Resources.Load`, строковые пути, editor scripts и build hooks.
- Структурный перенос не смешивается с художественной правкой.
- После переноса проверяются GUID, ссылки, Console, Play Mode и при необходимости build.
- Одна партия имеет одного владельца и может быть откатана независимо.

## 4. Группа 2 — высокая эффективность при подтверждённых условиях

### 4.1 Уникальные зависимости рядом с владельцем

Для уникального контента рекомендуется:

```text
Art/Worlds/<WorldId>/Chunks/<ChunkId>/
```

Это особенно полезно, если у чанка много уникальных моделей, материалов и текстур. Папка
упрощает передачу участка и просмотр его private-состава. Она не доказывает dependency closure:
shared-ассеты, markers, GameData и сценовые экземпляры проверяются отдельно.

### 4.2 Два пилота и измерение результата

Нужны два разных случая:

1. небольшой чанк с простыми зависимостями;
2. лаборатория с nested prefabs, actors, markers, overrides, probes и освещением.

На пилотах проверяются:

- время поиска типовых файлов художником и дизайнером;
- какие файлы меняются при обычной правке чанка;
- clean reimport и Player build;
- Play Mode и ключевые игровые сценарии;
- пробный merge двух независимых правок;
- целостность GUID, markers и GameData;
- удобство удаления или передачи чанка как единицы работы.

Только успешный пилот разрешает распространить выбранное дерево на остальные owners.

### 4.3 Разделение production, WIP и source

- В `Assets/Art` находится принятый игровой визуальный контент.
- Импортируемый WIP живёт в `Assets/Development/<TaskName>`.
- Production-сцены и prefabs не ссылаются на `Development`.
- `.blend`, `.psd`, `.kra`, high-poly и bake sources хранятся вне `Assets`, но остаются
  доступными и версионируемыми.
- `.bak`, экспортные копии и версии `_v2` не являются production-ассетами.

Папка `Development` не исключает содержимое из build сама по себе; отсутствие production-
зависимостей должно проверяться.

### 4.4 Vendor как целостные острова

- Один пакет рассматривается как один vendor island.
- Внутренняя структура пакета не нормализуется под правила проекта.
- Project-owned файлы не добавляются внутрь vendor island.
- Новые поставки отделяются от собственного контента.
- Существующие пакеты переносятся только при доказанной пользе и после проверки путей,
  `Resources`, shaders, editor scripts и процесса обновления.

### 4.5 Build audit и тяжёлые медиа

Семь UI-видео используются игрой, поэтому они не являются кандидатами на простое удаление.
Для них проверяются:

- фактический вклад в Player build;
- разрешение, длительность, codec и import settings;
- допустимое снижение размера без потери назначения;
- возможность потоковой доставки только при появлении соответствующего требования.

Та же логика применяется к vendor `Resources`, demos, samples и другим крупным бинарникам.
Экономия считается подтверждённой только по сравнению build и качества до/после.

### 4.6 Постепенная миграция старого контента

- Новый контент сразу следует принятой модели.
- Старый переносится владельцами небольшими dependency-замкнутыми партиями.
- Перенос выполняется отдельным changeset.
- Для переходного периода ведётся явный список уже перенесённых owners.
- Если новое дерево не становится основным в установленный контрольный срок, решение
  пересматривается.

## 5. Группа 3 — умеренная эффективность

### 5.1 Единый словарь имён

Для новых собственных ассетов сохраняется словарь `asset-organization-and-naming.md`.
К нему после принятия добавляется `CHN_`, если именно это написание будет выбрано.

- английский ASCII;
- смысловые блоки в `PascalCase`;
- без пробелов, `(1)`, `.001`, `Copy`, `Final`, `New`, `v2`;
- номер только для реального равноправного варианта;
- номер сегмента не входит в identity ассетов чанка;
- существующие файлы не переименовываются массово ради соответствия префиксам.

Преимущество `SM_` перед действующим `MSH_`, как и `AN_` перед `ANIM_`, не доказано и не
оправдывает появление второго словаря.

### 5.2 Подпапки только при наличии смысла

- Пустые type-folders не создаются ради симметрии.
- Основной prefab владельца лежит в корне owner-folder.
- `Meshes`, `Materials`, `Textures`, `Animations`, `VFX` создаются при наличии содержимого.
- `Misc`, `Other`, `Temp`, `New` запрещены без формального критерия.

Это снижает навигационный шум, но само по себе не решает зависимости или merge.

### 5.3 Тематическая общая библиотека

`Library/<Domain>/<OwnerOrSet>` предпочтительнее единой глобальной `Shared`, потому что
общая зависимость получает конкретного смыслового владельца. Преимущество этой схемы над
`Kits/Actors/Props` должно быть подтверждено пилотом.

Роль объекта остаётся в имени prefab и определяется действующим критерием:

> Actor — объект, которому нужны зависимости из `Gameplay` или у которого есть память.

Наличие анимации, света или звука само по себе не делает объект Actor.

### 5.4 Отдельный корень Audio

Отдельный `Assets/Audio` допустим как соглашение о границе визуального `Art`, но не должен
быть условием принятия всей миграции. Решение принимается вместе с определением назначения
корневой папки `Art`.

## 6. Группа 4 — высокий риск при сомнительной пользе или неприменимость

### 6.1 Массовое применение или удаление prefab overrides

Формула «применить либо удалить все meaningful overrides» опасна без классификации.
Overrides могут хранить:

- художественное содержимое, которое следует применить к prefab;
- root transform и данные конкретного экземпляра;
- persistent identity;
- временную либо устаревшую настройку;
- сценовую ссылку, для которой ещё не создана замена.

Каждая категория требует отдельного действия. В частности, простое удаление ссылок
лабораторного компонента на probes сломает переключение отражений.

### 6.2 Обязательный перенос всех vendor-пакетов

Перестановка существующего vendor island может нарушить строковые пути, импорт, shaders,
samples и обновление пакета. Новый адрес папки редко окупает такой риск сам по себе.

### 6.3 Actor как любой объект с поведением

Эта формулировка неприменима к действующей архитектуре: она превращает мигающую лампу,
декоративный Animator и ambient AudioSource в actors. Используется критерий зависимостей
из `Gameplay` или памяти.

### 6.4 MP4 как гарантированная дешёвая экономия

Видео занимает много места, но все семь файлов имеют runtime-потребителей. До замеров нельзя
обещать конкретную экономию или считать удаление безопасным.

### 6.5 Полная автоматизация импорта только по суффиксу

Один суффикс не описывает раскладку packed mask, особенности шейдера, источник normal map,
alpha, платформенные ограничения и vendor-исключения. Сначала применяется проверяемый ручной
контракт, затем узкая автоматизация подтверждённых случаев.

### 6.6 Big-bang migration и массовое переименование

Большой структурный diff затрудняет ревью, конфликтует с текущей работой и смешивает
перемещения с реальными изменениями содержимого. Миграция выполняется владельцами и партиями.

### 6.7 Безусловное уничтожение ProBuilder-оригинала после экспорта

Экспорт mesh asset можно выполнить без замены оригинала. Решение об удалении редактируемой
геометрии принимается отдельно после проверки результата. Незавершённая геометрия остаётся
в `_Blockout/` либо в другом явно определённом authoring-контексте.

## 7. Этапы миграции

### Этап 0. Утвердить целевую модель и границы

Входит:

- согласование дерева для unique и shared-контента;
- выбор `Library/<Domain>/<OwnerOrSet>` либо альтернативы после пилота;
- сохранение действующего словаря и решение по `CHN_`;
- классификация допустимых scene overrides;
- границы production, WIP, source, generated и vendor;
- назначение будущих владельцев регламентов.

**Условие выхода:** для нового ассета можно однозначно определить владельца и место; нет двух
конкурирующих обязательных правил.

### Этап 1. Зафиксировать исходное состояние

Входит:

- инвентаризация первой миграционной партии;
- прямые и транзитивные зависимости;
- `Resources`, строковые пути, editor scripts и build hooks;
- классификация embedded meshes, ProBuilder objects и overrides;
- снимок persistent IDs, markers и собранных GameData;
- размер сцены, время сохранения, время импорта и размер build;
- визуальные эталоны пилотных участков;
- фиксация пересекающейся активной работы в сценах и ассетах.

**Условие выхода:** известны потребители, исходные метрики, риски и граница первой партии.

### Этап 2. Остановить рост долга

Входит:

- новый production-контент создаётся по согласованной модели;
- WIP создаётся в `Development/<TaskName>`;
- production не ссылается на `Development`;
- новые vendor-поставки отделяются от project-owned content;
- новый импорт проверяется по роли;
- финальная embedded geometry больше не добавляется в production-сцены;
- существующие import anomalies исправляются небольшими проверяемыми партиями.

**Условие выхода:** новые изменения не увеличивают объём старого организационного долга.

### Этап 3. Провести два пилота

Пилоты: небольшой чанк и лаборатория.

Для каждого:

1. зафиксировать dependency closure, overrides, markers и сценовые связи;
2. сохранить финальную embedded geometry как owned assets;
3. сохранить редактируемые авторские источники;
4. перенести художественное содержимое в chunk-prefab;
5. классифицировать overrides вместо массового Apply/Revert;
6. заменить chunk → scene links только вместе с готовым binding-механизмом;
7. переместить private-ассеты в owner-folder с сохранением GUID;
8. проверить Prefab Mode и работу в контексте сцены;
9. выполнить clean reimport, Player build и Play Mode;
10. выполнить merge rehearsal двух независимых правок;
11. сравнить метрики и удобство поиска до/после.

Поведенческая правка, вынос геометрии и перемещение файлов оформляются отдельными
проверяемыми партиями.

**Условие выхода:** обычная правка чанка не меняет сцену; ссылки, свет, сохранения и GameData
целы; пилот подтверждён владельцем в Play Mode; выбранное дерево дало измеримую пользу либо
признано требующим пересмотра.

### Этап 4. Сделать production-сцену тонкой

Входит:

- последовательный вынос финальных embedded meshes;
- включение loose-контента в соответствующие чанки;
- удаление или применение только классифицированных художественных overrides;
- сохранение сценового владения APV, probes и generated lighting data;
- группировка markers по чанкам без перевыдачи ключей;
- явная маркировка оставшегося блокаута;
- регистрация обоснованных исключений.

Работа выполняется по одному чанку целиком, а не сначала по одному типу файлов во всей сцене.

**Условие выхода:** сцена в основном описывает композицию и сценовые системы; обычные правки
чанков её не меняют; размер и время сохранения сравнены с исходным состоянием.

### Этап 5. Перенести собственную библиотеку по владельцам

Порядок:

1. активно используемые наборы;
2. остальные production-наборы;
3. утверждённый будущий контент.

Входит:

- перенос private-комплектов целиком;
- назначение конкретных владельцев shared-ассетам;
- проверка cross-owner dependencies;
- сохранение одного канонического GUID;
- проверка строковых путей после каждой партии;
- удаление пустых старых веток после проверки потребителей;
- обновление списка перенесённых owners.

**Условие выхода:** у каждого перенесённого набора один канонический адрес, а старое дерево
сокращается по известной очереди.

### Этап 6. Оптимизировать тяжёлый и сторонний контент

Отдельными задачами:

- измерить вклад UI-видео в build и проверить варианты уменьшения;
- проверить vendor `Resources`, demos и samples;
- разобрать byte-identical duplicate candidates;
- завершить аудит texture и FBX import settings;
- переносить vendor islands только при самостоятельном обосновании;
- проверить восстановление бинарников и source storage через Git/LFS.

**Условие выхода:** экономия подтверждена build-замерами, а визуальное и игровое поведение
сохранено.

### Этап 7. Завершить переход и закрепить правила

Входит:

- clean clone, LFS pull, Unity reimport и Player build;
- Play Mode проверка владельцем;
- поиск ссылок на `Development` и старые строковые пути;
- проверка persistent IDs, markers и GameData;
- перенос подтверждённых правил в `asset-organization-and-naming.md`,
  `scene-regulations.md` и другие регламенты по маршрутизации;
- точечная автоматизация стабильных проверок;
- удаление либо регистрация переходных исключений;
- `Doc impact`, `Doc sync` и архивирование по workflow проекта.

**Условие выхода:** проект воспроизводится с чистого клона, действующие правила имеют один
источник правды, а переходное дерево больше не требует устных договорённостей.

## 8. Общие стоп-условия миграции

Партия останавливается и пересматривается, если:

- изменился GUID без отдельного решения;
- появились missing references или missing scripts;
- неясно, какие overrides относятся к экземпляру;
- обнаружена строковая зависимость, не покрытая проверкой;
- затрагиваются persistent keys или собранные GameData;
- меняется APV/baking contract;
- structural diff смешан с художественной или поведенческой правкой;
- чистый reimport или Player build не воспроизводит результат;
- два пилота не показали улучшения независимости правок и поиска.

## 9. Что принять из каждого предложения

Из `art-content-organization-proposal-alt.md`:

- приоритет тонкой сцены над косметикой дерева;
- существующий словарь префиксов плюс решение по `CHN_`;
- критерий Actor из действующего регламента;
- осторожность с vendor islands и массовой миграцией;
- отдельная проверка тяжёлых медиа;
- владелец для уникального и тематическая гипотеза для общего.

Из `art-content-organization-proposal.md`:

- два разных пилота;
- dependency inventory;
- clean reimport, build, Play Mode и merge rehearsal;
- проверка удобства поиска реальными ролями;
- stress-test роста мира и команды;
- подробные чек-листы переноса;
- явные критерии принятия решения.

Не принимать без переработки:

- массовое Apply/Revert overrides;
- Actor как любой объект с поведением;
- обязательный перенос существующих vendor islands;
- гарантированную экономию от удаления или переноса MP4;
- автоматический импорт, целиком определяемый именем файла;
- big-bang migration или массовое переименование ради эстетики дерева.

## 10. Решение о дальнейшем масштабировании

Распространение миграции за пределы двух пилотов разрешается только после ответа на четыре
вопроса:

1. Обычная правка чанка перестала менять общую сцену?
2. Два человека могут менять разные чанки без конфликта общих файлов?
3. Художник и дизайнер находят owner и его зависимости быстрее либо не медленнее?
4. Clean clone, reimport, build, Play Mode, persistent IDs и освещение сохранились?

Если ответ на любой вопрос отрицательный, корректируется модель или процесс пилота. Сам факт,
что новое дерево выглядит аккуратнее, не является основанием для дальнейшей миграции.
