# Организация арт-контента — альтернативное предложение

**Статус:** предлагаемое для рассмотрения, конкурирует с `art-content-organization-proposal.md`
**Дата:** 18.09.2026
**Проект:** SpiderRig · Unity 6.3 LTS (`6000.3.20f1`) · URP 17.3
**Основание:** разбор `art-content-organization-proposal.md` и `asset-organization-and-naming.md`
по существу, без презумпции, что любой из них утверждён.

> Документ не разрешает массовое перемещение, переименование или удаление ассетов.
> Он отвечает на вопрос, какие правила дают наибольшую отдачу при росте проекта,
> и в каком порядке их вводить.

## 1. Главный тезис

Ценность организации контента в этом проекте почти целиком лежит **не в дереве папок**,
а в контракте «сцена тонкая, чанк — один файл». Он даёт merge-изоляцию, быстрый
сейв и читаемый дифф. Дерево папок решает вторичную задачу — навигацию и передачу
участка другому человеку.

Поэтому правила разделены на два яруса:

| Ярус | Что | Зависит от оси дерева | Когда |
|---|---|---|---|
| **A** | контракт сцены и чанка, импорт, WIP, исходники | нет | сразу |
| **B** | ось дерева `Art`, словарь префиксов | да | отдельным решением |

Ярус A вводится независимо от того, какая ось будет выбрана.

## 2. Исходные факты

Проверено 18.09.2026:

- `Seg_01_Base.unity` — 60,8 МБ; остальные сцены проекта не больше 0,4 МБ;
- в `Art/Prefabs/Chunks` — 19 prefab assets;
- в `Assets` 24 корневые папки, из них `Development`, `ThirdParty` и `Audio` отсутствуют.

Взято из аудита `art-content-organization-proposal.md` §4 без повторной проверки:

- ~62,5 МБ сцены — 66 встроенных Mesh sections, плюс два крупных `ProBuilderMesh`;
- ~490 prefab overrides в сцене;
- компонент лабораторного чанка ссылается через оверрайды на две scene reflection probes;
- семь MP4 в UI — ~292,8 МБ;
- normal-текстуры, импортированные не как Normal Map;
- 942 из 1 999 файлов `Art` — vendor-острова.

Вывод из фактов: чанки введены, а сцена не похудела. Содержимое чанков живёт
в YAML сцены — встроенной геометрией и оверрайдами.

## 3. Ярус A — вводить сразу

### 3.1 Сцена слоя — только композиция

В сцене слоя допустимо:

- экземпляры `CHN_*` и их root transform;
- `Lighting/`: объёмы APV, reflection probes, Volume, сценовый свет;
- `Contract/`: маркеры, `SegmentBounds`, `SegmentInjector`;
- действительно глобальные объекты слоя.

В сцене слоя недопустимо после окончания блокаута:

- встроенные меши и `ProBuilderMesh`;
- loose FBX и материалы, принадлежащие конкретному месту;
- содержательные оверрайды внутренностей чанка;
- ссылки чанк → объект сцены и чанк → другой чанк.

`_Blockout/` остаётся законным местом для серых боксов до прихода художки.

**Критерий готовности:** обычная правка содержимого чанка не меняет файл сцены.

### 3.2 Чанк — один файл

- `CHN_<ChunkId>` — один prefab-файл, единица работы и merge.
- Правится в Prefab Mode.
- Один человек на один чанк на время правки.
- Внутреннее дерево — по `scene-regulations.md` §5: `StaticMesh/`, `Actors/`, `Live/`.
- Role-subprefabs (отдельные файлы под свет, звук и т. п.) не вводятся заранее —
  только когда доказан конфликт дисциплин внутри одного чанка.
- Meaningful override на экземпляре в сцене — либо применить в prefab, либо удалить.
- Связь с объектами сцены — через contract key или scene-level coordinator,
  не через сериализованную ссылку.

Первый известный кандидат на исправление — ссылка лабораторного чанка
на scene reflection probes.

### 3.3 Маркеры группируются по чанку

```text
Contract/
├── Laboratory/
├── Bridge/
└── SceneGlobal/
```

Маркеры остаются в сцене: выдача persistent ID рассчитана на scene workflow и
пропускает Prefab Stage. Группировка по чанку не убирает конфликты в YAML, но делает
видимыми осиротевшие маркеры при удалении или переносе чанка.

### 3.4 Суффиксы карт и импорт по суффиксу

| Карта | Суффикс |
|---|---|
| Base Color | `_BC` |
| Normal | `_N` |
| Metallic | `_M` |
| Roughness | `_R` |
| Smoothness | `_S` |
| Ambient Occlusion | `_AO` |
| Emission | `_E` |
| Height | `_H` |
| Opacity | `_O` |
| Packed mask | `_Mask`, порядок каналов записан рядом |

Суффикс — не косметика, а ключ для импорта. Пресет ставит Normal Map, sRGB и
компрессию по суффиксу, а не по папке. Поэтому правило работает при любой оси дерева.

Автоматический `AssetPostprocessor` — следующий шаг, не условие. До него — чек-лист
нового ассета (§6).

### 3.5 Исходники, WIP и тяжёлые медиа

- `.blend`, `.psd`, `.kra`, high-poly, bake sources — вне `Assets`.
- WIP, который надо увидеть в Unity, — `Assets/Development/<TaskName>/`.
  Production-сцены и prefabs на `Development` не ссылаются.
- `.bak`, экспортные копии и `_v2` в `Art` не допускаются.
- MP4 в UI (~292,8 МБ) — отдельная задача: проверить, нужны ли они в `Assets`
  и в каком разрешении и кодеке. Это самая крупная одиночная экономия.

### 3.6 Private и shared

- Ассет одного владельца лежит у владельца, сколько бы раз тот его ни использовал.
- Второй независимый потребитель → ассет переезжает к общему владельцу,
  оба потребителя ссылаются на один GUID.
- Копирование ассета во второго владельца запрещено.

## 4. Ярус B — ось дерева

### 4.1 Рекомендация: владелец для уникального, тема для общего

```text
Assets/Art/
├── Worlds/
│   └── <WorldId>/
│       └── Chunks/
│           └── <ChunkId>/
│               ├── CHN_<ChunkId>.prefab
│               ├── Meshes/
│               ├── Materials/
│               └── Textures/
├── Library/
│   └── <Domain>/            Laboratory, Industrial, Nature, Spider…
│       ├── Prefabs/
│       ├── Meshes/
│       ├── Materials/
│       └── Textures/
├── UI/<Feature>/
├── VFX/<Feature>/
└── Rendering/
    ├── Shaders/
    └── GlobalMaterials/
```

Type-подпапки внутри владельца создаются только при наличии содержимого.
Маленький чанк может быть одним файлом `CHN_Bridge.prefab`.

### 4.2 Почему владелец, а не тип

Главный вектор роста — уникальные чанки. При оси по типу каждый чанк размазан
по четырём зеркальным деревьям (`Models`, `Textures`, `Materials`, `Prefabs`).
Удаление чанка, передача его другому человеку, сбор его зависимостей — четыре обхода
вместо одной папки.

Второй довод — согласованность. `scene-regulations.md` §4 группирует иерархию сцены
по месту, потому что место совпадает с единицей работы. Папки по типу при иерархии
по месту — два способа мышления в одном проекте.

Ось по типу выигрывает в одном: при создании файла не нужно решать, кто владелец.
Поиск по типу закрывается фильтром `t:Texture`, пресеты — суффиксом (§3.4).

### 4.3 Почему `Library/<Domain>`, а не `Kits` / `Actors` / `Props`

Роль объекта меняется: пропу добавили поведение — он стал актором. При корнях
по роли ассет переезжает. Тема не меняется никогда: дверь лаборатории остаётся
в `Library/Laboratory`.

Роль уходит в имя: `PF_Actor_…`, `PF_Kit_…`, `PF_Prop_…`. Переименование дешевле
переезда и не рвёт логику поиска.

Критерий актора — две оси из `asset-organization-and-naming.md` §6.4: нужны
зависимости из `Gameplay` **или** есть память. Формулировка «имеет поведение»
слишком широка — по ней мигающая лампа становится актором.

### 4.4 Переходный период

Два дерева на переходе — неизбежная цена. Она ограничена правилом:

- новый контент — только в новом дереве;
- старый переносится **только при работе над его чанком**, отдельным коммитом,
  без смешивания с художественной правкой;
- массовой миграции нет.

Если через разумный срок новое дерево не стало основным, — решение пересматривается,
а не тянется бессрочно.

## 5. Именование

- английский ASCII, `PascalCase`, без пробелов, скобок, кириллицы;
- без `.001`, `(1)`, `Copy`, `Final`, `New`, `v2`;
- номер — только для реального равноправного варианта;
- номер слоя не появляется нигде, кроме имени сцены и её `SegmentDefinition`
  (`scene-regulations.md` §3).

Словарь префиксов один на проект. Из двух существующих вариантов основой берётся
словарь `asset-organization-and-naming.md` §6.3 — он полнее и содержит `DATA_`,
участвующий в контрактах загрузки. К нему добавляется `CHN_` для чанк-префаба.
Существующие файлы под префиксы не переименовываются.

## 6. Чек-листы

### 6.1 Новый ассет

- Определён владелец: чанк или тема библиотеки.
- Не создаётся копия уже существующего ассета.
- Имя и суффикс карты по словарю.
- Импорт соответствует роли: Normal Map, sRGB, Sprite, mipmaps, Read/Write.
- У статического FBX выключены import animation и import materials.
- Большой бинарник покрыт LFS.

### 6.2 Правка чанка

- Правка сделана в Prefab Mode.
- В сцене не осталось meaningful overrides.
- Файл сцены не изменился — либо изменение объяснимо (новый экземпляр, маркер, свет).
- Нет ссылок чанк → сцена и чанк → чанк.
- Маркеры в `Contract/<ChunkId>/` на своих местах.
- Проверено в Play Mode.

### 6.3 Перенос

- Только через Unity, вместе с `.meta`.
- Строковые пути, `Resources`, editor-скрипты проверены отдельно.
- Один перенос — один коммит, без художественной правки.
- После переноса: ссылки целы, Play Mode.

## 7. Порядок работ

| # | Шаг | Ценность | Цена |
|---|---|---|---|
| 1 | Запреты §3.1 на новую геометрию в сцене | высокая | ноль |
| 2 | Вынос встроенной геометрии из `Seg_01_Base` в ассеты | высокая | средняя |
| 3 | Применить или удалить оверрайды чанков; снять ссылку на probes | высокая | средняя |
| 4 | Импорт по суффиксу: ручной аудит normal maps и FBX | высокая | низкая |
| 5 | MP4 в UI | высокая | низкая |
| 6 | `Development/`, исходники вне `Assets` | средняя | низкая |
| 7 | Решение по ярусу B | средняя | решение |
| 8 | Новый контент — в новом дереве | средняя | низкая |

Шаги 2 и 3 делаются на одном чанке целиком, затем на следующем, — а не «все меши, потом
все оверрайды».

### Необратимое в шаге 2

`ProBuilderMesh` при сохранении в mesh asset теряет редактируемость в ProBuilder.
Перед экспортом решается по каждому объекту: геометрия финальная или ещё будет
правиться. Не финальная остаётся в `_Blockout/`.

## 8. Не делать сейчас

- массовую миграцию существующего дерева;
- перенос vendor-островов в отдельный корень — заморозить на месте и пометить;
- переименование существующих файлов под префиксы;
- отдельный корень `Audio` как пункт приёмки;
- удаление дубликатов без проверки GUID и ссылок.

## 9. Открытые вопросы

Ответы меняют приоритет яруса B, но не яруса A.

1. **Параллельная работа нескольких человек над чанками** — план ближайших месяцев
   или страховка? Если людей пока нет, ярус A окупается всё равно, а ось дерева
   можно отложить.
2. **Сколько уникального контента на чанк?** Если чанки в основном собираются
   из общей библиотеки и private-файлов у них единицы, довод за ось по владельцу
   (§4.2) заметно слабеет.
3. **Судьба `asset-organization-and-naming.md`.** После решения по ярусу B
   один из документов должен стать регламентом, а второй — уйти в историю.
   Три соглашения одновременно хуже любого одного.

## 10. Отличия от `art-content-organization-proposal.md`

| Тема | Там | Здесь |
|---|---|---|
| Приоритет | ось дерева, затем тонкая сцена (фаза 4) | тонкая сцена первой, ось отдельным решением |
| Общий контент | корни `Kits` / `Actors` / `Props` по роли | `Library/<Domain>` по теме, роль в имени |
| Критерий актора | «имеет игровое поведение» | зависимости из `Gameplay` или память |
| Словарь префиксов | новый, `SM_`, `AN_`, без `DATA_` | существующий §6.3 плюс `CHN_` |
| Vendor | перенос в `ThirdParty` фазой 6 | заморозить на месте |
| Пилоты | два пилота с merge rehearsal и замером поиска | сразу рабочий порядок по чанкам |
| Тяжёлые медиа | не в плане | отдельный шаг |
