## 0. Зачем этот документ

Проект вёл разработчик, который ушёл из команды. Нужно понять, что он успел построить,
и договориться о целевой структуре сцен до того, как в неё пойдут новые уровни.

Вводная от владельца проекта:
- планируется **полуоткрытый вертикальный мир** в духе OnlyUp — прохождение вверх по столбу;
- нужны **отдельные тестовые сцены** для фрагментов левел-дизайна, шейдеров/FX, новых фич;
- в тестовых сценах проверяется не только геометрия и её метрики, но и **эвенты**: двери,
  следящая камера, триггеры, поведение паука в ситуации;
- фрагмент либо **дозревает и уходит в билд**, либо **уезжает в архив** и билд его не видит;
- герой и игровая логика — **одна загрузка**, контент уровня — **другая**.

## 1. Разбор текущего состояния

### 1.1 Цепочка запуска (по коду)

```
Bootstrap.unity   →  ProjectContext (Resources/ProjectContext.prefab) → ProjectInstaller
                  →  Bootstrap.prefab → GameBootstrapper.Start() → StateMachine.Enter<BootstrapState>()
BootstrapState    →  LoadStaticData() из Resources        → LoadProgressState
LoadProgressState →  загрузка сейва                       → LoadLevelState
LoadLevelState    →  Curtain.Show()
                  →  LoadSceneAsync(GameStaticData.LoadScene)          ← Single
                  →  LoadAllScenes(GameStaticData.AdditiveScenes)      ← Additive
                  →  Curtain.Hide()
загруженная сцена →  СВОЙ SceneContext → SceneInstaller (298 строк, ~50 биндингов)
                  →  BuildLevelState.Initialize() → ждёт StartGame → InitGameWorld()
                  →  GameFactory спавнит паука / цветок / чекпоинты / генераторы / пикапы
```

Текущий конфиг в `Assets/Resources/StaticData/GameData/GameData.asset`:
`LoadScene: SCN_Test`, `AdditiveScenes: [Scene_StaticMesh]`, `TutorialSceneName: SCN_LevelDesingDraft`.

### 1.2 Эталонная пара (со слов владельца)

Последний работоспособный билд собирался из двух сцен:

| Сцена | Роль | Содержимое |
|---|---|---|
| `SCN_LevelDesingDraft` | база, Single | логика, DI, `SceneContext` |
| `Scene_StaticMesh` | аддитив | только статичный меш уровня, без логики |

Текущее `LoadScene: SCN_Test` — более позднее экспериментальное отклонение от этой пары.

**Это принципиально важно: нужный раскол уже существует в зародыше.** Логика в одной сцене,
контент в другой — ровно то, что требуется. Не хватает трёх вещей:

1. логическая сцена грузится как **Single**, то есть она база, а не резидентный слой;
2. она же тащит в себе 657 объектов контента — то есть логикой не ограничивается;
3. контентная сцена ровно одна и не нарезана.

Задача сводится не к «построить с нуля», а к «достроить и перевернуть уже начатое».

### 1.3 Что сделано правильно и переиспользуется

- Разделение состояний загрузки (`Bootstrap → LoadProgress → LoadLevel → BuildLevel`) — здоровая основа.
- Механизм аддитивной загрузки уже написан: `SceneLoader.LoadAllScenes()`.
- Данные уровня отделены от сцены и **уже ключуются по уровню**: `GameDatas` — это
  `Dictionary<string, GameData>`. Понятие «конфиг на уровень» в проекте есть.
- `SceneInstaller` имеет **всего одно сериализованное поле** (`_volume`) — то есть почти
  не привязан к конкретной сцене и переезжает дёшево. Важная хорошая новость.
- Шторка загрузки, сейв/лоад, локализация, машина состояний — в `ProjectContext`,
  живут корректно на уровне приложения.

### 1.4 Что блокирует поставленную задачу

**A. `SceneContext` + `SceneInstaller` лежат внутри каждой контентной сцены.**
Корень всего остального. Следствие видно в цифрах:

| Сцена | GameObject | PrefabInstance | SceneContext |
|---|---|---|---|
| `SCN_LevelDesingDraft` | 657 | 671 | да |
| `SCN_Test` | 657 | 671 | да |
| `SCN_LevelDesingDraft_Test` | 657 | 671 | да |
| `SCN_ForTutorialVideo` | 81 | 122 | да |
| `Test` | 58 | — | да |
| `Scene_StaticMesh` | 482 | — | нет (чистая геометрия) |
| `Scene_Light` | **0** | — | нет (пустая заготовка) |

Три сцены по 657/671 — клоны одной сцены. Новая тест-сцена сегодня делается через
«Save As» боевой целиком; дальше они расходятся, и правка в одной не доезжает до остальных.

**B. Аддитивная схема собрана «наизнанку».**
Резидентна *геймплейная* сцена, аддитивно подгружается *геометрия*. Нужно наоборот.

**C. Нарезка выбрана не по той оси.**
Раскол `Scene_StaticMesh` / `Scene_Light` — нарезка **по дисциплине** (меш отдельно, свет
отдельно) в пределах одной области. Для вертикального мира нужна нарезка **по области** —
на высотные сегменты. `Scene_Light` при этом пустая: раскол по дисциплине начали и не довели.

**D. Контент уровня спавнится из запечённых координат.**
Спавн паука, цветок, чекпоинты, генераторы, батарейки, энергия, «слоны», скиллы — всё из
`GameStaticData.GameDatas[имя_активной_сцены]`. Координаты туда **запекаются из маркеров
сцены** редакторным инструментом (разбор в 1.6) — то есть авторятся дизайнером в сцене,
а не вводятся руками.

Проблема не в подходе, а в ключе: словарь ключуется именем активной сцены, и в `GameFactory`
**8 обращений, все без `TryGetValue`**. Сцена, для которой не нажали «Collect», роняет игру
с `KeyNotFoundException`.

`GameDatas` читает ровно один класс — `GameFactory`. Больше у словаря потребителей нет.

**E. Имя сцены — это геймплейная логика.**
`SceneLoader.IsTutorialScene()` сравнивает имя активной сцены со строкой из конфига.
По нему ветвятся четыре места:

| Место | Что делает при `IsTutorialScene() == false` |
|---|---|
| `AbilityService.IsExploredAbility()` | попапы описания способностей **не показываются вообще** |
| `TasksService.IsWasOpened()` | попапы задач **не показываются вообще** |
| `FlowerPickup.Update()` | первый подбор цветка идёт без вступительного флоу |
| `GeneratorPickup.Update()` | первый запуск генератора идёт без вступительного флоу |

Подробный разбор семантики — в разделе 9.

**F. Тулинг есть для маркеров, но не для сцен.**
В `Assets/Editor/` лежит рабочая оснастка: цветные гизмо маркеров (`BatteryPointEditor`,
`SpiderSpawnMarkerEditor`) и кнопка запекания (`GameDataEditor`).

Чего нет — переключателя уровней и `playModeStartScene`.
Смена уровня = открыть `GameData.asset` и вписать строку.
Play с открытой тестовой сцены не работает: `GameBootstrapper` есть только в `Bootstrap.unity`,
машина состояний не стартует, `GameStaticData` остаётся null.

**G. Мелочи, подтверждающие незавершённость**
- `MainMenuState.Enter()` грузит сцену с именем `""`; состояние забиндено, но не используется.
- `ProjectInstaller` биндит фабрику `GameBootstrapper` на путь `Prefabs/GameBootstrapper`,
  которого нет (реальный префаб — `Resources/Bootstrap.prefab`). Биндинг мёртвый.
- `"ExitGameLoop"` захардкожен строкой в `ExitGameLoopState`.
- `GameScene` в Build Settings отключена; `Scene_Light` включена, но не используется.

### 1.5 Ключевое следствие: имя активной сцены выполняет три роли

Это главный технический вывод разбора и главный риск миграции.

```
SceneManager.GetActiveScene().name
   ├─ 1. хост DI         → в этой сцене лежит SceneContext + SceneInstaller
   ├─ 2. ключ контента   → GameDatas[имя]: спавн паука, цветка, чекпоинтов, пикапов
   └─ 3. флаг туториала  → IsTutorialScene() → правила AbilityService / TasksService
```

Сейчас это работает по совпадению: логическая сцена грузится Single, значит она же активная,
значит все три роли схлопываются в одну строку `SCN_LevelDesingDraft`.

**Как только логика переезжает в резидентный `Gameplay.unity`, все три роли ломаются
одновременно:** активной становится другая сцена, `GameDatas["Gameplay"]` ключа не имеет,
`IsTutorialScene()` навсегда возвращает false.

Поэтому в целевой схеме обязателен явный объект «текущий уровень», отвечающий на все три
вопроса вместо имени сцены. Это не украшение — **без него миграция технически невозможна**,
и это первое, что нужно сделать. Форма конфигурации — в разделе 6.1.

### 1.6 Пайплайн маркеров — выбранный гибрид уже существует

Находка, меняющая оценку работ. В `Assets/Scripts/Common/SceneMarkers/` лежит полный набор
маркеров, один в один повторяющий поля `GameData`:

`SpiderSpawnPointMarker` · `FlowerPointMarker` · `CheckPointMarker` · `BatteryPointMarker`
`EnergyPointMarker` · `ElephantPointMarker` · `GeneratorPointMarker` · `ProductSkillPointMarker`

Рабочий цикл дизайнера:

```
1. расставить маркеры в сцене       ← цветные гизмо, видны во вьюпорте
2. выделить GameData.asset
3. нажать «Collect»                 ← GameDataEditor сканирует АКТИВНУЮ сцену
4. координаты запеклись в GameDatas[имя активной сцены]
5. в рантайме GameFactory спавнит по запечённым координатам
```

То есть выбранный гибрид **уже реализован**: сцена — источник авторинга, ScriptableObject —
запечённые рантайм-данные. Это ровно тот процесс, который помнит владелец.

**Но пайплайн ломается об аддитивную схему там же, где и всё остальное:**

| Проблема | Следствие |
|---|---|
| `Collect` ключует по `GetActiveScene().name` | при резидентном `Gameplay` всё запечётся в ключ «Gameplay» |
| `FindObjectsOfType` сканирует **все загруженные сцены** | при нескольких открытых сегментах маркеры разных уровней молча сольются в один ключ |
| `GetUniqueId()` = `Guid.NewGuid()` на каждом нажатии | **повторный Collect инвалидирует сохранения** |
| `FindObjectOfType<SpiderSpawnPointMarker>()` без проверки на null | сцена без маркера спавна роняет инструмент `NullReferenceException` |
| `ElephantPoints` запекаются без `UniqueId` | несогласованность с остальными типами |

Инвалидация сохранений — не гипотеза. `UniqueId` из `GameDatas` штампуется на заспавненный
объект (`GameFactory`) и служит **ключом сохранения** для чекпоинтов, генераторов, батареек
и энергии (`CheckPoint.cs`, `Generator.cs`, `CheckpointData`, `GeneratorData`).
Новый `Guid.NewGuid()` при каждом Collect не совпадёт с сохранённым — пройденные чекпоинты
и запущенные генераторы сбрасываются.

**Переход к стабильным id уже начат и брошен.** `MarkerBase` с полем `UniqueId` написан
ровно под это, но от него наследуется **только `EnergyPointMarker`** — остальные семь
маркеров остались голыми `MonoBehaviour`. И даже для энергии `GameDataEditor` игнорирует
это поле и всё равно вызывает `Guid.NewGuid()`. То есть поле мертво даже там, где есть.

**Влияние на конечный билд — практически отсутствует.** Для одного отдельно взятого билда
GUID'ы фиксируются последним Collect перед сборкой и дальше не меняются; сейвы игрока
работают. Проблема проявляется в двух местах: при **патче** (Collect перед обновлением
перегенерирует id → у игроков слетает прогресс по чекпоинтам, генераторам, батарейкам,
энергии) и **в текущей разработке** (свои тестовые сейвы сбрасываются после каждого Collect).
Collect переписывает только запись активной сцены — другие уровни свои id сохраняют.

Предложение по этому пайплайну — в разделе 7.1.

Задел под поставленную задачу заложен, но остановлен ровно на середине.

## 2. Опора на индустриальную практику

Совпадает у Unity, у практиков и в документации Zenject.

**Трёхслойная схема сцен.** Крошечная сцена входа поднимает персистентные системы;
контент грузится аддитивно поверх. Продвинутая форма — держать персистентный слой
загруженным и **подменять только контентные сцены сверху**. Прямая формулировка из источников:
не копипастить один и тот же набор объектов настройки в каждую сцену.

**Zenject даёт под это готовый механизм:** `SceneContext.ContractNames` / `ParentContractNames`
для явных зависимостей между сценами, `ZenjectSceneLoader` с `LoadSceneRelationship.Child`,
`SceneDecoratorContext` для расширения сцены без её правки, `SceneParentAutomaticLoader`
для редактора. Проект **не использует ничего из этого** — грузит голым `SceneManager.LoadSceneAsync`.
Это и есть причина, по которой `SceneContext` пришлось положить в каждую сцену.

**Строковые имена сцен — признанный анти-паттерн.** Переименование или перенос ассета
молча ломает ссылку. Решение — обёртка `SceneReference` (GUID + путь) с PropertyDrawer.

**Мульти-сцена снимает merge-конфликты.** Сейчас любая правка геймплея в сцене — конфликт
в 657-объектном YAML.

**Play с любой сцены** — стандартно решается `EditorSceneManager.playModeStartScene`.

## 3. Целевая архитектура: слои

| Слой | Время жизни | Что внутри | Кто редактирует |
|---|---|---|---|
| **Bootstrap** | вся сессия приложения | `ProjectContext`, статик-дата, сейв, машина состояний, шторка, локализация | программист, редко |
| **Gameplay** | вся игровая сессия | `SceneContext` + `SceneInstaller`, паук, камера, HUD/UI, геймплейные сервисы, директор стриминга | программист |
| **Content** | сменный | геометрия, коллайдеры, эвенты, маркеры, свет сегмента | левел-дизайнер, художник |

Правило, из которого следует всё остальное (переформулировано по итогам внешней критики —
прежняя редакция «нужен в каждой сцене → его место в `Gameplay`» буквально запрещала
наш же контракт сегмента из раздела 7):

> **Глобальное состояние игровой сессии** — паук, камера, HUD, геймплейные сервисы,
> директор стриминга — живёт в `Gameplay` в **одном** экземпляре.
>
> **Одинаковое по структуре, но локальное по данным и жизненному циклу** — точка входа,
> границы сегмента, локальный Volume и свет полосы, reverb-зона, эмбиент локации,
> маркеры, роутер эвентов сегмента — **остаётся в сегменте**.
>
> Совпадение типа объекта не означает, что экземпляр должен быть один.

**Проверка в одну строку:** объект хранит состояние **всей сессии** → `Gameplay`;
состояние **этого места** → сегмент.

### 4.1 Коридор падения — политика, а не константа

Неочевидное следствие жанра. В OnlyUp-подобной игре падение за секунды проносит игрока
через несколько сегментов вниз. Обычная схема стриминга «держим N−1, N, N+1» ломается:
игрок влетает в невыгруженную геометрию.

Глубина падения как гейм-дизайн ещё не определена, поэтому **директор проектируется
с настраиваемой политикой выгрузки**, а не с зашитым правилом:

| Политика | Поведение | Когда годится |
|---|---|---|
| `KeepAll` | весь столб резидентен | ранний прототип, малый объём контента |
| `KeepBelowCheckpoint` | держим всё до последнего пройденного чекпоинта | падение до чекпоинта; безопасно, дороже по памяти |
| `KeepN` | держим N сегментов вниз | **только после замера** — см. условие безопасности ниже; до замера не применять |
| `KeepActiveOnly` (= `KeepN(1)`) | только активный + один соседний | **отладочная**: в бою не используется, обязана существовать с первого дня реализации стриминга — самый жёсткий прогон жизненного цикла сегмента (9.17) |

Смена политики — настройка, а не переписывание директора. Реальную цену по памяти меряем
на живом контенте, когда он появится.

**Условие безопасности `KeepN`** (добавлено по итогам второй внешней критики). При падении
нижний этаж обязан быть активирован **раньше**, чем паук войдёт в его триггеры. Отсюда
проверяемое неравенство:

```
глубина резидентной геометрии ниже игрока
  ≥  максимальная скорость падения
     × худшая задержка (load + inject + register + activate)
     + запас
```

Это тот же принцип, что и минимальная толщина коллайдера в 7.3 (скорость падения × шаг
физики), только применённый к задержке стриминга вместо шага симуляции.

**Пока эти числа не замерены, `KeepN` применять нельзя** — доказуемо безопасны только
`KeepAll` и `KeepBelowCheckpoint` (удержание всего достижимого коридора до гейта).
Что мерить — в таблице 4.2.1 и в базисе физики 7.3.

### 4.2 Про нарезку по дисциплине

Ось полезная, но вторичная — решает merge-конфликты, когда над одной областью работают
двое. **Основная ось — сегмент**; дробить сегмент на `_Art` / `_Design` только там, где
это реально нужно по составу команды. Иначе комбинаторный взрыв сцен.

### 4.2.1 Выгрузка сцены ≠ освобождение памяти

> По итогам второй внешней критики. Все политики выше построены на предпосылке
> «выгрузили сегмент — освободили память». **Предпосылка не выполняется сама собой.**

`UnloadSceneAsync` уничтожает GameObject'ы и убирает сцену, но **ассеты — меши, текстуры,
материалы, аудиоклипы — остаются в памяти**, пока не вызван `Resources.UnloadUnusedAssets`.
Этаж исчезнет из Hierarchy, а профайлер покажет ту же цифру.

**Наше усугубление:** проект грузится через `Resources`, а `StaticDataService` держит
ссылки на всю статик-дату всю сессию. Загруженное оттуда не освободится **никогда**,
сколько сегментов ни выгружай. Это ещё один довод к правилу «чанки — ссылками из сцены,
не через `Resources`» (9.6).

*Остро критично к старту — политика, а не числа:*

1. **`UnloadUnusedAssets` не вызывается после каждой выгрузки сегмента.** Он обходит весь
   граф объектов — это столл, а не фоновая операция.
2. **Вызывается в безопасные моменты**, которые у нас уже есть: под шторкой
   (`ICurtainRoot`), на гейте чекпоинта (там и так выгружаются нижние этажи), при рестарте
   и смене уровня.
3. **Освобождению мешают удержанные ссылки** резидентных сервисов. Ревизия реестров уже
   отложена (раздел 12) — она же закрывает и этот вопрос: ссылка, забытая в резидентном
   сервисе, держит ассет так же надёжно, как живой объект.
4. **Без замера политика бессмысленна.** Проверять не «сцена ушла из Hierarchy»,
   а фактически освобождённую память.

*Заполняется при профилировании:*

| Параметр | Значение |
|---|---|
| допустимый столл на `UnloadUnusedAssets` | __ мс |
| фактически освобождается на выгрузке этажа | __ МБ |
| частота вызова (каждый гейт / каждый N-й) | __ |

### 4.3 Состав `World_Common` — критерий

> Принято по итогам внешней критики: список «Volume, skybox, солнце, вода, погода, ветер,
> звук» был дан без признака, по которому туда что-то попадает. Без критерия сцена со
> временем собирает всё «вроде глобальное» и превращается в монолит, который боятся трогать.

**Критерий: в `World_Common` живёт только scene-bound** — то, что обязано быть объектом
или настройкой сцены. Всё остальное идёт своим механизмом.

| Элемент | Где живёт | Статус в проекте |
|---|---|---|
| солнце (направленный свет) | **сцена** `World_Common` | scene-bound |
| глобальный Volume | **сцена** `World_Common` | scene-bound; `SceneInstaller._volume` |
| skybox, ambient | **настройки Lighting сцены** | не объект вовсе |
| профили Volume | статик-дата | `VolumeProfilesStaticData` — уже есть |
| параметры воды | статик-дата | `WaterStaticData` — уже есть |
| вода, водопады | префабы из `Resources` | `GlobalWaterPath`, `WaterFallsPath` |
| погода | префаб | `Prefabs/Common/Cozy Weather Sphere` + `CozyWeatherChanger` |
| звук окружения | звуковой слой | не существует (9.8) |

Пять позиций из восьми уже живут не в сцене — монолита по построению не выходит,
`World_Common` остаётся тонким.

**Отклонён `WorldEnvironmentDefinition`** — прямое нарушение правила 6.1 «конфиг не хранит
того, что уже решается другим механизмом»: `VolumeProfilesStaticData` и `WaterStaticData`
существуют, новый definition стал бы третьим местом для тех же данных.

**«Сцена, которую боятся трогать»** — на этот случай уже есть правило 9.14: двое над одной
сценой = триггер разделения. Новая машинерия не нужна.

*Возможно пригодится в будущем:* если погода станет геймплейной и stateful (сцепление лап,
видимость), она переезжает в **сервис резидентного игрового слоя**, а не остаётся в сцене
окружения. Признак тот же, что у акторов (9.13-D): **есть ли у неё память**.

**Активная сцена — `World_Common`.**

> По итогам второй внешней критики. Документ убрал геймплейную зависимость от **имени**
> активной сцены (1.5), но не назначил политику самой активной сцены. А она в Unity
> определяет две вещи: куда падают созданные кодом объекты без явного владельца
> и **чьи Lighting Settings применяются**. Аддитивная загрузка активную сцену не меняет.

Без явного решения это ломает два уже принятых правила:

| Что ломается | Как |
|---|---|
| **Свет (4.3)** | skybox и ambient положены в `World_Common`, но Unity берёт их из активной сцены. После миграции `Bootstrap` грузится Single и остаётся активным — применятся его настройки, а света в нём нет |
| **Размещение (7.2.1, 8.1)** | фабрика без явного владельца кладёт объект в активную сцену. Окажись активным сегмент — переносимый груз уедет туда и умрёт при выгрузке |

**Политика:**

1. **Активная — `World_Common`.** Назначается один раз, `SetActiveScene`, сразу после
   загрузки резидентного слоя. Она резидентна, поэтому активная сцена никогда
   не становится невалидной, и она же владеет Lighting Settings по 4.3.
2. **Сегмент активным не делается никогда.** Это переключило бы освещение всего столба
   на настройки одного этажа.
3. **Все рантайм-объекты создаются с явным владельцем** — сегмент, динамический слой
   или `Gameplay`. Активная сцена остаётся **сетью безопасности**, а не механизмом
   размещения: объект без явного владельца попадёт в резидентную `World_Common`,
   то есть отказ будет безопасным — утечка, а не уничтожение при выгрузке.
4. **`SetActiveScene` вызывается ровно один раз** за сессию. Любой другой вызов —
   повод разобраться, а не поведение по умолчанию.

## 5. Схема B — структура для тестирования фрагментов

Главный принцип, ради которого всё затевается:

> **Тестовая сцена авторится ровно как сегмент билда.**
> Тогда «фрагмент дозрел» = внести его в каталог. «Фрагмент в архив» = убрать из каталога.
> Внутри сцены при этом не меняется ничего.


### 5.1 Два режима проверки: песочница ≠ приёмка

> По итогам внешней критики. Прежняя формулировка «резидентный слой байт в байт тот же»
> была неточной: **файлы те же, среда — нет.** `Sandbox_Root` подменяет директора,
> а именно в директоре живёт весь жизненный цикл — окно инъекции (8.1), выгрузка
> и восстановление состояния (9.17), передача владения объектами (7.2.1, 7.2.2).
> Фрагмент может безупречно работать в песочнице и сломаться при первой настоящей
> аддитивной загрузке.
>
> Критика заодно вскрыла противоречие, внесённое ранее: пункт приёмки «прогнать сегмент
> в политике `KeepActiveOnly`» был приписан песочнице — среде, где директора нет,
> а значит и политики стриминга быть не может.

| Режим | Что проверяет | Инструменты |
|---|---|---|
| **Authoring Sandbox** | форма, метрики, декор, поведение акторов в изоляции. Быстрая петля | debug-HUD, телепорт, слоу-мо, форс-запуск эвентов — всё остаётся как есть |
| **Production Simulation** | полная цепочка: `Bootstrap` → резидентный слой → каталог → **настоящий директор** → жизненный цикл сегмента | debug выключен либо строго read-only |

**Правило: Authoring Sandbox необходим, но приёмкой не является.** Фрагмент считается
готовым только после Production Simulation. Песочница при этом ничего не теряет — гейт
добавляется, а не заменяет.

*Форма Production Simulation — вариант выбирается на миграции:*

| Вариант | Как | Цена |
|---|---|---|
| **A. Самый дешёвый: ничего не строить** | запустить обычный билд/Play с `Bootstrap`, реальный каталог, дойти или телепортироваться до сегмента | ноль новой машинерии |
| **B. Редакторный режим** | пункт меню «прогнать сегмент как в билде»: поднимает цепочку и ставит паука на точку входа | инструмент, но экономит время на каждом прогоне |

Начинать разумно с варианта A — он появляется сам вместе с директором и каталогом,
строить под него ничего не нужно.

**Архив — папка с тильдой: `_Archive~/`** (по итогам внешней критики).
Unity **полностью игнорирует папки, имя которых заканчивается на `~`**: не импортирует,
не создаёт `.meta`, не находит через `AssetDatabase.FindAssets`, не кладёт в билд,
не конфликтует по GUID. Папка при этом остаётся на диске и в git. Это штатный механизм
Unity — так устроены `Documentation~` в пакетах; в проекте приём пока не используется.

Одним символом закрывается почти весь список рисков: сканирование редакторным тулингом
и нашими же валидаторами, находки в `FindAssets`, время импорта, попадание в билд.

| Правило архива | Зачем |
|---|---|
| архив только в `_Archive~/` (с тильдой) | Unity его не видит вовсе |
| ничего архивного не лежит внутри `Resources` | `Resources` в проекте разбросаны по плагинам (`VolumetricFog2`, Feel, NiceVibrations) — заархивировать папку с `Resources` внутри значит молча отправить её в билд |
| вернуть фрагмент = снять тильду | осознанный жест, а не случайность |
| окончательное удаление после `__` вех | карантин; срок назначается при появлении понимания ритма релизов |

*Отклонено:* хранить архив только в истории git или в отдельной ветке. Для дизайнера
«оно где-то в истории» заметно хуже видимой папки на диске; тильда даёт и невидимость
для движка, и доступность для человека.

*Вариант на будущее:* build-валидация по графу зависимостей — тяжелее, и при тильде
ловить почти нечего.

**Защита от «тестовое уехало в билд»** — три уровня:
1. папка `Assets/_Sandbox/` и префиксы `Test_` / `Sandbox_`;
2. источник правды о составе билда — **каталог сегментов**, а не Build Settings руками;
3. проверка при сборке падает, если в билд попала сцена из песочницы.

### 6.1 Модель конфигурации

> Принято по итогам внешней критики: один универсальный `LevelConfig` рискует повторить
> судьбу `GameData.asset` — глобального мешка, в который пишут все и который не сливается
> в мерже (9.14). Но и дробление на шесть типов Definition-ассетов — каркас под линейку
> миров, которых в планах нет. Принята середина: три сущности и два правила.

```
SegmentDefinition   ОДИН АССЕТ НА СЕГМЕНТ, АВТОРСКИЙ: SceneReference,
                    флаг первой встречи, доп. сцены сегмента.
                    Высотная полоса сюда НЕ пишется — она сгенерированная (7.6).
                    Владелец файла = автор сегмента → мерж-конфликтов нет (урок 9.14)

TowerCatalog        агрегатор ссылок на SegmentDefinition + политика стриминга (4.1).
                    Правится редко (добавить/убрать сегмент из билда) — почти
                    не конфликтует. Источник правды о составе билда (раздел 5)

CurrentLevel        РАНТАЙМ-состояние, не ассет: тонкий указатель на активный
                    SegmentDefinition. Отвечает «какой сегмент активен»;
                    всё остальное спрашивают у definition, не у него
```

**Правило 1 — один ассет на сегмент, никогда один общий.** Совместное редактирование
одного конфиг-файла всеми дизайнерами — путь `GameData.asset`, пройденный и закрытый.

**`TowerCatalog`: техническая спецификация** (принято по итогам внешней критики;
поделено по стадиям — игра на этапе прототипа, гейм-дизайн не финален):

*Критично к старту:*

1. **Форма:** ScriptableObject-агрегатор ссылок на `SegmentDefinition`. Один каталог —
   мир один (столб).
2. **Порядок сегментов** определяется **высотными полосами** из `SegmentDefinition`,
   а не порядком элементов списка. Список в инспекторе — представление; сортировку
   проверяет валидатор. Ручной порядок как источник правды — источник тихих багов.
3. **Синхронизация с Build Settings:** редакторная операция «применить каталог»
   перезаписывает `EditorBuildSettings` — резидентные сцены + сцены каталога, всё прочее
   исключается. Build Settings руками не правится; без этого механизма «источник правды —
   каталог» остаётся лозунгом.
4. **Валидатор каталога:**

| Проверка | Уровень |
|---|---|
| пустая или битая ссылка на сцену/definition | ошибка |
| один definition в каталоге дважды | ошибка |
| одна сцена в двух definition | ошибка |
| сцена из `_Sandbox/` в каталоге | ошибка, сборка падает |
| пересечение полос **несмежных** сегментов | ошибка |
| пересечение **смежных** — легально: это полоса перекрытия (схема ②); ошибка только если перекрытие больше заданной полосы | — |
| разрыв покрытия по высоте столба | предупреждение |
| `Light Probe Group` в сцене сегмента | предупреждение: проект на APV (9.15), классические пробы не используются |
| верхняя граница полосы выше 10 000 единиц | предупреждение: мир вышел за порог точности float, требуется решение по origin (7.4) |
| актор, чей диапазон движения выходит за сегмент-владелец плюс полосу перекрытия | предупреждение: подвижное между этажами — объект резидентного слоя (7.2.1) |
| missing scripts или битые ссылки в сцене сегмента | ошибка — классический след неудачного мержа, «конфликтов не было» ещё не значит целую сцену (9.14) |
| дубликат ключа памяти **по всему каталогу**, а не только среди загруженных сцен | ошибка: два объекта с одним ключом (7.2) — типовая причина, повторяющиеся локации-префабы |
| живой корень сегмента сохранён **включённым** | ошибка: сирены и FX стартуют до активации сегмента, инвариант пассивности рушится (8.1, п. 1а) |
| межсегментная ссылка указывает на несуществующий сегмент или отсутствующий в нём маркер | ошибка: в билде превратится в тихий `null` (7.7) |

Оговорка к пятой-шестой строке: совет критика «запрещать дубли диапазонов» в лоб
запретил бы нашу же полосу перекрытия — проверка адаптирована под схему стриминга.

*Может измениться в дальнейшей разработке (не проектируем сейчас):*

| Пункт критика | Почему отложен/отклонён |
|---|---|
| DLC / варианты, platform-specific исключения | в планах нет; появятся планы — каталог расширяем, не переделываем |
| синхронизация с Addressables | проект на Resources; Addressables — отдельная отложенная тема, связывать два нерешённых вопроса рано |
| граф зависимостей сегментов | концепта нет: желаемый набор вычисляет политика по полосам и чекпоинтам |
| optional-сегменты | боковое ответвление — обычный сегмент в каталоге; «опциональность» — следствие пути игрока, не свойство каталога |

**Правило 2 — конфиг не хранит того, что уже решается другим механизмом:**

| Идентичность (из критики) | Почему не в конфиге |
|---|---|
| `WorldId` / `GameSessionId` | мир один — столб; мультисессионности нет |
| `SaveNamespace` | память ключуется глобально по стабильному ID (7.2) — нечем занять |
| `TutorialPresentationPolicy` | шов «первая встреча» (раздел 10) — флаг в `SegmentDefinition`, не тип ассета |
| `SaveSchemaDefinition` | версия схемы — поле в `PlayerProgress` (7.2) |
| `GameplayModeDefinition` | билд/песочница различаются вызывающей стороной, не конфигом (тот же принцип, что в контракте сегмента для точек входа) |
| `StreamingProfile` | политика — поле `TowerCatalog`, не отдельный ассет |

## 7. Контракт сегмента

Отвечает на вопрос «что должно быть в сцене, чтобы паук в ней полноценно отрабатывал».

| Элемент | Обязателен | Назначение |
|---|---|---|
| `LevelEntry` | да | **точка входа**: где паук появляется, когда сессия начинается с этого сегмента. Обязателен, потому что любой сегмент обязан быть стартуемым — песочница, отладка, старт уровня |
| `SegmentBounds` | для билда | **авторинг** высотной полосы: дизайнер задаёт её в сцене. Директор читает не этот компонент, а запечённую копию — см. 7.6 |
| `Checkpoint` | нет | респавн; в билде ещё и гейт выгрузки нижних сегментов |
| маркеры пикапов | нет | цветок, батарейки, энергия, генераторы, скиллы |
| эвенты | нет | двери, платформы, триггеры, зоны камеры |

**Владение пауком** (принято по итогам внешней критики — формулировки «паук в резидентном
Gameplay» и «LevelEntry — точка спавна в каждом сегменте» противоречили друг другу):

- Паук **создаётся один раз за игровую сессию** фабрикой резидентного слоя
  (`GameFactory.CreateSpider`) и при смене сегментов **не пересоздаётся** — иначе
  резидентный `Gameplay` теряет смысл.
- `LevelEntry` не спавнит паука: при старте сессии с сегмента N паук **позиционируется**
  по его точке входа. Позиционирование ≠ спавн.
- Респавн — по чекпоинтам, это существующая система (`CheckPoint`, `RestartService`).

Точек, связанных с пауком, ровно две: **точка входа** и **чекпоинт**. Отдельные типы
`GameStartPoint`/`SandboxSpawnPoint` отклонены — «старт игры» и «старт в песочнице»
различаются вызывающей стороной, а не типом маркера. `SegmentPreviewEntry` — сценария
нет в игре. `RecoveryPoint` (подхват при падении) — не заводится, пока не спроектирована
сама механика подхватов (см. раздел 12).

**Контракт почти весь уже существует в виде маркеров** (1.6): `LevelEntry` — это
`SpiderSpawnPointMarker`, дальше `FlowerPointMarker`, `CheckPointMarker` и остальные.
Новыми будут только `SegmentBounds` (высотная полоса) и группировка эвентов.

### 7.1 Предложение: маркеры — источник правды в рантайме, запекание убрать

> **Статус: отложено решением владельца.** Пайплайн остаётся как есть, вопрос выносится
> в отдельную будущую задачу — владелец хочет очно сравнить текущий рабочий процесс
> с предлагаемым. Раздел сохранён как основа для этого сравнения.
>
> **Уточнение по итогам внешней критики:** из этого отложенного вопроса вынута
> ID-часть — она уехала в критический путь как **7.2** и чинится при живом запекании,
> не дожидаясь выбора пайплайна. Отложенным остаётся только сам выбор:
> запекание vs runtime-чтение маркеров.

**Сравнение в терминах рабочего процесса дизайнера:**

| Шаг дизайнера | Сейчас | Если убрать запекание |
|---|---|---|
| Подвинуть, добавить, удалить маркер | двигаю в сцене | двигаю в сцене — без изменений |
| Чтобы изменение заработало | выделить `GameData.asset` → нажать «Collect» | ничего не нажимать, просто Play |
| Забыл нажать | объект спавнится на старом месте, выглядит как баг спавна | невозможно по построению |
| Новая тестовая сцена | сперва нажать Collect, иначе игра падает | работает сразу |
| Посмотреть, что расставлено | Odin-словарь внутри ассета | сцена и иерархия |
| Прогресс после Collect | пройденные чекпоинты и генераторы сбрасываются | не сбрасывается |
| Работа вдвоём над разными уровнями | общий ассет — источник конфликтов в гите | каждый в своей сцене |

Ниже — техническое обоснование того же предложения.

Сегодня расстановка живёт в двух местах: маркеры в сцене (авторинг) и запечённые координаты
в `GameDatas` (рантайм). Синхронизирует их ручное нажатие «Collect». Отсюда все проблемы 1.6,
включая коварный симптом: **подвинул маркер, забыл нажать Collect — объект спавнится
на старом месте**, и это выглядит как баг спавна.

Предложение: `GameFactory` читает маркеры прямо из загруженной сцены сегмента,
`GameDatas` и «Collect» уходят.

Почему это дёшево и правильно:

| Довод | Деталь |
|---|---|
| Данные уже в сцене | маркеры — обычные `MonoBehaviour`, грузятся вместе со сценой; их просто не читают в рантайме |
| Один потребитель | `GameDatas` читает только `GameFactory`, 8 мест — замена локализована в одном классе |
| Убирает три проблемы разом | «забыл Collect», нестабильные GUID, ключевание по активной сцене |
| `UniqueId` стабилизируется сам | лежит на маркере, сериализуется в сцене, живёт в гите, переживает переименования |

Гибрид при этом сохраняется, но граница проходит там, где надо:
**`LevelConfig` отвечает за уровень** (какие сцены грузить, флаги, политика стриминга),
**сцена — за расстановку объектов**.

Цена: переписать 8 мест чтения в `GameFactory` + разовая миграция — проставить маркерам
стабильные id, сгенерировав их из текущих запечённых значений, чтобы существующие сейвы не слетели.

**Промежуточный вариант**, если полный переход не ко времени: оставить запекание, но читать
`UniqueId` с маркера вместо `Guid.NewGuid()` и повесить авто-Collect на вход в Play Mode.
«Забыл нажать» исчезает, id стабилизируются, архитектура не трогается. Дешевле, но
ключевание по активной сцене остаётся — а его придётся чинить при миграции в любом случае.

Рекомендация: раз миграция всё равно предстоит — идти сразу в «маркеры = источник правды».

Проверка контракта — редакторной валидацией: открыл сцену, увидел в консоли, чего не хватает.
Отсутствие маркера спавна должно давать внятное сообщение, а не `NullReferenceException`
в инструменте и `KeyNotFoundException` в рантайме, как сейчас.

### 7.2 Система стабильных ID — нулевая фаза миграции

> Принято по итогам внешней критики, вскрывшей внутреннее противоречие документа:
> вердикт 9.13-D объявил память мира включённой по умолчанию, ключ памяти — стабильный ID,
> а стабилизация ID при этом лежала в отложенных задачах. Дом стоял на фундаменте
> из таблицы «сделаем потом». Исправлено: **система стабильных ID — нулевая фаза
> критического пути миграции.** Она чинится при живом запекании — решение владельца
> по 7.1 (сравнить пайплайны, прежде чем выбирать) не переигрывается.

Без этих правил сейвы ломаются не только от «Collect», но и от обычной работы дизайнера:
дублирование объекта в Unity (Ctrl+D) копирует сериализованный ID — два объекта
с одним ключом памяти.

**Идентичность двухуровневая** (уточнено второй внешней критикой). Причина жёсткая:
сериализованное поле внутри prefab asset **одинаково у всех его инстансов**. Шесть техшахт
из одного префаба дадут шесть дверей с одним ID — и это не риск, а гарантия. Правило
«копия получает новый ID» здесь не помогает: у префаба нет события дублирования, которое
можно перехватить, ID наследуется по построению.

| Уровень | Где живёт | Смысл |
|---|---|---|
| **ID размещения** | на корне размещённого в сцене экземпляра локации или актора | «какая именно шахта» — уникален в каталоге |
| **Локальный ID актора** | внутри prefab asset | «дверь вот в этом шаблоне» — **общий по замыслу**, одинаковый у всех инстансов |
| **Ключ памяти** | пара из двух | уникальна |

Схема вырождается корректно: у **уникального сценового актора** (не из переиспользуемого
префаба) ID размещения и есть его собственный ID, второй уровень не нужен.

Имена уровней здесь описательные — регламент именования отдельной задачей.

**Шесть правил:**

1. **ID живёт на маркере/акторе** и сериализуется. `Collect` его **читает** —
   никогда не генерирует (сегодня — `Guid.NewGuid()` при каждом нажатии).
2. **Пустой ID и дубликат ID** — ошибка редакторной валидации, а не тихое поведение.
   Проверка уникальности идёт **по всему каталогу**, а не только среди загруженных сцен.
3. **Копия объекта получает новый ID размещения** — дубликат обнаруживается
   и перегенерируется у копии, не у оригинала.
4. **`OnValidate` никогда не регенерирует существующий непустой ID.**
5. **Память ключуется глобально по ключу памяти** (паре из двух уровней), а не
   «сегмент + ID» — перенос объекта между сегментами не трогает его сохранённое состояние.
6. **Осиротевшие записи игнорируются при загрузке и НИКОГДА не удаляются автоматически.**

   Исправлено по итогам второй внешней критики. Прежняя редакция — «вычищаются при
   следующем сохранении» — в стримящемся мире означала бы катастрофу: загружены
   3–5 этажей, игрок сохраняется на седьмом, и очистка стирает состояние всех дверей
   и генераторов ниже. **Не зарегистрирован сейчас ≠ удалён из игры.**

   Осиротевшая запись — это ID и маленькое состояние; сотня таких записей не стоит
   ничего. Очистка решала несуществующую проблему.

   Чистка возможна только как **осознанная ручная операция по манифесту каталога** —
   инструмент диагностики orphaned-записей уже отложен (раздел 12). Автоматики нет.

   *Вариант решения, если* понадобится удалять контент в патчах — tombstone-записи
   миграции поверх уже существующей версии схемы. Для прототипа преждевременно.

**Миграция:** первичные ID проставляются маркерам **из текущих запечённых значений
`GameDatas`** — существующие сейвы не слетают.

**Версия схемы сохранения:** поле версии в `PlayerProgress` — заводится в эту же фазу,
дальнейшие изменения формата памяти идут через него.

### 7.2.1 Владение объектами на границе сегментов

> Принято по итогам внешней критики: правило «резать границу по закрытым точкам» (9.10) —
> это level-design принцип, он не отвечает на рантайм-вопрос «кому принадлежит объект,
> оказавшийся между сегментами».

**Почему это критично именно здесь.** В проекте есть перенос объектов на платформе
(`PlatformObjectsService`, `Add(_flower)`, `HasAny<BatteryProduct>()`) — паук носит
**цветок и батарейки**. Сценарий: цветок появился по маркеру в `Seg_05`, игрок донёс его
до `Seg_06`, `Seg_05` выгружается — `UnloadSceneAsync` уничтожает всё в своей сцене,
включая цветок. Это потеря цели уровня, а не деградация. Проявится в день включения
стриминга — тот же класс дефекта, что память акторов (9.13-D) и мёртвые ссылки
в реестрах (9.17).

**Правило:**

> **Каждый рантайм-объект принадлежит ровно одному сегменту либо резидентному слою.**
>
> **Объект, способный покинуть свой сегмент** — переносимый, брошенный, сбитый вниз —
> **создаётся сразу в резидентном слое**, а не в сцене сегмента. Маркер в сегменте задаёт
> только точку появления. Тогда выгрузка сегмента физически не может его уничтожить.
>
> **Актор остаётся в своём сегменте**, и его диапазон движения не должен покидать
> сегмент-владелец плюс полосу перекрытия. Платформа, курсирующая между этажами, —
> не актор сегмента, а объект резидентного слоя.

Это ложится на уже принятое разделение: **маркер в сегменте — где появляется,
сам объект — где живёт.** Тот же приём, что с пауком (раздел 7, «Владение пауком»),
распространённый на переносимое.

Сегодня вопроса не существует — мир один и не выгружается. Парентинг спавна в сценах
не подтверждён; достоверно известно лишь `_parentNewObjectsUnderContext: 1`
у `ProjectContext`. Поэтому правило записывается явно, а не оставляется на то,
как сложится само.

Уже закрыто в других разделах и отдельных правил не требует: паук ногами в двух сценах
(резидентен — раздел 7), камера (резидентный слой), звук и частицы на границе (свой
сегмент + fade-out в `DeactivateAsync`, 9.8), канат/кабель/длинная дверь/лифт через
границу (правило реза по закрытым точкам, 9.10). AI в проекте нет.

### 7.2.2 Слой динамических объектов — где живёт то, что ушло из сегмента

> По итогам внешней критики. Правило 7.2.1 закрывало только объекты, **известные
> подвижными заранее** (груз, пикапы). Остаётся второй класс: объекты, которые
> **становятся** подвижными — отсоединённая деталь, обломок, сбитое вниз. Они рождаются
> контентом сегмента и перестают им быть.

**Проблема критична и датирована — она наступает на миграции, а не при включении
стриминга.** Сегодня рестарт работает перезагрузкой сцены (`RestartService.IsRestarting`,
`BuildLevelState.Restart()`). Как только `Gameplay` становится резидентным, «перезагрузить
сцену» перестаёт очищать мир — а переносимые объекты по правилу 7.2.1 живут именно
в резидентном слое. Значит донесённый цветок **переживёт рестарт**. Нужна явная операция
«очистить мир, оставить системы».

**Правила владения** (одинаковы для обоих вариантов ниже):

1. Известное подвижным заранее (груз, пикапы) — создаётся сразу в динамическом слое.
2. Становящееся подвижным в рантайме — передаётся в динамический слой в момент, когда
   перестаёт быть частью авторской композиции сегмента: подобрано, отсоединено, получило
   свободу движения.
3. **Обратного переноса нет** — ушедшее в динамический слой там и остаётся, иначе владение
   начнёт скакать.
4. **Очистка мира = очистка динамического слоя.** Рестарт и смена уровня чистят его,
   не трогая системы в `Gameplay`.

**Форма решения — выбирается на миграции, когда станет ясно, как перестроен рестарт.
Оба варианта дают одинаковую семантику:**

| Вариант | Как устроено | За | Против |
|---|---|---|---|
| **A. Отдельная сцена** `DynamicWorld` | пустая аддитивная сцена без контекста; передача через `SceneManager.MoveGameObjectToScene` | штатный механизм Unity; не добавляет уровень трансформа физическому грузу; очистка — одна операция над сценой | ещё одна сцена в работе и в каталоге |
| **B. Корневой объект** `DynamicRoot` внутри `Gameplay` | передача — репарент; очистка — уничтожение детей | ни одной новой сцены; проще в работе | лишний уровень трансформа под физическим грузом |

*Заполняется при тюнинге:* лимит и время жизни обломков. В игре, где предмет можно сбить
с сотен метров, динамический слой иначе копит мусор бесконечно. Число назначать пока не на чем.

**Времена жизни — что определено и что нет** (по итогам второй внешней критики: «мир помнит
всё» и «рестарт очищает динамический слой» формально сталкиваются).

| Событие | Что происходит с состоянием мира | Статус |
|---|---|---|
| падение, респавн на чекпоинт | **мир помнит всё** — рычаги, генераторы, двери, открытые проходы | **решено** владельцем (9.13-D) |
| новая игра | всё сбрасывается | тривиально |
| загрузка сейва | восстанавливается сохранённое | тривиально |
| **рестарт попытки** | **не определено** | **открыто — гейм-дизайн** |

Сегодня конфликта нет: `RestartService` — это просто флаг `IsRestarting`, рестарт
перезагружает сцену целиком, а прогресс приходит из сейва. Миру нечего помнить между
рестартами, он строится заново.

**Столкновение наступит ровно тогда, когда `Gameplay` станет резидентным** — то есть
в ту же дату, что и выбор формы динамического слоя. Решать вопрос «что переживает рестарт
попытки» нужно к этому моменту, и это решение гейм-дизайна, а не архитектуры.

Схемы ① и ② сводки намеренно **не меняются** до выбора варианта — чтобы не фиксировать
форму раньше, чем она понадобится.

### 7.3 Физический контракт сегмента

> Принято по итогам внешней критики: в игре про лазание **коллизия и есть геймплей**,
> а физического контракта в документе не было вовсе. Самый серьёзный из найденных пробелов.

**Почему это не абстракция.** `LegRaycast.GroundNormal` возвращает `_hit.normal` —
ноги паука ставятся **прямо на нормаль рейкаст-хита**. Значит масштаб, тип коллайдера
и сглаживание нормалей меняют постановку ног молча, без единой ошибки в консоли.

*Остро критично к старту — правила авторинга, бесплатны и предотвращают реальные баги:*

1. **Ноль non-uniform scale на объектах с коллайдерами.** Ломает `MeshCollider`
   и нормали, а на нормалях стоит вся постановка ног.
2. **Минимальная толщина коллайдера** — от максимальной скорости падения и шага физики.
   При `Fixed Timestep 0.02` быстро падающий объект проходит за шаг заметное расстояние;
   тонкий пол прошивается насквозь. Для вертикальной игры это правило первой очереди.
3. **Никаких микрозазоров на стыках** — ноги цепляются, IK дрожит. На стыках модулей
   перекрытие, а не подгонка впритык.
4. **`MeshCollider`: non-convex только для статики**, convex — только там, где нужен
   `Rigidbody`. Выпуклая оболочка меняет геометрию и ощущение поверхности.
5. **Нормали — часть контракта кит-модуля.** Сглаживание и зеркалирование нормалей
   меняют геймплей, а не только вид.
6. **Один шов в коде на вопрос «проходима ли поверхность».** Сегодня отвечает по слою
   (`NotMoveable`); слой остаётся частью контракта кит-модуля (9.13-B) и инструментом
   физической фильтрации — маска рейкаста ног работает именно так.

*Заполняется при тюнинге — базис физики:*

| Параметр | Значение |
|---|---|
| `Fixed Timestep` | 0.02 (текущее) |
| `Maximum Allowed Timestep` | 0.333 (текущее) |
| solver iterations | 6 (текущее) |
| max angular speed | 50 (текущее) |
| максимальная скорость падения | __ |
| требуется ли CCD и на чём | __ |
| минимальная толщина коллайдера | __ |

*Вариант решения, если* появится **второе** свойство поверхности (сцепление, влияние
на устойчивость груза) — компонент `TraversalSurface` с флагами и параметрами; слой
остаётся грубым фильтром физики, семантику начинает отдавать компонент. Триггер именно
такой: пока свойство одно («проходимо / нет»), компонент с одним полем — церемония.
Шов из правила 6 делает эту замену правкой одного файла, а не всего контента.

Признак того, что подход «слой на каждое свойство» плохо масштабируется, в проекте уже
есть: слой `TerrainNotMoveable` заведён и **не используется в коде ни разу** (см. раздел 12).

### 7.4 Высота мира и точность координат

> По итогам внешней критики: предельная высота мира нигде не была задана. Потолок сейчас
> назначить нельзя — он зависит от того, какой из планируемых режимов выберут тестировщики.
> Поэтому вместо цифры зафиксирована **растяжка**: порог, на котором вопрос становится
> настоящим, и автоматическое предупреждение при его пересечении.

**Где мы сейчас.** Максимальная координата по модулю в `GameData.asset` — **198 единиц**.
Весь текущий мир укладывается в 200 метров.

**Когда точность float становится вопросом:**

| Высота | Погрешность | Оценка |
|---|---|---|
| 200 (сейчас) | 0,012 мм | вопроса нет |
| 1 000 | 0,06 мм | вопроса нет |
| **10 000** | ~1 мм | **порог: дальше нужно мерить** |
| 100 000 | ~8 мм | jitter физики и IK, дрожание камеры |

Паук делает IK на сантиметровом масштабе, поэтому до 10 000 единиц погрешность
субмиллиметровая и не видна ни в ногах, ни в контактах, ни в балансировке груза.

*Остро критично к старту — ничего не строим, ставим растяжку:*

- **До 10 000 единиц вопроса не существует.** Все координаты абсолютные, floating origin
  не нужен, специальных мер не требуется.
- **Валидатор каталога (6.1): верхняя граница полосы сегмента выше 10 000 → предупреждение**
  «мир вышел за порог точности, требуется решение». Это не ошибка и ничего не блокирует —
  растяжка срабатывает сама, когда дизайн дорастёт, и не требует назначать потолок заранее.

*Возможно пригодится в будущем.* Если выбранный режим потребует мир выше порога, floating
origin становится отдельным проектом. Записываю цену заранее, чтобы решение принималось
со знанием — он ломает четыре механизма разом:

| Что ломается | Почему |
|---|---|
| запечённые мировые координаты | `GameDatas` хранит абсолютные `WorldPosition` — весь пайплайн маркеров (1.6, 7.1) |
| APV | cell data печётся в мировом пространстве; сдвиг origin ломает семплирование проб (9.15) |
| world-space эффекты | `_TerrainScan` — линии скана, следы; в проекте уже есть `TerrainScanOriginPositioner` |
| частицы в world simulation space | привязаны к мировым координатам |

*Отметено:* строить floating origin сейчас и назначать произвольный потолок. Выдуманное
число в такой ситуации хуже его отсутствия — его процитируют как закон, а потом нарушат.

### 7.5 Запечённые данные: сгенерированное отдельно от авторского

> По итогам внешней критики. Ранее в документе стоял организационный паллиатив —
> «Collect нажимает один назначенный человек». Он не защищает ни от забывчивости,
> ни от нажатия в неверной активной сцене, ни от слияния маркеров нескольких загруженных
> сцен, ни от конфликта общего ассета. Заменён техническими правилами.
>
> Часть рисков из критики уже закрыта разделом **7.2**: регенерация ID и пустые
> либо дублирующие ID стали ошибкой валидации ещё там.

**Корень проблемы — смешение.** `GameStaticData` держит в одном ассете авторские данные
(`LoadScene`, `AdditiveScenes`, `TutorialSceneName`) и сгенерированные (`GameDatas`,
запечённые из маркеров). Отсюда и неразрешимый мерж, и небезопасная перегенерация.

*Остро критично к старту — и ничего не предрешает в отложенном вопросе 7.1:*

1. **Сгенерированное отделяется от авторского и пишется по сегментам**, а не в общий
   ассет. Это распространение уже принятого правила 6.1 («один ассет на сегмент»)
   на запечённые данные. Каждый Collect трогает только свой файл — **мержить нечего,
   причина конфликта исчезает при сохранении запекания**.
2. **Сгенерированные данные не редактируются руками.** Правка идёт в маркеры сцены,
   затем перезапекание.
3. **Collect работает по явно выбранной сцене сегмента** и сканирует только её корни.
   Сегодня он берёт ключ из `GetActiveScene().name`, а `FindObjectsOfType` собирает
   маркеры **всех загруженных сцен** — в аддитивной схеме это молча слило бы несколько
   этажей в один ключ.
4. **Проверка актуальности:** запечённые данные разошлись с маркерами сцены → ошибка
   валидации, сборка падает. Это ответ на забывчивость, и он дешевле любого регламента.

*Вариант решения, если* запекание останется по итогам 7.1 — полная автоматизация
шагом сборки: `Validate → Bake → Compare → Build`. Сейчас строить нельзя: если победит
чтение маркеров в рантайме, шаг запекания исчезнет целиком и автоматизация окажется
выброшенной.

### 7.6 Высотная полоса: один источник правды

> По итогам второй внешней критики. Полоса была объявлена дважды — полем
> в `SegmentDefinition` (6.1) и компонентом `SegmentBounds` в сцене (раздел 7), оба
> описаны как редактируемые. Дизайнер поправил бы одно, забыл второе, и ошибка
> проявилась бы только на стриминге.

**Жёсткое ограничение, из которого всё следует:** директор решает, какую сцену грузить,
когда она **ещё не загружена**. Прочитать компонент из невыгруженной сцены он физически
не может. Значит данные для решения о загрузке обязаны жить вне сцены.

**Принятая модель — одна:**

| Где | Что это | Кто правит |
|---|---|---|
| `SegmentBounds` в сцене | **авторинг**: дизайнер задаёт полосу в вьюпорте, как маркеры | левел-дизайнер — **единственное редактируемое место** |
| запечённые данные сегмента (7.5) | производная копия полосы | никто руками; пишется запеканием |
| `SegmentDefinition` | полосу **не хранит** — он авторский, а полоса сгенерированная | — |
| директор и каталог | читают **только запечённое** | — |

Расхождение между сценой и запечённым ловит **уже принятая проверка актуальности**
(7.5, правило 4): запечённое разошлось с маркерами → ошибка валидации, сборка падает.
Новых механизмов не требуется — это тот же класс бага, под который проверка и заводилась.

### 7.7 Межсегментные ссылки

> По итогам второй внешней критики. Первая партия закрепила, что маркер телепорта заранее
> требует `Ready` для сегмента назначения (9.17), но не сказала, **чем источник называет
> цель**. Дизайнер сделает естественное — перетащит объект назначения в поле — и получит
> тихий `null` в сборке: **Unity не поддерживает сериализованные межсценовые ссылки.**

**Закон: контентные сцены не имеют сериализованных ссылок друг на друга.**

Ссылка на объект в другом сегменте задаётся парой:

```
SegmentDefinition (какой сегмент)  +  ID маркера назначения (что именно в нём)
```

Оба понятия уже приняты — `SegmentDefinition` в 6.1, идентичность маркеров в 7.2.
Новых сущностей не вводится.

**Разрешение — на директоре.** После перехода сегмента назначения в `Ready` директор
разрешает ID в рантайм-объект и отдаёт его источнику. До этого источник не срабатывает:
телепорт не переносит, пока назначение не готово.

**Неразрешимая ссылка — громкая ошибка, а не тихий `null`.** Нет такого сегмента, нет
такого маркера, сегмент не поднялся — это диагностируемый отказ, та же философия,
что у `Failed` в 9.17.

Закон общий, не про телепорты: так же адресуются катапульты, лифты, двери, открываемые
с другого этажа, камеры, нацеленные на объект вне своего сегмента, и цепочки эвентов.

**Побочная выгода — тестируемость.** Сегмент с жёсткой ссылкой на соседа нельзя прогнать
в песочнице отдельно (5.1). Закон сохраняет независимость сегмента, ради которой вся схема
и затевалась.

## 8. Модель DI для аддитивных сцен

Контентная сцена содержит эвенты (дверь, следящая камера), которым нужны сервисы из `Gameplay`.

**По умолчанию — сегменты без собственного `SceneContext`.** `StreamingDirector` живёт
в `Gameplay` и после загрузки сегмента прогоняет инъекцию по корневым объектам загруженной
сцены. Сегмент остаётся чистым контентом — ни одного объекта инфраструктуры, его свободно
ведёт левел-дизайнер.

**Запасной вариант** — сегменту действительно нужны свои биндинги. Тогда штатный механизм
Zenject: у `Gameplay` проставляется `ContractNames`, у сегмента — `ParentContractNames`,
загрузка через `ZenjectSceneLoader`. Либо `SceneDecoratorContext`.

Честный компромисс: первый вариант легче и чище для дизайнера, но он не «по учебнику Zenject».
Второй каноничен, но возвращает объект инфраструктуры в каждую контентную сцену — то есть
в мягкой форме воспроизводит нынешнюю проблему. Принято: первый по умолчанию, второй точечно.

### 8.1 Контракт жизненного цикла актора

> Принято по итогам внешней критики: фраза «директор прогоняет инъекцию по корням»
> недостаточна для production. В Unity `Awake`/`OnEnable` объектов сцены срабатывают
> в момент её активации — **до** того, как внешний директор успеет выполнить инъекцию.
> Это окно гонки закрывается не хитростью загрузки, а контрактом на стороне актора.

1. **Принятая модель — пассивные акторы** (она же инвариант 9.17): актор не ведёт логику,
   пока директор не активировал сегмент. Порядок «сцена активировалась → инъекция →
   регистрация → команда активации» перестаёт быть гонкой, потому что до команды актор
   ничего не делает.

   **1а. Два корня в сцене сегмента — техническая опора этого инварианта.**
   Исправлено по итогам второй внешней критики: пассивность акторов действует только
   на наш C#-код. `AudioSource.playOnAwake`, `ParticleSystem`, `Animator`, `Rigidbody`,
   триггер-коллайдеры и любой чужой компонент стартуют **до** команды директора —
   сегмент грузится, и сирены уже воют. Инвариант был декларативным.

   | Корень | Что внутри | Когда активен |
   |---|---|---|
   | **Статический** | геометрия, коллайдеры, свет сегмента | с `Ready` |
   | **Живой** | акторы, FX, звук, аниматоры, триггеры | с `Active`; **в сохранённой сцене выключен** |

   Выключенная иерархия закрывает весь список одним движением: `Awake` не вызывается,
   `playOnAwake` не срабатывает, `Animator` не считает, `Rigidbody` не симулирует,
   триггеры молчат. И стоимость покоя — **настоящий ноль**, а не проверка флага в `Update`
   (уточнение к 9.3: «ровно ноль» верно именно потому, что иерархия выключена).

   Статический корень отдельно нужен по **коридору падения**: паук, влетающий в полосу
   перекрытия, не должен провалиться сквозь сегмент, который загружен, но ещё не активирован.

   Шесть управляемых категорий из критики (коллизия, триггеры, скрипты, анимация, звук,
   физика) избыточны — двух корней достаточно.

2. **`Awake`/`OnEnable` — только самонастройка:** ссылки на собственные компоненты,
   кэширование, ноль обращений к зависимостям, ноль игровой логики, ноль подписок
   на внешние сервисы. **`Start` для игровой логики запрещён.** Точка входа актора —
   вызов активации от директора; точка выхода — деактивация (там же снимаются подписки).

3. **Объём инъекции:** обход всех корневых объектов загруженной сцены со всей иерархией,
   **включая неактивные объекты** и вложенные prefab instances (`Container.InjectGameObject`
   обходит дочерние).

4. **Объекты, созданные в рантайме,** инъекцию директора не получают — они создаются
   **только через фабрики** (существующий паттерн: `GameFactory`,
   `InstantiatePrefabResourceForComponent` — инъекция в момент создания).

5. **Повторная загрузка сегмента:** актор не хранит состояние в статике и не рассчитывает
   пережить выгрузку в полях. Всё, что должно пережить unload→reload, идёт через механизм
   памяти (9.13-D: `MarkerUniqueId` + `ISavedProgress`).

6. **Отклонено: `allowSceneActivation = false`.** Пока сцена не активирована, её корни
   недоступны (`GetRootGameObjects` пуст) — инъецировать нечего, а в момент активации
   `Awake` стреляет сразу; окно не закрывается. Второй, независимый довод — операция
   застревает на 0.9 и блокирует очередь, включая `UnloadSceneAsync` (9.17).

   *Поправка к прежней редакции:* раньше здесь же отклонялось и соглашение «держать корни
   выключенными в сцене» — с обоснованием «при пассивных акторах не нужно». Оно **нужно**
   (см. 1а): пассивность не распространяется на движковые компоненты. Хрупкость снимается
   валидатором, а не отказом от приёма. Это разные вещи: `allowSceneActivation` —
   активация **сцены** движком, выключенный корень — обычный `SetActive` внутри
   загруженной сцены.

7. **Валидация контракта:** прогон сегмента в `KeepActiveOnly` (9.16) — поведенческая
   проверка; **валидатор: живой корень в сохранённой сцене сегмента должен быть выключен**
   (6.1); редакторный линт «актор с логикой/зависимостями в `Awake`/`Start`» —
   в отложенных задачах (раздел 12).

### 9.2 Принцип: пять слоёв, поведение ровно на одном

```
5  Seg_05_Lab.unity           СЦЕНА-СЕГМЕНТ  расстановка чанков, маркеры, свет полосы
   └ 4  CH_Laboratory_001     ЧАНК           только композиция + эмбиент фрагмента
        ├ 3  ACT_Siren        АКТОР          меш + мигание + звук + скрипт
        ├ 3  ACT_SteamPipe    АКТОР          меш + пар FX + звук
        ├ 3  ACT_Door_Sliding АКТОР          меш + анимация + звук + триггер
        ├ 2  LAB_PropFridge_A ПРОП           меш + коллайдер, без логики
        └ 1  ENV_LabWall      КИТ-МОДУЛЬ     меш + коллайдер + материал, без логики
```

Правило, из которого следует всё: **поведение живёт только на слое 3 (актор).**
Чанк ничего не делает — он только компонует. Кит и проп — чистая геометрия.

Слоя акторов сейчас нет — это то, что нужно завести. Держать вложенность ≤5–7 уровней.

**Что считается актором** (по итогам внешней критики: правило «поведение только на акторе»
не определяло, что такое поведение — дизайнер не мог решить, актор ли его мигающая лампа):

> **Актор — объект, которому нужны зависимости из `Gameplay` ИЛИ у которого есть память.**
> Всё остальное — кит, проп, декор. Даже если оно движется, светится и звучит.

Формулировка для дизайнера, без программистских терминов: **актор — это то, что игра
должна восстановить после перезагрузки этажа, или то, что спрашивает что-то у игры.**
Мигающая лампа не спрашивает, и восстанавливать в ней нечего — значит декор.

Разбор спорных случаев:

| Объект | Зависимости | Память | Кто это |
|---|---|---|---|
| эмбиент-`AudioSource` | нет | нет | декор |
| лампа с flicker-скриптом, `Animator` без геймплея | нет | нет | **живой декор**, не актор |
| `LODGroup`, `ReflectionProbe` | нет | нет | движковый компонент |
| подвижная платформа | да | **да** (позиция) | **актор** |
| дверь, рычаг | да | **да** | **актор** |
| триггер-зона, зона следящей камеры | **да** (нужен паук/сервис) | нет | **актор** |
| damage surface | **да** | нет | **актор** |
| destructible prop | **да** | **да** | **актор** |
| physics material | — | — | ассет, не объект сцены |
| `OcclusionPortal` | — | — | неактуален: baked occlusion отключён (9.15) |

Третья ось из критики — «стоимость в покое» — не признак класса, а требование ко всем:
бинарные правила и бюджеты в 9.3.

*Отклонена* компонентная таксономия из девяти типов (`StaticModule`, `DecorativeProp`,
`InteractiveActor`, `HazardActor`, `TraversalActor`, `EnvironmentalEmitter`, `TriggerVolume`,
`SegmentService`, `AuthoringMarker`): две оси ортогональны и дают ответ механически,
а девять корзин пришлось бы поддерживать вручную — каждый новый объект становился бы
спором, куда его класть. При появлении реальной потребности типы всегда можно ввести
поверх осей.

### 9.3 Правила по типам содержимого

**Меш и коллайдеры** — слои 1–2. Ноль скриптов, ноль звука.

**Поведение** — слой 3, один актор = одна ответственность. Актор обязан быть самодостаточным:
не искать паука через `FindObjectOfType` (ломается в аддитивной схеме), а получать зависимости
инъекцией от директора (раздел 8).

**Стоимость в покое — правила вместо пожелания** (по итогам внешней критики: формулировка
«актор должен стоить около нуля» непроверяема — каждый скажет, что его скрипт почти
ничего не стоит).

*Остро критично к старту — бинарные правила, чисел не требуют:*

1. **Ноль `Find*` в рантайме** — расширение запрета из 8.1 (`FindObjectOfType`); линтуется.
2. **Ноль аллокаций в установившемся режиме** — видно в профайлере.
3. **Актор молчит вне `Active`** — из 8.1. Это главная гарантия: неактивный сегмент
   стоит не «около нуля», а **ровно ноль** — `Update` не вызывается. Вопрос сужается
   до одного активного сегмента.
4. **Нет собственного `Update`, если работу можно сделать по событию.**

*Заполняется при первом профилировании* — числа не выдумываем. **Предусловие: объявить
цель по кадру**, в проекте она не задана (`targetFrameRate` и `vSyncCount` не встречаются
в коде). Бюджеты на **активный** сегмент:

| Бюджет | Порог |
|---|---|
| активных `Update` | __ |
| `Animator` | __ |
| активных `ParticleSystem` | __ |
| `AudioSource` | __ |
| realtime-источников света | __ |
| physics queries за кадр | __ |

*Вариант решения, если* число `Update` станет проблемой — централизованный tick scheduler
с регистрацией акторов. Это архитектурное решение, а не бюджет; заранее не вводим.

**Звук.** Точечный (сирена, пар) — `AudioSource` на самом акторе, 3D.
Эмбиент фрагмента — на корне локации; форма зоны выбирается по акустике места (9.8).

> **Важно для вертикальной игры:** падающий паук проносится сквозь фрагмент за доли
> секунды; на такой скорости триггеры пропускаются, а `OnTriggerExit` может не сработать —
> звук залипнет. Лечится **не** формой зоны, а тем, что **аудиозона — вычисляемое
> состояние, а не накопленное**: пересчитывается каждый тик, пропущенный триггер
> самоисправляется на следующем. Подробности — 9.8.

**FX.** Пар и подобное — `ParticleSystem`/VFX Graph на акторе. Culling Mode задавать явно,
не оставлять по умолчанию. Пулинг нужен только для часто порождаемых эффектов; эмбиентный
FX внутри чанка живёт и умирает вместе с сегментом и в пулинге не нуждается.

**Свет** — локальный свет фрагмента внутри чанка; глобальная атмосфера столба в `World_Common`.

### 9.4 Порядок работы левел-дизайнера

```
1. Блокаут сегмента серыми боксами прямо в сцене
2. Прогон в песочнице B: паук реально проходит, метрики прыжка сходятся   ← раньше всякой красоты
3. Замена боксов на кит-модули ENV_*
4. Расстановка пропов LAB_Prop*
5. Расстановка акторов ACT_* из библиотеки (сирена, пар, дверь)
6. Звук: эмбиент на корне чанка, точечный на акторах
7. Свет и локальный Volume
8. Свернуть в CH_*-префаб — только если выполняется правило 9.5
9. Проверка контракта сегмента: маркеры на месте (раздел 7)
```

Шаг 2 — ключевой. Метрики проверяются на боксах, до вложения труда в художку.

### 9.5 Когда делать чанк-префаб, а когда оставить в сцене

Свернуть в префаб, если верно **хотя бы одно**:
- фрагмент переиспользуется два и более раз;
- над ним нужно работать параллельно с кем-то, кто правит ту же сцену;
- это самодостаточный сет-пис, который хочется тестировать отдельно в песочнице B.

Иначе — оставить в сцене. Уникальная разовая геометрия в префабе даёт лишний слой
косвенности без выгоды.

### 9.6 Плохие практики — с привязкой к проекту

| Практика | Что видно сейчас |
|---|---|
| **Контент в `Resources/`** | все рантайм-префабы проекта лежат там. Для чанков это запрет. Точная формулировка (уточнено внешней критикой): всё содержимое `Resources/` и его зависимости включаются в билд (`resources.assets`) независимо от ссылок, не стрипаются и плохо масштабируются для стриминга и обновления контента; большие папки замедляют старт (при запуске строится индекс). Это **не** значит, что всё одновременно резидентно в RAM — ассеты грузятся при `Resources.Load`. Чанки — **ссылками из сцены** (по умолчанию); Addressables — не рефлекс, а вариант решения, **если** появится удалённый контент или инкрементальные обновления |
| **Монолитный чанк** | `CH_Tuts_Level_001` — 417 вложенных префабов и 29 скриптов в одном ассете. Это уже не чанк, а уровень в префабе: тяжело открывать, невозможно вести вдвоём |
| **Логика размазана** | 7 чанков из 16 несут скрипты, 9 не несут. Правила, где живёт поведение, нет |
| **Разнобой в именах** | `CH_` и `CHN_` одновременно; `CH_Factory_002 1.prefab`, `LAB_PropFridge_B (1).prefab`, `LAB_PropPlaystation .prefab` — копипаст-артефакты, пробелы и скобки в именах ассетов |
| **Нет слоя акторов** | ноль `AudioSource` и `ParticleSystem` в environment-префабах: «жизнь» фрагмента не переиспользуется и не тестируется |
| **Дрейф оверрайдов** | правка инстанса в сцене вместо префаба: изменения базы перестают доезжать. Лечится дисциплиной — править в Prefab Mode |

### 9.7 Стыковка со схемами A и B

- **Чанк** — единица переиспользования между сегментами.
- **Сегмент-сцена** — единица стриминга.
- В песочнице B тестируется **чанк**, а не обязательно целый сегмент:
  `Sandbox_Root` + сцена с одним чанком и маркером спавна. Дозрел — инстанцируется
  в любой боевой сегмент. Это более мелкая и быстрая петля, чем тест сегмента целиком.

### 9.8 Звуковой слой — что закрыть до старта производства

Звуковой слой отсутствует полностью: ни одного `AudioMixer`, ни строки работы со звуком
в `Assets/Scripts`. Прежде чем дизайнеры начнут вешать звуки на акторы, нужен минимум —
иначе каждый выставит свои громкости, радиусы и кривые затухания, и свести это будет нечем.

*Остро критично к старту:*

1. **`AudioMixer` с группами** Ambient / SFX / UI. Ничто не играет мимо групп.
2. **Граница сервиса — против глобального `AudioManager`** (уточнено внешней критикой:
   «единая точка воспроизведения» — формулировка, из которой god-object растёт сам собой):

   | Сервис владеет | Сервис не трогает |
   |---|---|
   | микшер и группы | 3D-эмиттеры на акторах — это обычные `AudioSource` на префабе с нужной группой |
   | пул one-shot | точечные звуки актора: играются самим актором |
   | разрешение аудиозон | — |

3. **Аудиозона — вычисляемое состояние.** Каждый тик система определяет, в какой зоне
   слушатель, и сводит микс к этому состоянию. Триггеры допустимы как подсказка-оптимизация,
   **никогда как источник правды** — тогда пропуск триггера на скорости падения ничего
   не ломает, состояние сходится на следующем тике.
4. **Форма зоны — по акустике места, а не по одному правилу:** замкнутое пространство
   (интерьер лаборатории) — объём или портал; открытое — расстояние. Сфера вокруг корня
   локации протекает сквозь стены и для интерьера не годится.
5. **Fade-out перед выгрузкой сегмента** — иначе выгрузка вместе со звучащим эмбиентом
   даёт щелчок. Место уже есть: `DeactivateAsync` в протоколе сегмента (9.17), порядок
   «деактивация → выгрузка» там зафиксирован.

### 9.9 Проверка модели «этаж = сцена, локация = префаб»

Предложенная владельцем модель: вертикаль делится на этажи, этаж — одна сцена,
на этаже несколько локаций-биомов в виде префабов, внутри локации — акторы.

**В основе верно.** Уточнения ниже не отменяют модель, а снимают три места,
где она даёт сбой при масштабировании.

### 9.10 Три диссонанса и их разрешение

**Диссонанс 1. Этаж — единица замысла, сцена — единица памяти.**
Этаж придумывается по смыслу (тема, настроение, поворот), а сцена должна стримиться
примерно одинаковой ценой. Просторный атриум с пятью локациями и короткий технический
переход — это два очень разных бюджета в одном понятии «этаж».

*Разрешение:* по умолчанию один этаж = одна сцена, но архитектура **не должна это
предполагать**. Тяжёлый этаж режется на две сцены, пара лёгких склеивается в одну.
Каталог сегментов оперирует сценами, а не этажами; этаж — ярлык для людей.

**Диссонанс 2. Шов между этажами проходит там, где самое интересное.**
В игре про подъём ключевая геометрия — переходы: шахта, труба, лестница с этажа на этаж.
Объект физически принадлежит обеим сценам сразу. Отдать нижней — верх подъёма исчезнет
под игроком при выгрузке; отдать верхней — низа не будет, пока верх не догрузится.

*Разрешение — дизайнерское, не программистское:* **границу этажа выбирает левел-дизайнер**
и режет по закрытым точкам — площадка, чекпоинт, тамбур — **никогда посреди подъёма**.
Сверху страхует полоса перекрытия: в её пределах загружены обе сцены. Это надёжнее
и дешевле любой технической хитрости с переносом объектов между сценами.

**Диссонанс 3 (главный). «Локация = префаб» верно не всегда.**
Игра про постоянную новизну: большинство локаций **уникальны**. Уникальный контент,
завёрнутый в префаб, даёт оверрайды на инстансе, их дрейф и лишний слой косвенности
без единой выгоды.

*Разрешение:* **префабность определяется переиспользованием, а не местом в иерархии.**
Слой «локация» существует как понятие всегда, но станет ли он ассетом — отдельное решение:

| Локация | Чем является |
|---|---|
| повторяется (техшахта, типовой коридор, служебка) | **префаб** |
| уникальный герой-вид | **ветка в сцене**, собранная из кит-модулей и акторов |

Акторы и кит-модули при этом префабы всегда — переиспользование у них по определению.

**Дополнительно: глубина вложенности.** Сцена → локация → под-локация → актор → кит —
это уже 4–5 уровней ассетов при рекомендованных ≤5–7. Плюс правка кит-модуля потребует
открыть пять уровней Prefab Mode. Держать ~3 уровня ассетов (кит → актор → локация),
композицию выше делать сценой.

### 9.11 Технический ответ: диссонанса нет при одном условии

Запечённые данные принадлежат **сцене**, а не префабу:

| Данные | Поведение |
|---|---|
| Лайтмапы | грузятся и выгружаются **по сцене** — ложится на стриминг идеально |
| Light Probes (классические) | **legacy-путь, у нас не используется** (решение — 9.15, проект на APV). Для справки: общие для сцен, запечённых вместе; при аддитивной за/выгрузке требуют рететраэдрализации |
| Occlusion culling | печётся **набором сцен** в один общий ассет (на старте не используется — 9.15) |
| **Статичный** префаб, инстанцированный в рантайме | не получает запечённый свет сцены, не участвует в запечённом окклюжне и build-time static batching |

Отсюда прямой ответ на вопрос о диссонансе между аддитивностью и префабами:

> **Диссонанса нет — при одном условии: локации расставляются в сцене на этапе авторинга,
> а не спавнятся скриптом в рантайме.**
> Сцена — то, что стримится. Префабы — то, из чего сцена собрана заранее.
> Как только чанки начинают инстанцироваться кодом, теряются запечённый свет,
> окклюжн и статик-батчинг разом.

*Оговорка (уточнено внешней критикой): предупреждение касается **авторской статичной
геометрии, участвующей в бейке** — стен, полов, чанков. Динамика, заспавненная фабриками
(пикапы, FX, пул — 8.1), заведомо дорогой **не** является: освещается пробами/APV,
батчится SRP Batcher'ом (у нас URP — он включён по умолчанию), массовое закрывается
GPU instancing и пулом. Не переносить это предупреждение на неё.*

**Отдельное предупреждение про APV.** В Unity 6 URP каждая сцена по умолчанию попадает
в свой Baking Set, и **активным может быть только один Baking Set одновременно**.
Для столба, где загружено 3–5 этажей сразу, это значит: либо один Baking Set на весь
столб (или на группу этажей), запечённый вместе, либо отказ от APV в пользу реалтайма.
Решать **до** того, как будет напечён свет на двадцати этажах — переделка потом дорогая.

### 9.13 Возражения против этой же схемы

**A. Противоречие внутри схемы: уникальную локацию нечем тестировать.**
Пункт 9.10 говорит: уникальная локация — ветка сцены, а не префаб. Пункт 9.7 говорит:
в песочнице тестируем чанк. Ветку сцены в песочницу не перетащишь — то есть для контента,
который в этой игре будет преобладать, тестового пути не предусмотрено.

*Исправление:* в песочнице **две гранулярности**, ровно по двум способам авторинга:

| Что тестируем | Как загружаем в песочницу |
|---|---|
| переиспользуемая локация (префаб) | сцена-обёртка с одним экземпляром префаба |
| уникальная локация (ветка сцены) | **сама сцена-этаж**, поверх песочницы вместо боевого директора |

Схема B должна уметь принимать сцену-этаж целиком, а не только фрагмент.

**B. Слой коллайдера — это геймплей, и он живёт в художественном префабе.**
Проверено по коду: `LegRaycast` пускает лучи ног по сериализованной маске слоёв, а слой
`NotMoveable` **запрещает пауку двигаться** — `MovementState` обнуляет скорость,
`GroundedState` и `RecoveryState` на него ветвятся. То есть **поле `layer` на коллайдере
кит-модуля напрямую решает, проходима поверхность или нет.**

Риски: кит из ассет-стора приезжает на `Default`; дизайнер дублирует префаб и забывает слой —
визуально та же стена ведёт себя иначе; вариант префаба переопределяет слой, и дрейф
не виден во вьюпорте.

*Следствие для регламента:* **слой — часть контракта кит-модуля, а не решение на инстансе.**
Модуль поставляется с уже проставленным геймплейным слоем; менять слой на инстансе —
запрещённая операция. Плюс валидатор: пройти по сцене-этажу и подсветить коллайдеры на `Default`.

**C. Метрика кита не выведена из паука.**
Числа есть — `StepLength 0.85`, `DistanceFromGround 0.5`, `GroundStateRayDistance 3`,
прыжок из `MaxHeight` / `TimeToReachMaxHeight` — но модульная сетка нигде не зафиксирована.
При этом китов уже больше пятисот префабов.

*Возражение:* если размер модуля не согласован с досягаемостью паука, кит остаётся
декоративным — каждую игровую поверхность всё равно придётся лепить руками, и кит
не ускоряет левел-дизайн, ради чего он и заводится.

*Исправление:* до массового производства вывести и заморозить метрику (размер модуля,
высота уступа, ширина проёма, толщина стены) из фактических чисел паука, проверив
в песочнице. Это стандартная практика модульных китов.

**D. Состояние акторов при выгрузке этажа.**
Игрок открыл дверь на этаже 5, упал на этаж 3, поднялся обратно — этаж 5 успел выгрузиться
и загрузиться заново. Дверь снова закрыта.

Сейчас переживают перезагрузку только чекпоинты и генераторы — через `MarkerUniqueId`
плюс `ISavedProgress` / `IProgressWatchersService`. У акторов внутри локаций такого механизма нет.

*Коварство:* при политике `KeepAll` (первый этап) дефект не проявляется вовсе. Он всплывёт
ровно в день включения стриминга, когда контента уже много.

*Исправление:* акторы с состоянием подключаются к **уже существующему** механизму прогресса
(`MarkerUniqueId` + `ISavedProgress`), а не изобретают свой.

**Вердикт владельца:** мир помнит по умолчанию. Всё, что совершил игрок — включил рычаг,
запустил генератор, открыл дверь, — сохраняется. Упав в самое начало, игрок должен быть
спокоен, что коридоры и быстрые пути уже открыты. Исключение — неотключаемые ловушки
и циклические опасности: они живут своей жизнью и памяти не имеют.

*Следствие для регламента:* **память включена по умолчанию, отсутствие памяти — явное
исключение на акторе.** Обратное тому, что предполагалось выше.

*Следствие для приоритетов:* раз память по умолчанию, стабильный `UniqueId` перестаёт быть
делом одних чекпоинтов и становится несущей конструкцией — он нужен каждой двери и каждому
рычагу. Реализовано в **7.2**: система стабильных ID — нулевая фаза критического пути
(вынесена из отложенного 7.1 по итогам внешней критики).

### 9.14 Командная работа и мерж

**Что уже сделано правильно:**

| Проверено | Состояние |
|---|---|
| `m_SerializationMode: 2` (Force Text) | ✅ обязательное условие выполнено |
| `.gitattributes` | ✅ качественный: сцены и префабы помечены `merge=unityyamlmerge` и `lockable` |
| Git LFS | ✅ настроен и установлен, покрывает текстуры, модели, аудио, видео |
| `.gitignore` | ✅ есть |

**Дыра ровно одна, и она критическая.**
`.gitattributes` объявляет драйвер `merge=unityyamlmerge`, но **сам драйвер в конфиге
репозитория не настроен** — это прямо записано в комментарии внутри файла как невыполненное.
Значит при конфликте в `.unity` или `.prefab` Git не знает, чем их сливать, и падает
на обычный текстовый мерж, который для Unity YAML даёт битую сцену.

Настройка локальная, то есть **её обязан выполнить у себя каждый участник** — это первый
пункт регламента, а не разовое действие.

**Структурный принцип: конфликты не решают, их не создают.**

| Ситуация | Решение |
|---|---|
| двое на разных этажах | ноль пересечений — этаж = отдельная сцена |
| двое на одном этаже | это **триггер разделения**: либо локацию в префаб (правило 9.5), либо этаж на подсцены по дисциплине — арт / дизайн / свет (ось из 4.2) |
| один этаж, разделить нельзя | **крайняя мера** — лок; `lockable` в `.gitattributes` уже проставлен, см. ниже |

**Лок — крайняя мера, а не основная модель координации.** Порядок всегда такой:
разделить файлы (сцена на человека, локация в префаб) → и только если разделить нельзя,
брать лок. Лок добавляет операционную зависимость: забыли снять, работа с двух машин,
офлайн, расхождение remote и локального состояния.

> **Найдено в рабочей копии:** механизм уже активен и уже рассогласован.
> `Assets/Scenes/Bootstrap.unity` — права `-r--r--r--` (только чтение),
> `Assets/Scenes/SCN_Test.unity` — `-rw-r--r--` (записываемый). LFS-хуки
> `post-checkout` и `post-merge` установлены. Дизайнер, открывший сцену
> в состоянии «только чтение», упрётся в невозможность сохранить.
> **Нормализовать состояние прав до начала командной работы.**

**Ответственность и аварийное снятие:**

- лок берётся на рабочую сессию и **снимается в конце дня** — не «на всякий случай» и не бессрочно;
- владелец лока указывается в командном канале, когда берёт его больше чем на день;
- забытый лок снимает второй участник принудительно, **предварительно убедившись,
  что владелец не работает над файлом** — принудительное снятие при незакоммиченных
  правках владельца означает потерю его работы;
- лок на файл, который никто не правит, — это дефект процесса, а не безопасность.

**Бутылочное горлышко: `GameData.asset`.**
Все дизайнеры при каждом «Collect» пишут в один Odin-сериализованный ассет на 1466 строк.
Формат позиционный — пары `Entry:` / `Data:` без имён на большинстве узлов; UnityYAMLMerge
не сольёт его осмысленно. Это **структурная преграда для параллельного левел-дизайна**
и второй, независимый довод к 7.1.

*Решение — техническое, см. 7.5.* Организационный паллиатив («Collect нажимает один
назначенный человек») из документа убран по итогам внешней критики: он не защищает
ни от забывчивости, ни от нажатия в неверной активной сцене, ни от слияния маркеров
нескольких загруженных сцен, ни от самого конфликта. Причина конфликта — общий ассет,
и она устраняется разделением запечённых данных по сегментам, при сохранении запекания.

**Дневной регламент:**

```
УТРО
 1. git pull ДО открытия Unity          ← не наоборот: Unity держит файлы и кэш
 2. открыть Unity, дать импорту доесть
 3. взять лок на свои файлы             git lfs lock Assets/Scenes/Floor_05.unity

ДЕНЬ
 4. работать только в своих сценах и префабах
 5. общие ассеты (GameData, настройки проекта, слои, теги) — не трогать без уговора
 6. коммитить часто и мелко             ← цена неразрешимого конфликта = переделать
                                          свою работу с последнего коммита

ВЕЧЕР
 7. сохранить сцены и ЗАКРЫТЬ Unity     ← иначе .unity на диске не совпадает с видимым
 8. git pull                            ← merge, НЕ rebase — пояснение ниже
 9. конфликт в .unity/.prefab — только через UnityYAMLMerge, никогда текстовым мержем
10. commit + push, .meta коммитить ВМЕСТЕ с ассетом
11. снять лок                           git lfs unlock ...
```

**Три правила, которые чаще всего нарушают:**

1. **`.meta` коммитится вместе с ассетом.** Ассет без `.meta` у второго участника
   переимпортируется с новым GUID — и все ссылки на него по проекту рвутся молча.
2. **Unity закрыт или сцены сохранены до коммита.** Иначе коммитится не то, что на экране.
3. **Конфликт в сцене никогда не решается «принять свою версию»** — это тихо стирает работу
   второго. Конфликт в сцене = позвать второго участника, решать вдвоём.

**Почему merge, а не rebase** (исправлено по итогам внешней критики — раньше здесь стояло
`pull --rebase`): rebase проигрывает **каждый локальный коммит** против новой базы, поэтому
конфликт в сцене придётся разрешать **по разу на коммит**. Merge разрешает его один раз.
Для YAML на 657 объектов разница между «один раз» и «пять раз» решающая.

**Граница документа.** Всё выше — правила, **специфичные для сцен**: мета-файлы, закрытый
Unity перед коммитом, драйвер `UnityYAMLMerge`, структурное разделение файлов, локи.
Общая стратегия ветвления сюда **не входит** и не должна: в репозитории уже есть практика
(ветки по людям — `Boris-16-05-26`, `Rasim_Dev`; по фичам — `Aiming_Feature`, `Dev`),
её описание — отдельный документ (раздел 12).

**Честная оговорка.** UnityYAMLMerge закрывает многие случаи, но не все. Надёжный ответ
для сцен — предотвращение через разделение файлов, а не разрешение конфликтов. Мелкие
частые коммиты — страховка на случай, когда предотвратить не удалось.

**И более важное (по итогам внешней критики): merge, прошедший без конфликтов,
не означает целую сцену.** SmartMerge сводит YAML структурно, по идентификаторам объектов.
Результат может разобраться движком и при этом быть семантически битым: ссылка на удалённый
объект, оверрайд, который больше ни к чему не применяется, осиротевший GameObject.
«Конфликтов нет» — это не «всё хорошо».

**Ритуал после мержа сцены или префаба — одна минута:**

```
открыть сцену → консоль чиста (missing scripts / missing references)
              → сохранить
              → git diff после сохранения МАЛЕНЬКИЙ
```

Третий шаг — и есть проверка сериализации: если Unity при сохранении переписывает половину
файла, значит SmartMerge собрал то, что движок корректным не признал. Видно сразу,
инфраструктуры не требует.

Автоматическая EditMode-валидация после мержа — в отложенных, вместе с появлением тестовой
инфраструктуры (там же лежит прогон `KeepActiveOnly`).

### 9.15 Запечённый свет, APV и чанки-префабы

**Правила, подтверждённые документацией Unity:**

| Правило | Следствие для столба |
|---|---|
| Лайтмапы грузятся и выгружаются **по сцене** | на этажи ложится идеально |
| Сцену можно добавить **только в один** Baking Set | этаж принадлежит ровно одному набору |
| «Загружать несколько сцен вместе можно только если они в **одном** Baking Set» | **все одновременно загружаемые этажи обязаны быть в одном наборе** |
| «При одновременной загрузке нескольких сцен свет может оказаться слишком ярким, потому что URP суммирует свет всех сцен» | источники света этажа не должны светить в соседние |
| Occlusion culling печётся **набором сцен** | нарезка на наборы — общая для APV и окклюжна; **на старте baked occlusion отключён**, см. ниже |

**Что в проекте сейчас:** Baking Set заведён **на каждую сцену отдельно** —
`GameScene Baking Set`, `Scene_StaticMesh Baking Set`, `SCN_WIP Baking Set` (последний
уже запечён, есть `CellData.bytes`). В `Scene_StaticMesh` — 46 упоминаний ProbeVolume,
в `SCN_LevelDesingDraft` лежит `LightingData.asset`.

При этом в рантайме грузятся **две сцены из разных наборов** (`LoadScene` + `AdditiveScenes`).
По правилу выше активным может быть только один набор. **Стоит проверить в Play Mode,
корректно ли освещается паук** — он динамический объект и светится от проб.

**Рабочая гипотеза для целевой схемы** (понижено с «правила» по итогам внешней критики —
утверждение выведено из документации, не из эксперимента): один Baking Set на группу
совместно загружаемых этажей; при коридоре падения такая группа тяготеет к «весь столб».
Disk streaming для APV снимает вопрос рантайм-памяти, но **не** вопрос итерации: правка
одного этажа против перепекания набора — это и есть больное место, и его цену мы не мерили.
Выбор группировки — только по результатам спайка ниже.

**Транзитивное замыкание: промежуточной группировки не существует**
(по итогам второй внешней критики — прежний fallback «разбить по 2–3 этажа» был
доказуемо неверен).

Из двух правил Unity — сцена входит ровно в один набор, и одновременно загружаемые сцены
обязаны быть в одном наборе — при полосе перекрытия следует:

```
Seg_N и Seg_N+1 загружены вместе  ⇒  они в одном наборе
верно для КАЖДОЙ соседней пары
«быть в одном наборе» — отношение транзитивное
⇒  Seg_1 ~ Seg_2 ~ … ~ Seg_N  —  все в одном наборе
```

На стыке любых двух «групп по 2–3 этажа» понадобятся оба этажа сразу, и правило снова
нарушено. Цепочку можно разорвать **только там, где два соседних этажа никогда
не загружены вместе** — то есть на жёстком переходе без перекрытия (шторка, шлюз, лифт
с загрузкой). А это **решение гейм-дизайна, а не техническая настройка**.

Поэтому вариантов ровно два:

| Вариант | Что означает |
|---|---|
| **Один Baking Set на весь столб** | APV с disk streaming для того и сделан; цена — итерация бейка |
| **Явные жёсткие границы** | столб режется на независимые области переходами без перекрытия; требует решения гейм-дизайна |

**Спайк APV — обязательный гейт до первого боевого запекания.**
Остро критично; условия: Unity 6000.3.20f1, наш URP asset, **player build, не только
редактор**. Протокол:

1. Три аддитивные сцены в одном Baking Set; загрузка/выгрузка в разных порядках,
   включая сценарий падения (быстрый пролёт вниз через сцену).
2. Локальные источники света у швов — проверка утечек света между этажами.
3. Правка одного этажа: что перепекается (весь набор или сцены выборочно) и сколько времени.
4. Объём cell data на этаж, **пиковая память**, время загрузки набора и **время активации**.
5. Паук (динамический объект, светится от проб) освещён корректно во всех состояниях.
6. **`World_Common` и прочие постоянно загруженные lighting-contributor сцены** — влияют ли
   они на группировку, то есть обязаны ли входить в набор наравне с сегментами.
7. **Переход через границу предполагаемых наборов** — проверка того самого случая,
   который ломает промежуточную группировку.
8. **Одновременное присутствие верхнего и нижнего окна** полосы перекрытия.
9. **Disk streaming** под нагрузкой: поведение при быстром пролёте вниз.

**Критерии принятия** (поля фиксируются сейчас, пороги заполняются при спайке):
итерация бейка одного этажа ≤ __ мин; cell data ≤ __ МБ на этаж; пиковая память ≤ __ МБ;
время активации ≤ __ мс; ноль видимых утечек на швах; освещение паука корректно
в player build.

**Не прошло** → либо жёсткие границы (гейм-дизайн), либо отказ от APV в пользу
реалтайм-света (отдельное решение с новой ценой). Промежуточной группировки нет.

Lighting Scenarios (смена настроения с высотой) — не входит в спайк первой волны;
вариант решения, если появится такой художественный запрос.

**Решение: система проб — APV, классические Light Probes не используются**
(зафиксировано по итогам внешней критики №13; решение владельца, совпадает
с направлением Unity — APV позиционируется для больших стримящихся миров,
классические пробы в Unity 6 — legacy-путь). Следствия:

- рететраэдрализация (`LightProbes.TetrahedralizeAsync`, `needsRetetrahedralization`)
  **не входит** в протокол директора — при APV её не существует;
- случайные `Light Probe Group` (ассет-стор, старые сцены) ловит валидатор (6.1) —
  иначе в проекте молча заведутся две системы проб;
- *вариант решения, если* когда-либо вернёмся на классические пробы: готовый рецепт
  из критики — пакет сегментов загружен → probe data готова → **один** коалесцированный
  `TetrahedralizeAsync` на пакет (не после каждой сцены) → сегменты `Ready`.

**Решение: baked occlusion на старте не используется** (по итогам внешней критики №14,
вскрывшей конфликт запечённого окклюжна с произвольными политиками стриминга).

*Остро критично к старту — отключён, и вот почему:*

- Umbra требует **замороженной геометрии** — как и свет. На прототипе, где визуал
  выстраивается от общего к частному по скриншотам, каждый перебейк это выброшенное время.
- В вертикальном столбе с длинными взглядами вверх и вниз отсекать особо нечего —
  главную отсечку уже делает **сам стриминг**: дальние этажи физически выгружены.
- Раз бейка нет — нет и проблемы групп совместимости. Моделировать нечего.

*Правило на будущее, если baked occlusion понадобится:* **группа окклюжн-бейка =
группа APV Baking Set**. Это одно и то же множество «сцены, которые могут оказаться
загруженными вместе» — отдельные `OcclusionGroupId` / `LightingBakeGroupId` /
`AllowedCoexistenceSet` были бы тремя именами для одного понятия. Размер группы
проверяется тем же спайком (выше). Загрузка подмножества совместно запечённых сцен
легальна; запрещено только пересечение групп — и это запрещает сама группировка.

*Вариант решения, если* профилирование первых собранных этажей покажет overdraw:
сначала **GPU occlusion culling** (Unity 6 URP, GPU Resident Drawer) — работает в рантайме,
бейка не требует, групп совместимости не знает и потому дружит с любой политикой стриминга.
Сейчас выключен: `m_GPUResidentDrawerMode: 0` во всех четырёх URP-ассетах проекта.
Baked Umbra по группам — только если GPU-отсечки окажется мало.

**Конфликт запечённого света с чанками-префабами.**
По справке Unity: простого способа положить в префаб данные о том, какой лайтмап
использовать, его координаты и масштаб, **нет**. Назначение лайтмапа — это данные рендерера
в конкретной сцене; префаб их не переносит. Именно поэтому существуют сторонние
скрипты вроде PrefabLightmapping.

*Практическое следствие:* работать с чанком как с префабом можно и нужно — но **свет
принадлежит сцене-этажу и печётся последним, после того как форма заморожена.**

### 9.16 Скорректированный пайплайн левел-дизайна

```
1. ГРЕЙБОКС всего этажа            в СЦЕНЕ-этаже, не в префабе
        │
2. ПРОГОН МЕТРИК в песочнице       сцена-этаж целиком; паук проходит?
        │
3. РАЗРЕЗ НА ЛОКАЦИИ               ПО СМЫСЛУ (лаборатория, шахта, атриум),
        │                          НЕ по геометрии и не «по четвертям»
4. локация ──┬─ сработал триггер 9.5 ──► ПРЕФАБ, осмысленный pivot
             └─ не сработал ──────────► ветка сцены
        │
5. РАБОТА В ПРЕФАБЕ                форма · кит · пропы · акторы ·
        │                          декор · материалы · шейдеры · поведение
        │                          ← всё это МОЖНО тюнить в изоляции
6. СБОРКА ЭТАЖА                    расстановка, стыки, маркеры контракта
        │
7. ЗАМОРОЗКА ФОРМЫ                 ◄── рубеж
        │
8. СВЕТ                            только в СЦЕНЕ-этаже, НЕЛЬЗЯ в изоляции
        │                          (окклюжн на старте не печём — 9.15)
        │
9. ЗАПЕКАНИЕ                       в общем Baking Set столба
```

**Пункт приёмки после включения стриминга:** каждый сегмент прогоняется в режиме
**Production Simulation** (5.1) в политике `KeepActiveOnly` — цикл unload→reload, состояние
восстановилось, ошибок в консоли нет. Именно в этом режиме, а не в Authoring Sandbox:
политика стриминга — поведение директора, которого в песочнице нет. Пока тестовой
инфраструктуры нет, это ритуал чек-листа; при её появлении — автотест.

**Главная дисциплина, которую задаёт запечённый свет:** пайплайн делится рубежом на
две фазы — «форма и геймплей» (свободные дешёвые итерации в префабе) и «свет»
(после заморозки формы). Любая правка декора после запекания обесценивает бейк этажа.

**Что можно и чего нельзя тюнить в изолированной песочнице:**

| Можно | Нельзя |
|---|---|
| форма и метрики | запечённый свет — другие соседи, другой баунс |
| декор, материалы, шейдеры | окклюжн — печётся набором сцен (когда/если включим) |
| поведение акторов | звуковой баланс с соседними локациями |

**Распаковывать ли префаб при переносе в билд-сцену — нет.** Распаковка убивает главное
преимущество: правка префаба автоматически доезжает до всех сцен. Оверрайды на инстансе —
индикатор долга: если правок в сцене больше, чем в префабе, либо перенести их в префаб,
либо честно распаковать.

*Оговорка:* оверрайды, связанные с запечённым светом, неизбежны и в префаб
не применяются — их придётся отличать от содержательных. Это цена схемы.

### 9.17 Протокол сегмента

> Принято по итогам внешней критики: в документе была схема стриминга, но не был
> определён жизненный цикл сегмента. **Реализация протокола — гейт включения стриминга,
> не первый этап** (на политике `KeepAll` выгрузки нет, `UnloadSceneAsync` в коде проекта
> не встречается ни разу). Но семантика фиксируется сейчас, чтобы контракт сегмента
> и директор проектировались под неё.

**Почему это не теория.** Наше же решение из раздела 8 — сегменты без своего
`SceneContext`, инъекцию прогоняет директор после загрузки — создаёт окно между
`LoadSceneAsync.isDone` и концом инъекции, в котором `Awake`/`OnEnable`/триггеры акторов
уже исполняются, а зависимости ещё не пришли. То же с регистрацией в save-системе
(`ProgressWatchersService.RegisterWatchers` вызывается извне после создания объекта).
И главный жанровый кейс: падение может вернуть паука в сегмент, который прямо сейчас
выгружается, — а `UnloadSceneAsync` в Unity **неотменяем**.

**Состояния сегмента — шесть, не больше:**

```
Unloaded ──► Loading ──► Ready ──► Active
                │           ▲         │
                │           └─────────┘  Deactivate
                ▼           │
             Failed ────────┴──► Unloading ──► Unloaded
          (откат обязателен)
```

`Loading` включает в себя загрузку сцены, инъекцию и регистрацию как внутренние шаги —
снаружи они неразличимы и отдельных публичных состояний не заслуживают.

**Выход из `Active` — только через `Ready`** (исправлено по итогам второй внешней критики:
диаграмма рисовала `Active → Unloading` в обход, а интерфейс и правило «сначала деактивация
и дерегистрация, потом `UnloadSceneAsync`» говорят иное). Порядок: `DeactivateAsync` →
`Ready` → `ReleaseAsync` → `Unloading`.

**`Failed` — не покой, а «загрузка прервана, требуется откат»** (исправлено там же).
Прежняя редакция «`Failed` = сегмент считается выгруженным» верна только для случая,
когда загрузка не состоялась вовсе. Но отказ может случиться и после того, как сцена
уже в `SceneManager`: `Awake` прошёл, часть акторов зарегистрирована, и тут инъекция
бросила исключение. Считать такой сегмент выгруженным — значит никогда его не выгрузить
и однажды загрузить второй экземпляр.

Поэтому: **единственный законный переход из `Failed` — в `Unloading`**, и сегмент
считается выгруженным только после **подтверждённого отката**, в обратном порядке:

```
деактивировать активированное → дерегистрировать зарегистрированное
→ выгрузить загруженную сцену → дождаться подтверждения выгрузки
```

Это та же дисциплина обратного порядка, что и при штатной выгрузке. Отдельного состояния
вроде `CleanupPending` не требуется — им и является `Failed` в этой редакции.

**Инвариант:** сегмент не `Active` — триггеры и логика его акторов не работают.
Акторы просыпаются по команде активации от директора, а не по собственному `OnEnable`.

**`Active` не эксклюзивен — в полосе перекрытия активны оба сегмента.**

> Исправлено по итогам второй внешней критики. Молчаливая посылка «активен ровно один»
> сталкивалась с полосой перекрытия: у соседнего сегмента статический корень включён
> с `Ready` (геометрия есть, паук по ней ходит), а живой выключен — **дверь видно,
> до неё можно дотянуться, и она не работает.**

Машина состояний этого никогда и не требовала: `Active` — свойство сегмента, а не
единственная роль. В полосе активны оба, за её пределами — один. Цена ограничена тем,
что полоса узкая.

«Логически текущий этаж» остаётся одним — им пользуются политика выгрузки и гейт
чекпоинта, — и управляет им принятый гистерезис (ниже), а не порог по центру паука.
Отдельных сущностей вида `LoadedSet` / `SimulationActiveSet` не вводим: это взгляд
на уже имеющиеся состояния как на множества.

Ноги, груз и камера при этом закрыты и без активации: ноги упираются в статический
корень, включённый с `Ready`; груз живёт в динамическом слое (7.2.2); камера резидентна.

**Правила директора:**

| Правило | Зачем |
|---|---|
| На сегмент — **одна операция в полёте**; новый запрос встаёт в очередь, а не стреляет параллельно | исключает гонку «грузим и выгружаем одновременно» |
| `UnloadSceneAsync` неотменяем → возврат игрока в выгружаемый сегмент = дождаться конца выгрузки, загрузить заново | кейс падения в сегмент «между выгрузкой и уничтожением» |
| Предзагрузка **не отменяется** — токен лишь снимает ожидание результата | см. пояснение под таблицей |
| `Failed` = **откат обязателен**, затем `Unloaded` + громкая ошибка в лог | сегмент считается выгруженным только после подтверждённого отката — сцена могла успеть попасть в `SceneManager` |

**Честная семантика отмены** (исправлено по итогам второй внешней критики — раньше здесь
стояло «предзагрузка отменяема `CancellationToken`», и это было неточно):

У `AsyncOperation` от `LoadSceneAsync` **нет API отмены**. Токен отменяет **наше ожидание
результата**, а не саму операцию Unity. Поэтому:

1. **Отмена означает «результат больше не нужен»**, а не «загрузка прекращена».
2. **Начатая загрузка доходит до конца.** Затем сегмент активируется и сразу выгружается —
   через обычный `ReleaseAsync`, по общему правилу «одна операция в полёте».
3. **Дешевле не отменять, а не начинать.** Спекулятивную предзагрузку не запускать, пока
   направление движения нестабильно. В игре с коридором падения направление меняется
   мгновенно — это ровно тот случай, где отменить хочется, а нельзя.

Отсюда же **второй, независимый довод против `allowSceneActivation = false`** (первый —
в 8.1: корни недоступны, инъецировать нечего): операция застревает на 0.9 и **блокирует
очередь последующих**, включая `UnloadSceneAsync`. Приём отклонён окончательно.

**Семантика интерфейса** (форма кода — на этапе реализации; UniTask и токены в проекте
уже используются):

- `PrepareAsync(context, token)` — загрузка + инъекция + регистрация → `Ready`
- `ActivateAsync(token)` — включение логики и триггеров → `Active`
- `DeactivateAsync(token)` — обратный переход в `Ready`
- `ReleaseAsync(token)` — дерегистрация + выгрузка → `Unloaded`

**Транзакция состояния — точный порядок** (уточнено второй внешней критикой: раньше стояло
только «деактивация и дерегистрация, потом выгрузка», и не было сказано, **когда снимается
состояние**. Дерегистрировать раньше, чем снял, — значит потерять дверь, открытую
за секунду до выгрузки):

```
ВЫГРУЗКА
  заморозить события        ← ничего не меняется между снятием и записью
  → снять состояние
  → записать в PlayerProgress
  → дерегистрировать из save-системы
  → снять подписки, твины, FX
  → UnloadSceneAsync

ЗАГРУЗКА (обратный порядок)
  загрузить сцену
  → инъекция
  → регистрация
  → восстановить состояние
  → Activate                ← только теперь
```

**Восстановление строго до `Activate`** — и это безопасно именно благодаря двум корням
(8.1, п. 1а): живой корень ещё выключен, поэтому дверь не доигрывает анимацию
из закрытой в открытую на глазах у игрока, а актор не отрабатывает кадр в неверном состоянии.

**Чем директор решает, что грузить** (принято по итогам внешней критики: высота паука —
рабочая первая модель, но её нельзя зашивать в API):

1. **Сменная политика вместо зашитого Y.** Директор получает желаемый набор сегментов
   от политики (вход — контекст игрока: позиция, текущий логический сегмент, пройденный
   чекпоинт). Полоса отвечает на «принадлежит ли позиция сегменту», а не
   публикует `minY/maxY`. Первая политика — высотная; модель в интерфейсе не фиксируется.
2. **Preload-маркеры — обязательны с первого этапа стриминга.** В проекте уже есть
   телепорты (`TeleportService`, префабы `Teleports`) и катапультные механики: по чистой
   высоте директор узнаёт о прыжке только после него. Маркер на источнике телепорта
   заранее требует `Ready` для сегмента назначения; телепорт не срабатывает, пока
   назначение не `Ready`.
3. **Гистерезис границы.** Активный сегмент переключается с запасом полосы перекрытия,
   не по точному Y — гасит дребезг на границе (ноги паука цепляются за нижний сегмент,
   когда центр уже в верхнем; лифты и платформы, ползающие по границе).

Дальняя видимость верхних этажей — это не задача стриминга: решается дешёвыми прокси
(силуэт столба в слое атмосферы), а не загрузкой полных сцен ради вида издалека.

**Реализация стриминга начинается с агрессивного режима, а не заканчивается им**
(принято по итогам внешней критики: `KeepAll` маскирует ошибки жизненного цикла).
Порядок работ: сначала выгрузка гоняется в `KeepActiveOnly` (таблица 4.1), и только
потом включается мягкая боевая политика. Критерий готовности стриминга: сегмент
переживает цикл unload→reload в `KeepActiveOnly` — состояние акторов восстановлено
(память из 9.13-D), подписки очищены, в сервисах-реестрах (`SpiderRegistry`,
`FlowerRegistry`, `PlatformRegistry`, `ProgressWatchersService`) нет ссылок на
уничтоженные объекты. Риск реальный: сегодня весь мир строится одним выстрелом
(`BuildLevelState.InitGameWorld`), реестры держат прямые ссылки на сценовые объекты,
а единственный teardown — полный рестарт через `DOTween.KillAll()`; кодовая база
молчаливо предполагает «время жизни мира = время жизни сессии».

## 10. Туториал — почему он не блокирует архитектуру

Окончательного решения по туториалу нет. Есть гипотезы: обучение в начале игры с объяснением
различия режимов управления (ходьба — одно, управление платформой и камерой — другое);
сегодня же туториал — это **попап при взаимодействии с новым объектом**, и такие попапы
в будущем могут появляться и в середине игры.

Хорошая новость: **в коде уже реализовано именно это, и от структуры сцен оно не зависит.**
Разбор четырёх мест из пункта 1.4-E показывает единую семантику:

```
показать обучающий попап  =  ЭТО ПЕРВАЯ ВСТРЕЧА  И  презентация первой встречи включена
                             └──────────┬───────┘     └──────────────┬───────────────┘
                      _pickedProducts / _taskIds /            IsTutorialScene()
                      WasPicked — реестр «уже видел»,         глобальный рубильник,
                      пообъектный, лежит в прогрессе          привязанный к имени сцены
```

То есть пообъектный реестр «первой встречи» **уже есть и уже сохраняется в прогрессе** —
ровно та механика, которую описывает владелец. `IsTutorialScene()` — не логика туториала,
а всего лишь глобальный рубильник «показывать ли первую встречу вообще», случайно
привязанный к названию сцены.

**Предложение:** при миграции заменить `ISceneLoader.IsTutorialScene()` на нейтральный шов —
одно свойство вида «презентация первой встречи включена». Сегодня оно питается флагом из
конфига уровня и даёт **ровно нынешнее поведение, строка в строку**. Когда дизайн туториала
созреет, тот же шов переключается на прогресс игрока — и четыре места вызова не трогаются.

Итог: вопрос туториала **снят с критического пути**. Архитектура сцен его не предрешает,
а миграция его не ломает.

| **Мёртвый код**: `MainMenuState`, битый биндинг `GameBootstrapper`, хардкод `"ExitGameLoop"`, `GameScene` | косметика, не мешает | попутно при работе с состояниями загрузки |
| **Нормализовать права файлов сцен** (9.14): `Bootstrap.unity` сейчас `-r--r--r--`, `SCN_Test.unity` — записываемый; `lockable` активен и рассогласован | сохранение в сцену «только для чтения» упрётся молча | **до начала командной работы над сценами** |
| **EditMode-валидация сцен после мержа** автотестом (9.14) | тестовой инфраструктуры в проекте нет; пока закрывается ручным ритуалом за минуту | вместе с появлением тестовой инфраструктуры — там же прогон `KeepActiveOnly` |
| **Отдельный регламент ветвления** — практика есть (ветки по людям и по фичам), не описана | смешивать branch policy с архитектурой сцен нельзя | когда над проектом будет работать больше одного человека регулярно |
| **Мёртвый слой `TerrainNotMoveable`** — заведён, в коде не используется (7.3) | занимает слот в глобальном списке слоёв, вводит в заблуждение | при работе над физическим контрактом |
| **Правила движущихся платформ и парентинга** паука и груза (`SpiderPlane`, `PlatformSelector` есть, правила катания не определены) | механика не спроектирована | когда появится дизайн платформ-транспорта |
| **5×CS0672 в `_TerrainScan`** | предупреждения, рендер не затронут | отдельной задачей |
