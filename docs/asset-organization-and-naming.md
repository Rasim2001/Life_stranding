## 0. Зачем этот документ

В проекте уже есть рабочая база: арт в основном собран в `Art`, код — в `Scripts`,
сцены — в `Scenes`, настройки — в `Settings`, а динамически загружаемые данные —
в `Resources`. Проблема не в отсутствии структуры, а в том, что рядом живут несколько
разных соглашений:

- тип и назначение файла конкурируют как ось группировки;
- `UI`, `Materials` и часть префабов имеют больше одного возможного дома;
- встречаются `Cutscene`, `CutScene` и `CutScenes`, `Lab` и `LAB`;
- есть опечатки уровня `Infastructure`, `Pefabs`, `Poduct`, `Genereator`;
- копии получают имена `(1)`, `1`, `.001`, `_Test`, а не осмысленную роль;
- собственный контент и поставляемые пакеты местами лежат в одной ветке;
- `Resources` выглядит как обычная папка, хотя её пути используются кодом как ключи.

Попытка вылечить это одним большим переносом даст много изменений `.meta`, сцен,
префабов и строковых путей одновременно. Цена ошибки выше пользы от красивого дерева.
Поэтому принят подход: **сначала остановить рост путаницы, затем улучшать затронутые
области небольшими проверяемыми партиями**.

## 0.1 Правило в один экран

```text
НОВЫЙ ФАЙЛ
   │
   ├─ сторонний пакет? ─────────────► его собственная папка; не нормализовать
   │
   ├─ нужен только редактору? ──────► Editor/ или Editor-only assembly
   │
   ├─ сцена? ───────────────────────► Scenes/ по роли из scene-architecture.md
   │
   ├─ код? ─────────────────────────► Scripts/<Feature или Infrastructure>
   │
   ├─ художественный ассет? ────────► Art/<Type>/<Domain>/<Set>
   │
   ├─ конфигурация проекта? ────────► Settings/<System>
   │
   └─ обязан грузиться строкой? ────► Resources/ только после явного решения
                                         │
                                         └─ путь становится контрактом
```

Семь обязательных правил:

1. **Ссылки важнее красивого дерева.** Существующий рабочий путь не меняется ради косметики.
2. **У каждого нового ассета один канонический дом.** Не создаём второй `UI`, `Materials`
   или `Prefabs` на верхнем уровне.
3. **Новые имена — английский ASCII без пробелов.** Формат и словарь описаны в разделе 6.
4. **`Resources` — API, а не склад.** Новый файл попадает туда только если доказана
   необходимость загрузки через `Resources`.
5. **Сторонний пакет — неприкосновенный остров.** Не переименовываем его папки и файлы.
6. **Перенос выполняется только в Unity вместе с `.meta`.** Один перенос — одна
   предметная задача с проверкой ссылок.
7. **Старое имя не обязано быть исправлено немедленно.** Новый регламент не требует
   массовой миграции.

## 1. Границы регламента

### 1.1 Входит в регламент

- структура новых папок внутри `Assets`;
- имена собственных папок и файлов проекта;
- размещение художественных ассетов, префабов, сцен, кода и настроек;
- граница между авторским, сторонним и сгенерированным;
- правила безопасного переноса и постепенной нормализации;
- отдельный контракт для `Resources`;
- связь файловой структуры с резидентными и сменными слоями сцен.

### 1.2 Не входит в регламент

- автоматический перенос или переименование текущих ассетов;
- переписывание `Resources` на Addressables;
- рефакторинг классов, namespace и assembly definitions;
- удаление дубликатов без проверки ссылок и содержимого;
- обновление или переупаковка Asset Store-пакетов;
- ветвление Git;
- окончательное решение по архивированию текущих сцен-клонов;
- реализация каталогов сегментов и стриминга.

Эти изменения могут быть полезны, но каждое из них — отдельная задача с собственным
планом проверки.

### 1.3 Область собственности

Регламент обязателен для **новых и изменяемых собственных файлов проекта**. Он не
применяется задним числом к содержимому внешних пакетов.

```text
СОБСТВЕННОЕ                       СТОРОННЕЕ / ПОСТАВЛЯЕМОЕ
Art/<наши ассеты>                 Plugins/<Vendor>
Scripts                           Stylized Water 3
Scenes                            TextMesh Pro
Settings                          Art/VFX/Feel
Resources/<наши runtime-ключи>    Art/VFX/HighlightPlusBundle
Timeline/<наши таймлайны>         отдельные shader/tool packages
```

Если происхождение папки неочевидно, сначала назначается владелец и категория,
а уже потом обсуждается её перемещение.

## 2. Аудит текущего состояния

Аудит выполнен только чтением рабочей копии. Файлы проекта не изменялись.

### 2.1 Масштаб

По отслеживаемым файлам без `.meta`:

| Ветка | Примерный объём | Наблюдение |
|---|---:|---|
| `Assets/Art` | 3662 | основной контент, но также несколько крупных внешних пакетов |
| `Assets/Plugins` | 1502 | сторонний код и плагины |
| `Assets/_PolygonPrototype` | 1050 | отдельный прототипный/поставляемый остров |
| `Assets/Scripts` | 352 | собственный код проекта |
| `Assets/Resources` | 106 | критическая runtime-ветка |
| `Assets/Scenes` | 31 отслеживаемый файл, 9 сцен проекта | рабочие, тестовые и переходные сцены рядом |

В `Assets` более двадцати корневых папок. Само количество не является ошибкой:
часть корней создана Unity или внешними пакетами. Ошибка начинается, когда у нового
собственного файла есть два равноправных возможных адреса.

### 2.2 Что уже сделано правильно

- Есть понятные основные корни `Art`, `Scripts`, `Scenes`, `Settings`, `Resources`.
- В `Resources` уже различены `Prefabs` и `StaticData`.
- В `Art` используется стабильная верхняя ось по типу: `Models`, `Textures`,
  `Materials`, `Prefabs`, `Animations`, `Shaders`, `UI`, `VFX`.
- Сцены и префабы хранятся как текст, `.meta` ведутся в Git, бинарные ассеты покрыты LFS.
- Архитектура сцен уже определяет три слоя: `Bootstrap`, `Gameplay`, `Content`.
- Для будущего мира уже принята единица стриминга: **сегмент = сцена**.
- Переиспользуемая локация уже мыслится как префаб/чанк, а уникальное — как ветка сцены.

Эту основу нужно закрепить, а не заменять новым корнем вроде `Assets/_Project`.
Появление второго параллельного дерева сейчас только удвоит варианты выбора.

### 2.3 Где возникает путаница

| Наблюдение | Риск | Решение регламента |
|---|---|---|
| `Art/UI` и корневой `UI` | два дома для одного типа | новым UI-ассетам — только `Art/UI` |
| `Art/Materials` и корневой `Materials` | два дома для материалов | новым материалам — только `Art/Materials` |
| префабы в `Art/Prefabs` и `Resources/Prefabs` | назначение неочевидно | обычные — `Art`; строково загружаемые — `Resources` |
| сторонний код внутри `Art/VFX` | аудит `Art` принимает vendor-код за собственный | пометить как vendor-остров, не переносить |
| `Cutscene`, `CutScene`, `CutScenes` | поиск и сортировка расходятся | новый канонический термин `Cutscene` |
| `Lab` и `LAB`, `interactive` и `Interactive` | case-only конфликты на разных ОС | новый канонический `Laboratory`, `Interactive` |
| `(1)`, ` 1`, `.001`, `Untitled` | имя не объясняет различие | роль/вариант/порядковый номер в явном суффиксе |
| опечатки в путях | опечатка становится частью API/namespace | старое не трогать массово; новое писать по словарю |

### 2.4 Наблюдения по `Resources`

В собственном коде есть централизованный `AssetsPath` и прямые вызовы
`Resources.Load` / `Resources.LoadAll`. Значит физические пути в `Resources`
участвуют в поведении приложения.

Аудит выявил два строковых ключа, которым сейчас не соответствует файл по указанному
пути:

| Ключ | Текущее значение | Наблюдение |
|---|---|---|
| `GameBootstrapperPath` | `Prefabs/GameBootstrapper` | такого ассета в `Resources` не найдено |
| `FlowerPickupCutscenePath` | `Prefabs/Timeline/FlowerPickupCutscene` | ассет лежит глубже: `Prefabs/Timeline/Cutscenes/...` |

**Оба ключа сейчас инертны** — игра из-за них не падает:

- `GameBootstrapperPath` используется только в биндинге фабрики `GameBootstrapper`,
  у которой `.Create()` не вызывается нигде (мёртвый биндинг, см. `scene-architecture.md`,
  раздел 1.4-G). Реальный префаб лежит в `Resources/Bootstrap.prefab` и попадает в игру
  через сцену `Bootstrap`, а не через этот ключ;
- `FlowerPickupCutscenePath` — **ноль потребителей**, мёртвая константа.

Это **не предложение немедленно переименовать файлы** и не сообщение о живом баге.
Это кандидаты на удаление либо на починку при следующем касании соответствующих систем.
Они показывают, почему перенос в `Resources` нельзя смешивать с общей уборкой:
строка и файл расходятся молча.

### 2.5 Наблюдения по коду

У собственного `Assets/Scripts` нет своей `.asmdef`; найденные assembly definitions
принадлежат внешним пакетам. Разделение собственного кода на assemblies потенциально
уменьшит область перекомпиляции и зафиксирует зависимости, но создание `.asmdef`
меняет правила компиляции и может вскрыть неявные связи. Поэтому это **не часть
файловой уборки**, а отдельный будущий технический рефакторинг.

## 3. Основные принципы

### 3.1 Папка отвечает на три вопроса

Путь должен последовательно отвечать:

1. **Кто владеет?** Проект, Unity или внешний поставщик.
2. **Каков жизненный цикл?** Runtime, Editor-only, сцена, настройка, источник или архив.
3. **К какому домену относится?** Spider, Environment, Laboratory, UI, Water и т. п.

Имя файла после этого отвечает:

4. **Что это?** Prefab, texture, material, data, animation.
5. **Какова роль и вариант?** Actor, Kit, Prop, Mobile, LOD, AO и т. п.

### 3.2 Один канонический дом

Новый файл не кладётся туда, где «ближе сейчас». Для каждого класса файлов есть
один адрес:

- художественный материал → `Art/Materials`;
- обычный игровой префаб → `Art/Prefabs`;
- строково загружаемый префаб → `Resources/Prefabs`;
- ScriptableObject-конфигурация, назначаемая ссылкой → `Settings/<System>`;
- ScriptableObject, который обязан загружаться через `Resources.Load` →
  `Resources/StaticData`;
- runtime-код → `Scripts`;
- editor-код → `Editor` рядом с системой или общий `Assets/Editor`;
- сцена → `Scenes`.

### 3.3 Путь не кодирует всё

Не нужно одновременно дублировать тип, домен и роль на каждом уровне:

```text
ПЛОХО
Art/Prefabs/Environment/EnvironmentPrefabs/Lab/LabPrefabs/...

ХОРОШО
Art/Prefabs/Environment/Laboratory/PF_Prop_Laboratory_Pipe_A.prefab
```

Каждый уровень добавляет новое значение. Папка без собственного смысла не создаётся.

### 3.4 Стабильность важнее идеальности

Текущие верхние корни сохраняются. Переход делается по правилу:

> **Новое — сразу по регламенту. Старое — при касании, если перенос безопасен и входит
> в задачу. Критические пути — только отдельной миграцией.**

### 3.5 Авторское, сгенерированное и внешнее не смешиваются

- **Авторское** редактируется человеком и является источником правды.
- **Сгенерированное** можно воспроизвести из авторского и не правят руками.
- **Внешнее** обновляется поставщиком; локальные изменения осложняют обновление.

Один файл не может одновременно считаться двумя категориями.

## 4. Каноническая карта `Assets`

Это структура для **новых файлов** и целевое направление для небольших будущих
миграций. Она сохраняет существующие корни.

```text
Assets/
├─ Art/                         художественные и игровые content-ассеты
│  ├─ Animations/
│  ├─ Materials/
│  │  ├─ _Master/               только master-материалы
│  │  ├─ _Common/               доказанно общие материалы
│  │  └─ <Domain>/<Set>/
│  ├─ Models/<Domain>/<Set>/
│  ├─ Prefabs/
│  │  ├─ Actors/<Domain>/
│  │  ├─ Chunks/<Location>/   только переиспользуемые локации; уникальная —
│  │  │                        ветка сцены, не префаб (см. 5.2)
│  │  ├─ Kits/<Domain>/
│  │  └─ Props/<Domain>/
│  ├─ RenderTextures/<Domain>/
│  ├─ Shaders/                  собственные shader assets; vendor-острова не трогать
│  ├─ Text/
│  ├─ Textures/<Domain>/<Set>/
│  ├─ UI/<Feature>/
│  └─ VFX/<Domain>/
│
├─ Editor/                      общее editor-only tooling проекта
├─ Resources/                   только assets с runtime-загрузкой через Resources API
│  ├─ Prefabs/<System>/
│  └─ StaticData/<System>/
│
├─ Scenes/
│  ├─ Bootstrap.unity
│  ├─ Gameplay.unity
│  ├─ World_Common.unity
│  ├─ Segments/
│  ├─ Sandbox/
│  └─ _Archive~/                Unity не импортирует папки с суффиксом ~
│
├─ Scripts/
│  ├─ Cameras/
│  ├─ Common/                   только доказанно общее; не свалка
│  ├─ Hints/
│  ├─ HUD/
│  ├─ Infastructure/            legacy-имя: пока не переименовывать
│  ├─ PickupObjects/
│  ├─ SpiderController/
│  ├─ UI/
│  └─ WaterSystem/
│
├─ Settings/<System>/           собственные Unity/URP/config assets
├─ Timeline/<Feature>/          авторские Timeline assets
├─ Plugins/<Vendor>/            сторонние плагины
└─ <VendorRoot>/                существующие корни поставщиков; структура заморожена
```

### 4.1 Почему не вводится `Assets/_Project`

В новом проекте единый корень собственных файлов может быть удобен. В этом проекте
он потребует перенести почти все рабочие ассеты и одновременно оставит внешние острова.
На переходном этапе появятся два дерева: старое и новое. Это ухудшит навигацию и создаст
массовые diff, не добавляя игрового поведения.

Решение: **сохранить нынешние канонические корни и ужесточить правила внутри них**.

### 4.2 `Art`: тип сначала, домен затем

Проект уже построен вокруг `Art/Models`, `Art/Textures`, `Art/Materials`,
`Art/Prefabs`. Менять ось на feature-first сейчас невыгодно.

Канонический шаблон:

```text
Art/<AssetType>/<Domain>/<Set>/<File>
```

Примеры:

```text
Art/Models/Environment/Laboratory/MSH_Laboratory_Pipe_A.fbx
Art/Textures/Environment/Laboratory/TEX_Laboratory_Pipe_A_BC.png
Art/Materials/Environment/Laboratory/MAT_Laboratory_Pipe_A.mat
Art/Prefabs/Props/Laboratory/PF_Prop_Laboratory_Pipe_A.prefab
```

Допустимое исключение — самодостаточный внешний пакет. Его внутренняя структура
остаётся авторской.

### 4.3 `Scripts`: домен или технический слой

Первый уровень `Scripts` отвечает за систему или техническую роль. Нельзя создавать
папку по временному экрану, имени разработчика или номеру задачи.

`Common` принимает файл только если:

- у него минимум два независимых потребителя;
- он не знает о конкретной фиче;
- его название остаётся осмысленным вне исходной фичи.

Если хотя бы одно условие не выполнено, файл остаётся в папке владельца.

Существующую опечатку `Infastructure` нельзя исправлять попутно: путь связан с большим
числом файлов, а namespace `Infastructure.*` используется кодом. Будущее исправление
`Infrastructure` — отдельный атомарный рефакторинг.

### 4.4 `Settings`

`Assets/Settings` хранит только ассеты конфигурации, которые Unity импортирует и на
которые ссылается проект: URP Render Pipeline Assets, Renderers, Volume Profiles,
Build Profiles и настройки собственных систем.

Шаблон:

```text
Settings/<System>/<Asset>
```

Не смешивать `Assets/Settings` с корневым `ProjectSettings`: последний управляется
Unity и не является местом для пользовательских ассетов.

### 4.5 Старые дублирующие корни

| Корень | Статус |
|---|---|
| `Assets/Materials` | legacy; новые файлы запрещены, будущий перенос только после аудита ссылок |
| `Assets/UI` | legacy; новые файлы запрещены, канонический дом — `Art/UI` |
| `Assets/Packages` | legacy/vendor; не добавлять собственный контент |
| `Assets/MCP` | tooling; не смешивать с runtime-кодом или игровыми ассетами |
| `_PolygonPrototype`, `_TerrainScan`, `_Shields`, `_TK_Tools` | отдельные существующие острова; сначала определить владельца и способ обновления |
| `_SharedModels_DontAddToGit` | локальный обмен/источник, не канонический дом импортированных ассетов |
| `Stylized Water 3` | vendor-остров. **Пробел в имени** — исключение из правила 6.2, допустимое как поставляемая папка; не переименовывать |
| `TextMesh Pro` | vendor-остров, создан Unity; не трогать |
| `SceneNotes` | назначение не определено — назначить владельца или убрать |
| `TutorialInfo` | остаток Unity-шаблона; кандидат на удаление после проверки ссылок |
| `Timeline` | собственные Timeline-ассеты, канонический дом (см. карту в 4) |
| `Editor` | общее editor-only tooling проекта, канонический дом |

«Legacy» не значит «срочно удалить». Это значит **не увеличивать долг**.

## 5. Связь с архитектурой сцен

### 5.1 Имена и расположение сцен

Архитектура сцен задаёт имена резидентных слоёв и сегментов. Этот документ их
не переопределяет.

```text
Scenes/
├─ Bootstrap.unity              одна на приложение
├─ Gameplay.unity               один резидентный gameplay-слой
├─ World_Common.unity           общая атмосфера столба
├─ Segments/
│  ├─ Seg_01_Base.unity
│  ├─ Seg_02_Street.unity
│  └─ Seg_05_Bridges.unity
├─ Sandbox/
│  ├─ Sandbox_Laboratory.unity
│  └─ Sandbox_SpiderCamera.unity
└─ _Archive~/
```

Физический перенос текущих сцен в это дерево выполняется **только после** появления
конфигурационного шва из раздела 6.1 документа по сценам. Сейчас имя активной сцены
участвует в нескольких ветках поведения; сначала убирается эта связь, потом меняется путь.

### 5.2 Внутри сегмента

Файловая структура поддерживает правило:

```text
Seg_05_Bridges.unity
├─ уникальная геометрия и baked data ─────── в сцене сегмента
├─ переиспользуемая локация ──────────────── PF_Chunk_Bridges_*
├─ повторяемый набор модулей ─────────────── PF_Kit_*
├─ объект с поведением ───────────────────── PF_Actor_*
└─ статический одиночный объект ──────────── PF_Prop_*
```

Один и тот же объект не дублируется как «почти одинаковая» копия в нескольких
папках сегментов. Общий prefab имеет одного владельца и используется ссылкой.

### 5.3 Сегментные данные

Предложенные в архитектуре `SegmentDefinition` принадлежат автору сегмента и должны
лежать рядом как отдельные ассеты, а не собираться в один общий изменяемый файл:

```text
Settings/World/Segments/
├─ DATA_Segment_01_Base.asset
├─ DATA_Segment_02_Street.asset
└─ DATA_Segment_05_Bridges.asset
```

`TowerCatalog` — редкий агрегатор:

```text
Settings/World/DATA_TowerCatalog.asset
```

Если конкретная реализация потребует загрузки этих объектов через `Resources.Load`,
их физический адрес выбирается отдельным решением. Не следует заранее помещать их
в `Resources` «на всякий случай».

**Авторское и сгенерированное для сегмента живут раздельно** (`scene-architecture.md`, 7.5
и 7.6). `SegmentDefinition` — **авторский** ассет: `SceneReference`, флаги, дополнительные
сцены. Всё, что производится запеканием из маркеров сцены — координаты спавна, чекпоинты,
**высотная полоса** — в него не попадает и лежит отдельным per-segment файлом:

```text
Settings/World/Segments/
├─ DATA_Segment_05_Bridges.asset            авторский, правится руками
└─ Generated/
   └─ DATA_SegmentBaked_05_Bridges.asset    сгенерированный, руками не правится
```

Два правила, оба из архитектуры сцен:

- **высотная полоса авторится компонентом `SegmentBounds` в сцене**, запекается
  в сгенерированный файл, и именно его читают директор и каталог. В `SegmentDefinition`
  полосы нет — один источник правды (7.6);
- **сгенерированное пишется по сегментам**, а не в общий изменяемый ассет: именно общий
  файл сделал `GameData.asset` неразрешимым в мерже (7.5, 9.14).

### 5.4 Авторские и запечённые данные

Сгенерированный свет, APV, occlusion и другие baked-данные принадлежат сцене/сегменту,
который их породил. Их имя должно включать ключ сегмента. Общий изменяемый
`GameData.asset` не становится домом для per-segment результата.

Точное расположение Unity-generated файлов зависит от формата, который создаёт Unity.
Главный инвариант:

> По имени и ссылкам всегда можно однозначно определить сцену-владельца; generated-файл
> не редактируется вручную и не переиспользуется между независимыми сегментами.

### 5.5 Иерархия внутри сцены сегмента

Регламент папок отвечает на вопрос «в какой папке лежит файл». Но левел-дизайнер
проводит день **внутри сцены**, и там структура тоже обязательна — она не косметика,
её нарушение роняет сборку.

**Два корня — обязательны** (`scene-architecture.md`, 8.1 п. 1а):

```text
Seg_05_Bridges.unity
│
├─ Static/                     активен всегда, начиная с Ready
│  ├─ Geometry/                меш, коллайдеры, декор
│  ├─ Lighting_Local/          локальный Volume, источники света полосы
│  └─ Markers/                 LevelEntry · SegmentBounds · Checkpoints · точки пикапов
│
└─ Live/                       ★ В СОХРАНЁННОЙ СЦЕНЕ ВЫКЛЮЧЕН
   ├─ Actors/                  двери, рычаги, платформы, сирены, трубы с паром
   ├─ Events/                  триггер-зоны, зоны следящей камеры
   └─ Audio/                   эмбиент локации
```

**Почему живой корень выключен.** Пассивность акторов действует только на наш C#-код.
`AudioSource.playOnAwake`, `ParticleSystem`, `Animator`, `Rigidbody` и триггер-коллайдеры
стартуют сами, как только сцена загрузилась, — то есть **до** того, как директор активирует
сегмент. Сегмент грузится, а сирены уже воют. Выключенная иерархия закрывает это одним
движением, и стоимость покоя становится настоящим нулём.

**Почему статический корень активен раньше.** Паук, влетающий в полосу перекрытия,
не должен провалиться сквозь сегмент, который загружен, но ещё не активирован.

| Правило | Проверка |
|---|---|
| ровно два корня, имена одинаковы во всех сегментах | валидатор |
| `Live` сохранён **выключенным** | **валидатор роняет сборку** |
| коллайдеры и свет — только в `Static` | ревью |
| всё с памятью или зависимостями — только в `Live/Actors` | критерий актора, 6.4 |
| маркеры контракта не разбросаны по сцене | валидатор контракта сегмента |

**Слой коллайдера — это геймплей, а не техническая мелочь** (`scene-architecture.md`, 7.3).
`NotMoveable` запрещает пауку двигаться; ноги ставятся на нормаль рейкаст-хита. Поэтому
слой проставляется **на кит-модуле один раз** и не меняется на инстансе, а non-uniform
scale на объектах с коллайдерами запрещён — он ломает нормали.

**Межсегментных ссылок в сцене нет** (`scene-architecture.md`, 7.7). Телепорт, лифт, дверь
с другого этажа адресуются парой `SegmentDefinition + ID маркера`, а не перетаскиванием
объекта из соседней сцены: Unity не поддерживает сериализованные межсценовые ссылки,
в билде они превращаются в `null`.

## 6. Правила именования

Unity не требует единого художественного соглашения для имён обычных ассетов.
Следующие правила — **внутренний стандарт SpiderRig**, выбранный ради поиска,
предсказуемости и переносимости между Windows/macOS/Linux.

### 6.1 Общая грамматика

Для новых собственных ассетов:

```text
<TYPE>_<Domain>_<SemanticName>[_<RoleOrVariant>][_<Index>].<extension>
```

Обязательные свойства:

- английский ASCII;
- без пробелов;
- без кириллицы;
- смысловые слова в `PascalCase`;
- `_` разделяет крупные смысловые блоки;
- расширение в нижнем регистре, если формат и инструмент это допускают;
- имя объясняет отличие варианта;
- порядковые номера дополняются нулями: `01`, `02`, `10`;
- версия не хранится в имени — для этого есть Git.

```text
ХОРОШО
PF_Actor_Flower_Default.prefab
PF_Prop_Laboratory_Wall_A_03.prefab
TEX_Laboratory_Pipe_A_BC.png
MAT_Spider_Glass.mat
DATA_Segment_05_Bridges.asset

ПЛОХО
Flower 1.prefab
Lab_Wall (14).prefab
Слой 1.png
Red_.mat
NewMaterial_Final_v2.mat
Plane.001.fbx
```

### 6.2 Имена папок

- `PascalCase`: `DestroyableObjects`, `CameraSystem`, `VolumeProfiles`.
- Одно каноническое написание домена во всём проекте.
- Без пробелов и дефисов.
- Аббревиатуры читаются как слово или принятый термин: `UI`, `HUD`, `VFX`, `QTE`, `URP`.
- Не использовать имя типа во множестве вариантов: выбран `Cutscene`, не смешивать
  `CutScene`, `CutScenes`, `Cutscene`.
- Имя человека допустимо только в локальной песочнице, но не в production-ветке.
- `_Common` разрешён только для доказанно общих ассетов.
- Суффикс `~` имеет технический смысл: Unity игнорирует такую папку. Использовать
  только для осознанного архива, который не должен импортироваться.

### 6.3 Префиксы ассетов

**Ядро — шесть префиксов**, которые нужно помнить наизусть: `PF_`, `TEX_`, `MAT_`,
`MSH_`, `DATA_`, `SFX_`. Они помечены ★ в таблице. Остальные вводятся по мере появления
соответствующих ассетов — заучивать шестнадцать строк сразу не нужно, регламент, который
не помнят, не соблюдают.

| Тип | Префикс | Шаблон | Пример |
|---|---|---|---|
| ★ Prefab | `PF_` | `PF_<Role>_<Domain>_<Name>` | `PF_Actor_Spider_Player` |
| ★ Texture | `TEX_` | `TEX_<Domain>_<Name>_<Map>` | `TEX_Factory_Wall_A_N` |
| ★ Material | `MAT_` | `MAT_<Domain>_<Name>` | `MAT_Flower_Petal_Red` |
| Physics Material | `PMAT_` | `PMAT_<Domain>_<Name>` | `PMAT_Spider_SurfaceGrip` |
| ★ Model/source mesh | `MSH_` | `MSH_<Domain>_<Name>` | `MSH_Factory_Pipe_A` |
| Animation Clip | `ANIM_` | `ANIM_<Domain>_<Action>` | `ANIM_Flower_Defeat` |
| Animator Controller | `AC_` | `AC_<Domain>_<Name>` | `AC_Spider_Thruster` |
| Avatar/Mask | `AV_` / `MASK_` | по типу | `MASK_Spider_UpperBody` |
| Shader | `SHD_` | `SHD_<Domain>_<Name>` | `SHD_Common_Toon` |
| Shader Graph | `SHG_` | `SHG_<Domain>_<Name>` | `SHG_Water_Surface` |
| VFX asset/prefab | `VFX_` | `VFX_<Domain>_<Effect>` | `VFX_Generator_Sparks` |
| Render Texture | `RT_` | `RT_<Domain>_<Use>` | `RT_Spider_Glass` |
| ★ Audio SFX | `SFX_` | `SFX_<Domain>_<Event>` | `SFX_Flower_Pickup` |
| Music | `MUS_` | `MUS_<Location>_<State>` | `MUS_Laboratory_Ambient` |
| ★ ScriptableObject data | `DATA_` | `DATA_<System>_<Name>` | `DATA_Water_Global` |
| Timeline | `TL_` | `TL_<Feature>_<Event>` | `TL_Flower_Pickup` |

Префиксы не применяются задним числом к сторонним пакетам и не являются причиной
немедленного переименования существующего рабочего файла.

### 6.4 Роли префабов

Префикс `PF_` отвечает за Unity-тип, следующий блок — за архитектурную роль:

| Роль | Значение | Пример |
|---|---|---|
| `Actor` | **нужны зависимости из `Gameplay` ИЛИ есть память** — см. критерий ниже | `PF_Actor_Generator_Main` |
| `Chunk` | переиспользуемая композиция локации — **только если сработал триггер** 9.5 архитектуры сцен | `PF_Chunk_Factory_002` |
| `Kit` | модуль строительного набора без поведения | `PF_Kit_Laboratory_Wall_A` |
| `Prop` | статический или простой одиночный предмет | `PF_Prop_Laboratory_Fridge_A` |
| `UI` | UI composition/root | `PF_UI_PausePopup` |
| `FX` | визуальный эффект без доменной логики | `PF_FX_Water_Splash` |

**Критерий актора — две оси, а не «есть поведение»** (`scene-architecture.md`, 9.2):

> **Актор — объект, которому нужны зависимости из `Gameplay` ИЛИ у которого есть память.**
> Всё остальное — `Kit`, `Prop`, `FX`, даже если оно движется, светится и звучит.

Формулировка для дизайнера: **актор — то, что игра должна восстановить после перезагрузки
этажа, или то, что спрашивает что-то у игры.**

| Объект | Кто это |
|---|---|
| мигающая лампа, `Animator` без геймплея, эмбиент-`AudioSource` | **живой декор** → `PF_Prop_` или `PF_FX_`, **не** `Actor` |
| дверь, рычаг, подвижная платформа, разрушаемый предмет | **`Actor`** — есть память |
| триггер-зона, зона следящей камеры, damage surface | **`Actor`** — нужны зависимости |

Формулировка «имеет собственное поведение» слишком широка и возвращает путаницу,
которую критерий двух осей и устраняет.

Если префаб одновременно кажется `Chunk` и `Actor`, сначала решается владение
поведением по документу архитектуры сцен: **поведение живёт только на слое актора**,
чанк лишь компонует. Имя не должно маскировать смешанную ответственность.

### 6.5 Карты текстур

Принятые суффиксы:

| Карта | Суффикс |
|---|---|
| Base Color / Albedo | `_BC` |
| Normal | `_N` |
| Ambient Occlusion | `_AO` |
| Metallic | `_M` |
| Roughness | `_R` |
| Smoothness | `_S` |
| Emission | `_E` |
| Mask Map / packed map | `_Mask` с документированным порядком каналов |
| Height | `_H` |
| Opacity | `_O` |

Не смешивать в одной папке `_Albedo`, `_BaseColor`, `_Diffuse` для одного значения.
Существующие наборы можно оставить как есть; новый набор использует таблицу.

### 6.6 Сцены

Имена сцен подчиняются архитектурной роли, поэтому универсальный `SCN_` не навязывается:

| Роль | Формат | Пример |
|---|---|---|
| Bootstrap | точное имя | `Bootstrap.unity` |
| Gameplay | точное имя | `Gameplay.unity` |
| Общий мир | точное имя | `World_Common.unity` |
| Сегмент | `Seg_<NN>_<Name>` | `Seg_05_Bridges.unity` |
| Песочница | `Sandbox_<Feature>` | `Sandbox_Laboratory.unity` |
| Узкий тест | `Test_<System>_<Case>` | `Test_Streaming_UnloadReload.unity` |

`SCN_`, `Scene_`, `Test` без уточнения и имя вида `LevelDesingDraft_Test` считаются
legacy. Их будущие имена выбираются при миграции сцен, не сейчас.

**Имя не защищает от попадания в билд — защищает папка.** Песочницы и узкие тесты живут
в `Scenes/Sandbox/`, и по архитектуре сцен (раздел 5) действуют три уровня защиты:

1. папка и префиксы `Sandbox_` / `Test_`;
2. **источник правды о составе билда — каталог сегментов**, а не Build Settings руками:
   операция «применить каталог» перезаписывает `EditorBuildSettings`;
3. **валидатор роняет сборку**, если сцена из песочницы попала в билд.

Поэтому `Test_`-сцену нельзя класть рядом с сегментами «чтобы не искать» — она должна
лежать в `Sandbox/`, иначе третий уровень защиты не сработает.

### 6.7 C# и editor-код

- имя `.cs` в точности совпадает с главным типом;
- тип и файл — `PascalCase`;
- interfaces — `IName`;
- без asset-префиксов: `PF_`, `DATA_`, `SCN_` к коду не применяются;
- `Editor`-скрипт лежит в папке `Editor` рядом с владельцем либо в общем
  `Assets/Editor`;
- runtime-код не ссылается на `UnityEditor`;
- новое имя namespace следует корректному словарю, но существующий
  `Infastructure.*` исправляется только отдельным рефакторингом.

### 6.8 Запрещённые служебные суффиксы

Не использовать:

- `Final`, `FinalFinal`, `Latest`, `New`, `Old`;
- `Copy`, `(1)`, `(2)`;
- случайные даты;
- инициалы автора в production-ассете;
- `Test` для файла, который идёт в билд;
- `.001` из DCC как единственное объяснение различия;
- `v2`, `v3`, если обе версии не являются реальными runtime-вариантами.

Допустимы осмысленные варианты:

```text
PF_UI_SettingsPopup_Mobile.prefab
PF_UI_SettingsPopup_Desktop.prefab
MSH_Spider_Body_LOD0.fbx
MSH_Spider_Body_LOD1.fbx
```

## 7. Особый контракт `Resources`

### 7.1 Почему это не обычная папка

Unity включает ассеты из любой папки с именем `Resources` в Player build. Они доступны
по относительному строковому пути без расширения. В этом проекте такие пути уже
централизованы в `AssetsPath` и используются сервисами, фабриками, UI и кат-сценами.

Следствие:

> **Путь внутри `Resources` — часть программного контракта. Перемещение или
> переименование меняет ключ загрузки даже при сохранённом GUID.**

`.meta` защищает сериализованные Unity-ссылки, но не исправляет строку
`"StaticData/UI/TasksPopupData"` в коде.

### 7.2 Что разрешено добавлять

Новый ассет попадает в `Resources` только если одновременно выполнены условия:

1. он действительно создаётся/читается динамически и обычная serialized reference
   не подходит;
2. определён владелец загрузки;
3. определён момент освобождения или доказано, что ассет нужен всю сессию;
4. ключ хранится централизованно, а не размножен строковыми литералами;
5. добавлена проверка, что ключ разрешается в ассет;
6. размещение согласовано на ревью.

«Так проще найти из кода» не является достаточным основанием.

### 7.3 Что не класть

- исходные FBX, PSD и рабочие файлы DCC;
- материалы и текстуры, которые уже входят в prefab/scene по ссылке;
- контент «на будущее»;
- временные тестовые ассеты;
- большие библиотеки вариантов;
- editor-only иконки и конфигурации;
- копию ассета, который уже имеет канонический адрес в `Art` или `Settings`.

### 7.4 Текущая структура сохраняется

```text
Resources/
├─ Prefabs/<System>/
└─ StaticData/<System>/
```

Не вводить третий параллельный способ группировки. Существующие пути заморожены до
предметной миграции.

### 7.5 Перенос из `Resources`

Перенос допустим только отдельной задачей:

```text
инвентаризация всех Resources.Load / LoadAll / Zenject resource bindings
  → список ключей и владельцев
  → выбор serialized reference или Addressables
  → миграция одной системы
  → проверка Editor + development build
  → профилирование памяти/старта
  → только затем удаление старого ключа
```

Addressables — возможное направление, но не обязательное условие этого регламента.
Пакета Addressables сейчас нет в `Packages/manifest.json`; добавление новой системы
загрузки ради структуры папок было бы неоправданным расширением задачи.

## 8. Сторонние пакеты и служебные папки

### 8.1 Vendor-остров

Для каждого внешнего пакета сохраняется его собственный корень. Внутри:

- не переименовывать файлы под стандарт SpiderRig;
- не раскладывать shaders, materials и scripts по нашим папкам;
- не исправлять опечатки поставщика;
- не добавлять собственные файлы, если можно создать adapter/extension снаружи;
- обновлять пакет одной отдельной задачей.

Причина: переупаковка делает обновление поставщика ручным merge и затрудняет
определение локальных изменений.

### 8.2 Новые зависимости

Предпочтительный порядок:

1. Unity Package Manager в корневом `Packages`;
2. отдельный `Assets/Plugins/<Vendor>/<Package>`;
3. отдельный vendor-root, только если этого требует поставщик.

Нельзя импортировать новый пакет прямо в `Art/Common`, `Scripts/Common` или
`Resources` без изолированного корня.

### 8.3 Папки с подчёркиванием

Начальный `_` — только средство сортировки и сигнал специального статуса. Он сам
по себе **не исключает** содержимое из импорта или билда.

| Формат | Значение |
|---|---|
| `_Common` | часто используемое внутри конкретной ветки |
| `_Master` | master-ассеты, от которых создают экземпляры/варианты |
| `_Archive~` | архив, который Unity не импортирует благодаря `~` |
| `_SomeTool` | существующий отдельный tool/vendor-root; значение фиксируется владельцем |

Не создавать новые `_Misc`, `_Temp`, `_Old`.

## 9. Плохие практики

### 9.1 Массовая косметическая перестройка

**Плохо:** одним коммитом переименовать `Art`, `Resources`, `Scripts`, сцены и сотни
ассетов.  
**Почему:** невозможно отличить потерю ссылки от нормального diff; возрастает риск
строковых путей, merge-конфликтов и case-only проблем.  
**Правильно:** одна предметная область, отдельный коммит перемещения, отдельная проверка.

### 9.2 Второе «идеальное» дерево

**Плохо:** начать складывать новое в `Assets/_Project`, оставив старое в `Art`,
`Scripts`, `Scenes`.  
**Почему:** у каждого файла появляется два возможных дома.  
**Правильно:** улучшать уже существующие канонические корни.

### 9.3 `Resources` как глобальный service locator

**Плохо:** положить файл в `Resources`, чтобы не назначать ссылку в Inspector.  
**Почему:** строковый ключ не проверяется компилятором, ассет всегда попадает в билд,
а большие наборы ухудшают запуск и управление памятью.  
**Правильно:** serialized reference по умолчанию; `Resources` — только осознанная граница.

### 9.4 Нормализация внешнего пакета

**Плохо:** перенести его shaders в `Art/Shaders`, scripts в `Scripts`, demo-сцены
в `Scenes`.  
**Почему:** обновление перестаёт быть заменой vendor-острова и превращается в ручной merge.  
**Правильно:** оставить пакет целым; собственные adapters держать в собственном домене.

### 9.5 Дубли вместо вариантов

**Плохо:** `Lab_Wall (1)` … `Lab_Wall (14)`.  
**Почему:** имя не говорит, отличаются ли файлы или это случайные копии.  
**Правильно:** если это реальные модули — `PF_Kit_Laboratory_Wall_A_01` … `_14`;
если содержимое одинаково — один prefab и несколько экземпляров в сцене.

### 9.6 Общие папки без критерия

**Плохо:** `Common`, `Materials/Materials`, `Prefabs/Common` как место для всего,
что некуда положить.  
**Почему:** владелец и зависимость исчезают, папка растёт без границ.  
**Правильно:** общий только при двух независимых потребителях; иначе владелец — фича.

### 9.7 Перемещение вне Unity

**Плохо:** перетащить ассет в Explorer без соответствующего `.meta`.  
**Почему:** Unity выдаст новый GUID, сериализованные ссылки потеряются.  
**Правильно:** перемещать через Project window; ассет и `.meta` коммитить вместе.

### 9.8 Case-only rename

**Плохо:** отдельным движением `interactive` → `Interactive` на Windows.  
**Почему:** case-insensitive файловая система и Git могут не зафиксировать переход
одинаково у всех.  
**Правильно:** отдельная задача с временным промежуточным именем и проверкой на чистой
рабочей копии.

## 10. Безопасное внедрение

### 10.1 Фаза 0 — регламент

- согласовать этот документ;
- назначить канонические термины;
- не перемещать существующие файлы;
- применять правила ко всем новым ассетам.

**Риск:** нулевой для runtime.

### 10.2 Фаза 1 — остановить рост долга

- новые UI → только `Art/UI`;
- новые materials → только `Art/Materials`;
- новые обычные prefabs → только `Art/Prefabs`;
- новые `Resources` — только через ревью;
- vendor-пакеты — только отдельным корнем;
- копии не получают `(1)`.

**Критерий завершения:** на протяжении десятка подряд добавленных ассетов не появилось
новых неоднозначных корней и имён. Критерий по количеству файлов, а не по времени —
у команды из двух человек на прототипе нет спринтов, и календарная метрика тут не работает.

### 10.3 Фаза 2 — инвентаризация без переноса

- каталог владельцев корневых папок;
- список всех строковых resource-ключей;
- список сцен в Build Settings / будущем `TowerCatalog`;
- список дублирующих имён и предполагаемых владельцев;
- классификация `authoring / generated / vendor / archive`.

Сюда входит проверка двух найденных несовпадений `AssetsPath`, но не их автоматическая
починка.

### 10.4 Фаза 3 — миграция при касании

Когда фича всё равно меняется:

1. выбрать малую замкнутую область;
2. до переноса найти все строковые и сериализованные потребители;
3. закрыть Unity у остальных участников или согласовать лок;
4. переместить через Unity Project window;
5. сохранить ассет и затронутые сцены/префабы;
6. проверить Console, missing scripts/references и diff;
7. запустить сцену владельца и development build, если затронут runtime-path;
8. коммитить перенос отдельно от смыслового изменения.

### 10.5 Фаза 4 — архитектурные миграции

Только отдельными задачами:

- исправление `Infastructure` → `Infrastructure`;
- введение assembly definitions для собственного кода;
- перенос сцен в `Segments` / `Sandbox` после конфигурационного шва;
- вынос отдельных систем из `Resources`;
- Addressables, если это оправдано профилированием или требованиями доставки;
- очистка/замена крупных vendor demo-наборов.

### 10.6 Матрица риска

| Изменение | Риск | Требуемая проверка |
|---|---|---|
| добавить новый обычный ассет по регламенту | низкий | import + ссылка владельца |
| переименовать обычный asset через Unity | средний | references + diff + сцена владельца |
| переместить prefab, используемый сценами | средний/высокий | все сцены-потребители |
| изменить путь в `Resources` | высокий | все ключи + runtime + build |
| переименовать scene | критический до config seam | loader, Build Settings/catalog, active-scene logic |
| переименовать script/namespace | высокий | compile + serialized components + DI |
| изменить vendor-структуру | высокий, обычно запрещено | update path и полный regression |
| case-only rename | высокий | Git на чистой копии и другие ОС |

## 11. Чек-листы

### 11.1 Новый ассет

- [ ] Определён владелец: проект или поставщик.
- [ ] Выбран единственный канонический корень.
- [ ] Путь следует `Type / Domain / Set`.
- [ ] Имя — английский ASCII без пробелов.
- [ ] Есть корректный type-prefix.
- [ ] Вариант назван по смыслу, не `(1)` и не `Final`.
- [ ] Ассет не помещён в `Resources` только ради удобства.
- [ ] `.meta` добавлен вместе с файлом.
- [ ] У файла нет второго канонического дубликата.

### 11.2 Новый prefab

- [ ] Определена роль: `Actor`, `Chunk`, `Kit`, `Prop`, `UI` или `FX`.
- [ ] Поведение живёт только на actor-слое согласно архитектуре сцен.
- [ ] Baked light/occlusion не запакованы в переиспользуемый prefab.
- [ ] Prefab не создаётся вместо нескольких экземпляров уже существующего prefab.
- [ ] Имя уникально и понятно в окне поиска без просмотра полного пути.

### 11.3 Новый файл в `Resources`

- [ ] Есть причина не использовать serialized reference.
- [ ] Владелец загрузки известен.
- [ ] Ключ централизован.
- [ ] Ключ не конфликтует с другим asset-path.
- [ ] Известен жизненный цикл и освобождение памяти.
- [ ] Есть проверка missing/null.
- [ ] Проверен Player build.

### 11.4 Перенос или переименование

- [ ] Изменение входит в текущую задачу, а не является попутной косметикой.
- [ ] Найдены `Resources.Load`, scene-name и AssetDatabase string paths.
- [ ] Найдены сцены, префабы, ScriptableObjects и настройки-потребители.
- [ ] Изменение выполняется через Unity.
- [ ] Ассет и `.meta` перемещаются вместе.
- [ ] Нет параллельной работы в тех же сценах/префабах.
- [ ] Console чиста после reimport.
- [ ] Нет missing scripts/references.
- [ ] Diff содержит ожидаемый перенос, а не delete+unrelated recreate.
- [ ] Пройдена сцена владельца; для runtime-key — development build.

### 11.5 Ревью структуры

Пять вопросов:

1. С первого взгляда ясно, кто владелец файла?
2. Есть ли только один логичный адрес для такого файла?
3. Можно ли понять назначение по имени без открытия Inspector?
4. Изменился ли runtime-контракт: `Resources`, имя сцены, DI, Build Settings?
5. Можно ли откатить этот перенос независимо от смысловых изменений?

Если на любой вопрос ответ «нет», изменение нужно разделить или уточнить.

## 12. Отложенные решения

| Решение | Почему не сейчас | Условие возврата |
|---|---|---|
| Полный переход на feature-first дерево | конфликтует с уже большой type-first веткой `Art` | только при крупной смене production pipeline |
| `Assets/_Project` | создаёт второе параллельное дерево | не вводить без отдельной миграции всего собственного контента |
| Addressables | новый runtime и build pipeline, пакет пока не установлен | требования патчинга/CDN или доказанная проблема Resources |
| assembly definitions проекта | меняют границы компиляции и вскрывают зависимости | отдельный code-architecture spike |
| массовое исправление опечаток | большой diff без игрового эффекта | по одной системе при её активной переработке |
| глобальный asset-linter | сначала нужно прожить ручной регламент | после стабилизации словаря и нескольких итераций ревью |
| удаление дублей | одинаковое имя не доказывает одинаковое содержимое | dependency audit + визуальная/поведенческая проверка |
| перенос текущих сцен | имя активной сцены пока участвует в поведении | после config seam из `scene-architecture.md`, раздел 6.1 |

  Asset Database и рекомендация Addressables как системы управления runtime-ассетами.

  границы `.asmdef`, Editor-only и test assemblies.

  адреса, группы, labels, загрузка и освобождение зависимостей.
- [Архитектура сцен и уровней](scene-architecture.md) — проектные правила Bootstrap /
  Gameplay / Content, сегментов, префабов, baked data и командного мержа.

### 13.1 Что является фактом Unity, а что решением проекта

| Положение | Источник |
|---|---|
| `Editor`, `Resources`, `Plugins` и `~` имеют специальное значение | правило Unity |
| `.meta` содержит GUID и должен двигаться с ассетом | правило Unity |
| путь `Resources.Load` — строковый ключ без расширения | правило Unity |
| большие `Resources` влияют на build/startup/memory | правило Unity |
| `Art/Type/Domain/Set` | решение SpiderRig с учётом текущей базы |
| английский ASCII, `PascalCase`, таблица префиксов | внутренний naming standard |
| не вводить `_Project` и не делать big-bang migration | решение для текущего проекта |
| имена `Bootstrap`, `Gameplay`, `World_Common`, `Seg_NN_Name` | архитектура сцен SpiderRig |

Такое разделение важно: внутренний naming можно улучшать по опыту команды, но нельзя
голосованием отменить механику `Resources`, `.meta` или специальных папок Unity.
